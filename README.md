# RustOS Mobile

Экспериментальное capability-based микроядро для AArch64 на Rust.

Написано с нуля — загрузчик, планировщик, IPC, управление памятью и
capability-система без заимствованных компонентов. Запускается в QEMU, на
Raspberry Pi 5 и на Android-телефоне (тестировалось на Xiaomi Redmi Note 7, Qualcomm SDM660).

---

## Идея

Микроядро держит у себя минимум механизмов — адресные пространства, потоки,
планирование, IPC, таймеры. Драйверы, файловые системы и сетевые стеки — userspace:
файловая подсистема уже живёт там, каждое монтирование — отдельный процесс.

Доступ к любому ресурсу идёт через capability-хендл: токен на внутренний объект ядра
с набором прав. Неявной глобальной власти нет — поток видит только те ресурсы, на
которые у него есть хендл. Хендлы передаются между процессами по IPC, права при
передаче можно только сужать.

Платформенный код — boot, MMU, прерывания, context switch — изолирован через hardware abstraction layer (HAL); остальное ядро от конкретного железа не зависит.

Имена в коде — таргет `aarch64-unknown-molecular`, `target_os = "molecular"`,
модуль `std::os::molecular` — идут от `molecular`, внутреннего имени проекта.
Система называется RustOS, проект — `molecular`; оба имени временные, подробнее
в [docs/workspace.md](docs/workspace.md#наименование).

## Возможности

- Модель безопасности построена на передаче capability: права на ресурсы
  раздаются точечно — передать другому процессу можно только сузив, а отзыв
  снимает права разом со всеми производными
- Запуск изолированных процессов и потоков, планировщик с элементами реального времени
- Управление физической и виртуальной памятью процессов
- Высокопроизводительная синхронная и асинхронная передача данных между
  процессами. Типизированный интерфейс для построения контрактов
- Драйверы, сервисы и пользовательские программы работают в userspace — состав
  образа и композицию системы задают TOML-манифесты, а собирает их `cargo xtask`
- Композиция описана планом, а не кодом: супервизор поднимает компоненты в
  порядке их зависимостей, раздаёт им capability слотами и поднимает потребителей
  заново вместе с ушедшим провайдером. Путей программ и прикладных контрактов он
  не знает
- Загрузка идёт двумя ступенями: ramdisk несёт ступень 0 — маршрутизатор имён,
  корневую файловую систему и владельца политики загрузки, — а тот разматывает
  остальные компоненты из файлов и подаёт их супервизору транзакцией
- Файловая подсистема в userspace: маршрутизатор имён держит таблицу
  монтирований, каждое монтирование обслуживает свой процесс — read-only дерево
  поверх userland-образа и изменяемое дерево в памяти. Смонтировать — передать
  маршрутизатору capability сессии. Данные идут кадром либо напрямую через
  capability на регион файла
- Драйверы устройств в userspace: IRQ-линия и окно регистров выдаются процессу
  как capability, рабочий пример — драйвер PL031 RTC
- Стандартная библиотека Rust портирована на систему: программа образа пишется
  обычным `fn main`, а системную часть отдаёт модуль `std::os::molecular`
- Работа на реальном железе и в QEMU, автоматические тесты под QEMU

Пока нет: UEFI boot, драйверов периферии (GPIO, I2C, SPI), сетевого стека.
Файловая подсистема работает, но без дисковой файловой системы, клиентской
библиотеки и плоскости потока — подробности в
[docs/filesystem.md](docs/filesystem.md).

## Программы на стандартной библиотеке

Программа образа пишется на обычном Rust: `fn main`, `println!`, типы и
контейнеры из `std`. Строка печати уходит в системный журнал под именем
компонента.

```rust
fn main() {
    println!("hello");
}
```

Системную часть отдаёт модуль `std::os::molecular`: через него программа
получает стартовый набор capability — то, что композиция выдала ей при запуске.
Типизированные обёртки над capability и контракты IPC приходят программе
обычными зависимостями.

Примеры в образе — `user/hello-std` и `user/clock-std` (второй спрашивает время
у драйвера часов). Устройство слоя —
в [docs/userland.md](docs/userland.md#программа-на-стандартной-библиотеке).

## Запуск

Своё AArch64-устройство добавляется YAML-спекой в `devices/spec/` — формат образа,
адрес загрузки, команды прошивки. Toolchain, зависимости и запуск на железе —
[docs/environment.md](docs/environment.md) и [docs/commands.md](docs/commands.md).
