# Устройство репозитория

Репозиторий разделён на домены и workspace по профилям сборки. Зависимости и
состав workspace проверяет `cargo xtask check-layers`
([commands.md](commands.md#проверка-слоёв)).

## Наименование

| Имя | Назначение | Где используется |
|-----|------------|------------------|
| RustOS | система | документация, комментарии, пользовательский вывод |
| `molecular` | проект | идентификаторы в коде и сборке |

Оба имени временные. Система в документации называется RustOS.
Идентификатор проекта используется в имени репозитория, таргете
`aarch64-unknown-molecular`, `target_os = "molecular"`, модуле
`std::os::molecular` и ключе `metadata.molecular`.

## Домены

| Домен | Назначение |
|-------|------------|
| `lib/` | Общие библиотеки ядра и userspace, ABI и IPC-контракты |
| `kernel/` | Механизмы ядра, HAL и встроенные драйверы |
| `user/` | Userspace-компоненты, приложения, примеры и тестовые программы |
| `tools/` | Инструменты хоста |
| `xtask/` | Команды сборки, запуска и проверок |
| `fuzz/` | Fuzz-цели разборщиков внешних форматов |

`lib/` зависит только от своего домена. Домены `kernel/`, `user/`,
`tools/` и `fuzz/` могут зависеть от собственного домена и `lib/`.
Домену `xtask/` доступны все домены, кроме `fuzz/`.

Архитектура крейта определяется записью
[реестра архитектур](#реестр-архитектур). Архитектурный крейт может зависеть
от нейтральных крейтов и крейтов той же архитектуры. Общий интерфейс с
реализациями под `cfg(target_arch)` остаётся архитектурно нейтральным.

## Таргеты сборки

| Таргет | Назначение |
|--------|------------|
| `aarch64-unknown-none` | Ядро и общий код |
| `targets/aarch64-unknown-molecular.json` | Userspace и стандартная библиотека RustOS |

Библиотеки `core` и `std` для системного таргета собираются из исходников
через `-Zbuild-std`. Подготовку исходников и выбор таргета выполняет
`cargo xtask` ([commands.md](commands.md#исходники-стандартной-библиотеки)).

## Профили сборки

Профиль задаёт таргет, доступность `std` и toolchain workspace.
Он объявляется ключом `[workspace.metadata.molecular] profile`.

| Профиль | Манифест workspace | Назначение |
|---------|--------------------|------------|
| `common` | [Cargo.toml](../Cargo.toml) | Общий `no_std`-код: host-тесты и проверки под bare-таргет |
| `host` | [tools/Cargo.toml](../tools/Cargo.toml) | Инструменты хоста на `std` |
| `platform` | [kernel/platform/Cargo.toml](../kernel/platform/Cargo.toml) | Платформенные крейты с `forced-target` |
| `std-runtime` | [lib/std-runtime/Cargo.toml](../lib/std-runtime/Cargo.toml) | Зависимости стандартной библиотеки |
| `userland` | [user/Cargo.toml](../user/Cargo.toml) | Программы с системной `std` |
| `fuzz` | [fuzz/Cargo.toml](../fuzz/Cargo.toml) | Fuzz-цели со своим toolchain |

Отделённые workspace перечислены в `workspace.exclude` корневого манифеста.
Они согласуют с корнем общие свойства пакетов, линты и версии зависимостей.

## Реестр архитектур

[Корневой манифест](../Cargo.toml) объявляет архитектуры и для каждой задаёт
имя, bare-таргет и системный таргет. Команды проверок выбирают таргеты из этого
реестра. Платформенные крейты принадлежат workspace `platform`.

## Состояние процесса

Одна копия рантайма владеет кучей, futex, TLS, журналом и стартовым хендлом
процесса. Freestanding-программа использует `runtime` напрямую, программа
на `std` — через стандартную библиотеку, программа на C или C++ — через
`c-library`.

Крейт объявляет владение состоянием ключом
`metadata.molecular.process-state`. Проверка слоёв запрещает программе на
`std` зависимости, которые создадут вторую копию этого состояния.

ABI и IPC-контракты состояния процесса не содержат и доступны обычными
зависимостями. Крейты, встроенные в `std` через `rustc-dep-of-std`, и
зависимости программы имеют отдельные экземпляры этих типов. Системная граница
`std::os::molecular` передаёт хендлы; типизированные требования программы
предоставляет крейт `components` ([userland.md](userland.md#программа-на-стандартной-библиотеке)).
