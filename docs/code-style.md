# Стиль кода

Документ задаёт оформление исходников: структуру файла, именование,
видимость, комментарии и дисциплину. Правила одинаковы для всех
крейтов workspace; различия между архитектурно-независимым и платформенным
кодом отмечены явно.

Форматирование применяется механически через `cargo fmt --all`, параметры
зафиксированы в `rustfmt.toml`.

## Крейт и no_std

Архитектурно-независимые крейты, тестируемые с `std`, используют
`#![cfg_attr(not(test), no_std)]`. Крейты без host-тестов используют
`#![no_std]`.

Для heap-аллокаций подключается `extern crate alloc`; тестовый `extern crate
std` идёт под `#[cfg(test)]`.

## Структура файла

Корневой `lib.rs` крейта организован в следующем порядке:

1. `//!` doc-комментарий модуля;
2. crate-level атрибуты (`#![no_std]`/`#![cfg_attr...]`, `#![allow...]`);
3. `extern crate` (при необходимости);
4. объявления подмодулей (`mod`/`pub mod`) — по алфавиту;
5. `pub use` реэкспорты публичного API.

```rust
//! capability targets и таблица handle'ов.
#![cfg_attr(not(test), no_std)]

extern crate alloc;

mod api;
mod handle;
mod handle_table;

pub use handle::{Capability, HandleId};
pub use handle_table::HandleTable;
```

Файл с определениями (типы, функции, реализация) организован в порядке:

1. `//!` doc-комментарий модуля (если он несёт контракт сверх имени файла);
2. `use`-импорты (группами: `core`/`alloc` → внешние крейты → `crate::`);
3. константы и type alias'ы;
4. определения `struct`, `enum`, `trait`;
5. `impl`-блоки (в том же порядке, что определения);
6. свободные функции;
7. `#[cfg(test)] mod tests`.

## Именование

Идентификатор называет вещь, а не аббревиатуру её названия. Сокращения
допустимы только в роли устоявшихся обозначений предметной области:
регистры процессора (`pc`, `sp`), адресные пространства (`va`, `pa`) и
подобные термины, чья короткая форма является стандартной, а не произвольной.

Типы, трейты и варианты enum'ов — `UpperCamelCase`. Функции, методы,
локальные переменные, поля — `snake_case`. Константы — `SCREAMING_SNAKE_CASE`.

Тесты именуются по проверяемому сценарию в `snake_case`:
`allocate_switches_to_next_region_when_exhausted`.

## Видимость

Правило минимальной видимости: элемент получает наименьшую область видимости,
при которой он доступен всем своим потребителям. Поле структур публично, только если оно составляет контракт типа. Внутреннее
состояние остаётся приватным.

## Комментарии

Doc-комментарий (`///` или `//!`) на публичном элементе описывает контракт:
что элемент делает и какие предусловия/постусловия он устанавливает. Одна-три
строки. Если контракт очевиден из имени и типов, комментарий не нужен.

Doc-комментарии пишутся только на публичных элементах. Приватным функциям,
типам, полям и константам достаточно имени и сигнатуры.

Маркер комментария роли не играет: проза, прилипшая к объявлению, описывает его
целиком и остаётся doc-комментарием, записан он через `///` или через `//`.
Над непубличным объявлением её нет. Исключение — контракт `unsafe fn`, который
записывается блоком `// SAFETY:`.

Комментарий над тестовой функцией уместен как regression guard: одна-две строки
о том, какой баг тест удерживает.

Комментарий называет назначение, а не наблюдаемое поведение и не порядок шагов:
«серверная сторона порта», а не «переносится серверу целиком, и её уход лишает
порт получателей».

Формулировка утвердительная, в настоящем времени. В комментарий не входят:
определение через отрицание («X, а не Y»), обоснования («поэтому», «потому что»,
«так как»), гипотетические сценарии в сослагательном наклонении («снял бы»,
«разбудил бы») и отсылки к будущей работе. Точка с запятой как разделитель в
русской прозе заменяется точкой, запятой или тире.

Строчный комментарий `//` уместен в двух случаях:
- неочевидный инвариант или ограничение, которое нельзя выразить типом;
- поведение, требующее знания доменной логики вне кода (аппаратный протокол,
  security-инвариант, ABI-деталь).

Место такого комментария — у той строки, которую он ограничивает, внутри тела.

Дисциплина блокировок описывается запретом («отзыв не выполняется под
table-локом»), а не расположением строк («накопитель заведён до взятия лока») —
второе читается из кода.

Комментарий, пересказывающий, что делает код, — признак плохих имён. Его
удаляют и улучшают имена.

Строки комментария переносятся по той же границе `max_width`, что и код
(задана в `rustfmt.toml`). Переносить строку заметно раньше границы нельзя.

Ссылки между кодом и документацией однонаправленны: документы `docs/`
ссылаются на код, комментарий на файл `docs/*.md` не ссылается.

## unsafe

Workspace-линт `unsafe_code = "deny"` действует по умолчанию на все крейты.

Платформенные крейты (`hal-*`, `drivers-*`) снимают запрет целиком:
`#![allow(unsafe_code)]` в корне крейта.

Архитектурно-независимые крейты снимают запрет точечно — только на уровне
файла, у которого нет безопасной альтернативы (`#![allow(unsafe_code)]` в
начале файла).

Перед каждым `unsafe`-блоком обязателен комментарий `// SAFETY:`,
доказывающий корректность операции: какие предусловия выполнены и кем они
гарантированы.

```rust
// SAFETY: caller гарантирует, что новый базовый адрес замаплен и хранит
// валидный объект `T` (контракт `unsafe fn`); `relocated_raw` имеет размер
// и layout `*const T`, поэтому `transmute_copy` корректно собирает fat
// pointer из пары usize.
unsafe {
    let ptr: *const T = core::mem::transmute_copy(&relocated_raw);
    &*ptr
}
```

## Обработка ошибок

Ошибки представлены enum'ом с вариантами без данных (или с минимальными
данными); каждый вариант имеет doc-комментарий. `#[derive(Debug)]` — повсеместно.
`core::fmt::Display` реализуется там, где нужен человекочитаемый вывод.
Ошибочные состояния возвращаются через `Result`.

В коде ядра `unwrap`/`expect`/`panic!` на достижимых путях запрещены: паника
роняет машину целиком. Ошибка возвращается через `Result`, а «невозможное»
состояние делается невыразимым типом (`NonZero`, newtype, замкнутый enum).

Несколько значений через публичный API возвращаются именованной структурой.
Кортеж в публичной сигнатуре не используется.

## Тесты

Тесты размещаются:

- **Интеграционные** (используют крейт как чёрный ящик) — в `tests/`
  рядом с `src/`.
- **Юнит-тесты** (тестируют детали реализации) — в `#[cfg(test)] mod tests`
  внутри того же файла.

Имена тестов описывают проверяемый сценарий в `snake_case`:
`allocate_switches_to_next_region_when_exhausted`.

Уровень выбирается по тому, откуда наблюдаем проверяемый эффект; при равном
покрытии берётся уровень выше по списку:

1. **Host-тест** (`cargo test --workspace`) — эффект выражается через логику
   крейта и воспроизводится на моках, без настоящих MMU и scheduler'а.
2. **Userspace-тест** (`user/testrunner`) — эффект выражается через syscall-ABI.
   Потомок, которому мало одного exit-кода, поднимается фикстурой
   `port-fixture`.
3. **Kernel-тест** (`kernel/*/src/kernel_tests`) — эффект виден только с EL1:
   системные регистры, биты leaf-PTE, trap-vector.

Права страницы наблюдаются на третьем уровне: data abort в EL0 останавливает
машину, а не завершает процесс, поэтому проверить отказ доступа из userspace
нельзя.
