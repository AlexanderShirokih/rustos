# Стиль кода

Документ задаёт оформление исходников: структуру файла, именование, видимость,
комментарии, формулировки и дисциплину.

Форматирование применяется механически через `cargo fmt --all`, параметры
зафиксированы в `rustfmt.toml`. Правила, которые не берут `cargo fmt` и
`cargo clippy`, проверяет `cargo xtask style`
([commands.md](commands.md#проверка-кодстайла)).

## Крейт и no_std

Крейты `lib/` могут использоваться как ядром, так и userspace-приложениями. Ядро
не использует крейт Rust `std`, поэтому реализует необходимые примитивы
самостоятельно. Архитектурно-независимые крейты, тестируемые с `std`, используют
`#![cfg_attr(not(test), no_std)]`. Крейты без host-тестов используют `#![no_std]`.

Для heap-аллокаций подключается `extern crate alloc`; тестовый `extern crate
std` идёт под `#[cfg(test)]`.

Пользовательским программам доступна стандартная библиотека. Платформенный слой
ОС размещён в `std`, и такая программа пишется обычным `fn main`
([userland.md](userland.md#программа-на-стандартной-библиотеке)).

## Структура файла

Корневой `lib.rs` крейта организован в следующем порядке:

1. `//!` doc-комментарий модуля;
2. crate-level атрибуты (`#![no_std]`/`#![cfg_attr...]`, `#![allow...]`);
3. `extern crate` (при необходимости);
4. объявления подмодулей (`mod`/`pub mod`) — по алфавиту;
5. `pub use` реэкспорты публичного API.

Корень содержит только перечисленное. Определения, `impl`-блоки и вызовы макросов
лежат в подмодулях и попадают в корень через `pub use`. Компилятор принимает функции
с атрибутами `#[proc_macro*]` только в корне proc-macro крейта, и они остаются там.

```rust
//! capability targets и таблица handle'ов.
#![cfg_attr(not(test), no_std)]

extern crate alloc;

mod api;
mod handle;
mod handle_table;

pub use handle::{Capability, HandleId};
pub use handle_table::HandleTable;
```

Файл с определениями организован в порядке:

1. `//!` doc-комментарий модуля (если он задаёт контракт сверх имени файла);
2. `use`-импорты (группами: `core`/`alloc` → внешние крейты → `crate::`);
3. константы и type alias'ы;
4. определения `struct`, `enum`, `trait`;
5. `impl`-блоки (в том же порядке, что определения);
6. свободные функции;
7. `#[cfg(test)] mod tests`.

Тело функции разделено пустыми строками на логические блоки. Слипшийся блок кода читается как
одно неразличимое действие, а пустая строка проводит границу между шагами без
комментария.

## Именование

Идентификатор называет вещь, а не аббревиатуру её названия. Сокращения допустимы
только там, где короткая форма стала устоявшимся обозначением предметной области.
Таковы регистры процессора (`pc`, `sp`), адресные пространства (`va`, `pa`) и
подобные им — их короткая форма стандартна, а не выдумана автором.

Типы, трейты и варианты enum'ов — `UpperCamelCase`. Функции, методы, локальные
переменные, поля — `snake_case`. Константы — `SCREAMING_SNAKE_CASE`.

Имя константы называет величину целиком — что за вещь и в чём её мера.
Предельный и размерный суффиксы называют единицу измерения: `BANNER_MAX_BYTES`,
а не `BANNER_MAX`, `REPLY_TIMEOUT`, а не `WAIT`. Doc-комментарий имени не
заменяет.

Общее значение держит единый источник — `memory::PAGE_SIZE` вместо локальной
константы и голого литерала. Слой, не зависящий от такого источника, объявляет
свой.

## Видимость

Элемент получает наименьшую область видимости, при которой он доступен всем
своим потребителям. Поле структуры публично, только если составляет контракт
типа; внутреннее состояние остаётся приватным.

## Комментарии

Текст над публичным объявлением описывает контракт — что элемент делает и
какие предусловия устанавливает, — одной-тремя строками. Контракт, очевидный
из имени и типов, не комментируется. Контракт `unsafe fn` записывается блоком
`// SAFETY:`. Комментарий над тестовой функцией называет баг или инвариант,
который тест удерживает, и не пересказывает тело теста.

Комментарий называет назначение, а не наблюдаемое поведение и не порядок шагов:
«серверная сторона порта», а не «переносится серверу целиком, и её уход лишает
порт получателей».

Комментарий, пересказывающий код, — признак плохих имён. Улучшают имена, а
пересказ удаляют.

Отсылки к будущей работе в комментарий не входят.

## Формулировки

Раздел обязателен для комментариев, doc-комментариев и документов `docs/`.

Формулировка буквальна. Артефакт описывается тем действием, которое он
выполняет. Метафора, олицетворение и украшающий оборот запрещены.

| Запрещено                              | Как писать                          |
|----------------------------------------|-------------------------------------|
| система `смотрит` наружу модулем       | границу образует модуль             |
| типы через границу не `ходят`          | типы через границу не передаются    |
| объект `хочет` быть разбуженным        | объект разбуждается                 |
| имя `ходит` между слотами              | имя переносится между слотами       |

Границу проводит смысл глагола. Глагол с прямым техническим значением
применяется свободно — «крейт держит состояние», «запись лежит в секции»,
«значок уходит». Глагол живого существа, восприятия, намерения или походки
буквального смысла для артефакта не имеет. Закрытый список таких слов отвергает
правило `animistic_verb` проверки `cargo xtask style`. Список неполон, и
остальное держит автор.

Строчный комментарий `//` внутри тела уместен в двух случаях: неочевидный
инвариант, который нельзя выразить типом, и поведение, требующее знания
доменной логики вне кода (аппаратный протокол, security-инвариант, ABI-деталь).
Место такого комментария — у той строки, которую он ограничивает.

Строка комментария заполняется до границы `max_width`: перенос заметно раньше
неё рвёт абзац. Ссылки между кодом и документацией однонаправленны. Документы
`docs/` ссылаются на код, комментарий на файл `docs/*.md` не ссылается.

## Проза

Комментарии `.rs` и документы `docs/*.md` пишутся по одной норме.

Порядок слов — прямой: подлежащее, сказуемое, дополнение. Дополнение и
косвенный падеж не выносятся в начало предложения ради акцента. Прямой
порядок — `У неё нет приёмника` и `Система не поддерживает эту функцию`,
инверсия — `Приёмника у неё нет` и `Поддержки этой функции в системе нет`.

Глагол называет операцию и не одушевляет объект кода метафорой живого
существа или движения. Двоеточие вводит перечисление либо идёт после ярлыка
(`Аргументы:`, `Возврат:`, `SAFETY:`), а обоснование записывается отдельным
предложением с союзом.

Отдельные обороты запрещены поимённо правилами `cargo xtask style`.

## unsafe

Платформенные крейты (`hal-*`, `drivers-*`) снимают workspace-запрет
`unsafe_code` целиком — `#![allow(unsafe_code)]` в корне крейта.
Архитектурно-независимые крейты снимают его точечно, только в файле, у которого
нет безопасной альтернативы.

Комментарий `// SAFETY:` доказывает корректность операции: какие предусловия
выполнены и кем они гарантированы.

```rust
// SAFETY: caller гарантирует, что новый базовый адрес замаплен и хранит
// валидный объект `T` (контракт `unsafe fn`); `relocated_raw` имеет размер
// и layout `*const T`, поэтому `transmute_copy` корректно собирает fat
// pointer из пары usize.
unsafe {
    let ptr: *const T = core::mem::transmute_copy(&relocated_raw);
    &*ptr
}
```

## Обработка ошибок

Ошибки представлены enum'ом с вариантами без данных или с минимальными данными;
каждый вариант имеет doc-комментарий. `#[derive(Debug)]` — повсеместно,
`core::fmt::Display` — там, где нужен человекочитаемый вывод.

В коде ядра паника на достижимом пути запрещена. Ошибка возвращается через
`Result`, а «невозможное» состояние делается невыразимым типом (`NonZero`,
newtype, замкнутый enum).

Запреты проверяются линтами, объявленными в `[workspace.lints.clippy]` корневого
манифеста и его userspace-копии. Рабочему коду запрещены индексация среза без
проверки границ, `unwrap`, `expect`, `panic!`, `todo!`, `unimplemented!` и
возврат ошибки паникой из функции, отдающей `Result`; приведение, способное
усечь значение, требует `try_from` либо обоснования на месте.

Крейт, которому линт неприменим, снимает его в своём корне. Так освобождены три
класса:

- платформенные крейты — там, где запрет вытекает из природы кода;
- хостовые инструменты, которым доступна `std`;
- программы-фикстуры, у которых паника и есть способ сообщить о провале.

Рабочему коду вне этих трёх классов остаётся точечное снятие у самого места.

Снятие в голове модуля допустимо там, где основание одно на весь файл. Так снят
запрет индексации в модулях, целиком собранных из `const fn`, где `get` по срезу
недоступен, и запрет дробления `unsafe`-блока в модулях, где операции блока
доказаны одним комментарием `SAFETY`. Модуль со смешанным содержимым такого
снятия не получает.
