# Стиль кода

Документ задаёт оформление исходников: структуру файла, именование, видимость,
комментарии и дисциплину. Правила одинаковы для всех крейтов workspace;
различия между архитектурно-независимым и платформенным кодом отмечены явно.

Форматирование применяется механически через `cargo fmt --all`, параметры
зафиксированы в `rustfmt.toml`. Правила, которые не берут `cargo fmt` и
`cargo clippy`, проверяет `cargo xtask style`
([commands.md](commands.md#проверка-кодстайла)).

## Крейт и no_std

Крейты `lib/` делят ядро и userspace, а под ядром стандартной библиотеки нет.
Архитектурно-независимые крейты, тестируемые с `std`, используют
`#![cfg_attr(not(test), no_std)]`. Крейты без host-тестов используют `#![no_std]`.

Для heap-аллокаций подключается `extern crate alloc`; тестовый `extern crate
std` идёт под `#[cfg(test)]`.

Программе образа стандартная библиотека доступна: платформенный слой RustOS
живёт в `std`, и такая программа пишется обычным `fn main`
([userland.md](userland.md#программа-на-стандартной-библиотеке)).

## Структура файла

Корневой `lib.rs` крейта организован в следующем порядке:

1. `//!` doc-комментарий модуля;
2. crate-level атрибуты (`#![no_std]`/`#![cfg_attr...]`, `#![allow...]`);
3. `extern crate` (при необходимости);
4. объявления подмодулей (`mod`/`pub mod`) — по алфавиту;
5. `pub use` реэкспорты публичного API.

```rust
//! capability targets и таблица handle'ов.
#![cfg_attr(not(test), no_std)]

extern crate alloc;

mod api;
mod handle;
mod handle_table;

pub use handle::{Capability, HandleId};
pub use handle_table::HandleTable;
```

Файл с определениями организован в порядке:

1. `//!` doc-комментарий модуля (если он несёт контракт сверх имени файла);
2. `use`-импорты (группами: `core`/`alloc` → внешние крейты → `crate::`);
3. константы и type alias'ы;
4. определения `struct`, `enum`, `trait`;
5. `impl`-блоки (в том же порядке, что определения);
6. свободные функции;
7. `#[cfg(test)] mod tests`.

## Именование

Идентификатор называет вещь, а не аббревиатуру её названия. Сокращения
допустимы только в роли устоявшихся обозначений предметной области: регистры
процессора (`pc`, `sp`), адресные пространства (`va`, `pa`) и подобные термины,
чья короткая форма является стандартной, а не произвольной.

Типы, трейты и варианты enum'ов — `UpperCamelCase`. Функции, методы, локальные
переменные, поля — `snake_case`. Константы — `SCREAMING_SNAKE_CASE`.

## Видимость

Элемент получает наименьшую область видимости, при которой он доступен всем
своим потребителям. Поле структуры публично, только если составляет контракт
типа; внутреннее состояние остаётся приватным.

## Комментарии

Проза над объявлением описывает его целиком и остаётся doc-комментарием,
записана она через `///` или через `//`. Место ей только над публичным
элементом: там она описывает контракт — что элемент делает и какие
предусловия устанавливает, — одной-тремя строками. Контракт, очевидный из имени
и типов, не комментируется; приватным функциям, типам, полям и константам
достаточно имени и сигнатуры. Исключения два: контракт `unsafe fn`, который
записывается блоком `// SAFETY:`, и regression guard над тестовой функцией —
одна-две строки о том, какой баг тест удерживает.

Комментарий называет назначение, а не наблюдаемое поведение и не порядок шагов:
«серверная сторона порта», а не «переносится серверу целиком, и её уход лишает
порт получателей». Пересказ того, что делает код, — признак плохих имён: его
удаляют и улучшают имена.

Формулировка утвердительная, в настоящем времени. В комментарий не входят:
определение через отрицание («X, а не Y»), обоснования («поэтому», «потому что»,
«так как»), гипотетические сценарии в сослагательном наклонении («снял бы»,
«разбудил бы») и отсылки к будущей работе. Точка с запятой как разделитель в
русской прозе заменяется точкой, запятой или тире.

Строчный комментарий `//` внутри тела уместен в двух случаях: неочевидный
инвариант, который нельзя выразить типом, и поведение, требующее знания
доменной логики вне кода (аппаратный протокол, security-инвариант, ABI-деталь).
Место такого комментария — у той строки, которую он ограничивает.

Строки комментария переносятся по той же границе `max_width`, что и код;
переносить заметно раньше границы нельзя. Ссылки между кодом и документацией
однонаправленны: документы `docs/` ссылаются на код, комментарий на файл
`docs/*.md` не ссылается.

## unsafe

Workspace-линт `unsafe_code = "deny"` действует по умолчанию на все крейты.
Платформенные крейты (`hal-*`, `drivers-*`) снимают запрет целиком —
`#![allow(unsafe_code)]` в корне крейта. Архитектурно-независимые крейты снимают
его точечно, только в файле, у которого нет безопасной альтернативы.

Перед каждым `unsafe`-блоком обязателен комментарий `// SAFETY:`, доказывающий
корректность операции: какие предусловия выполнены и кем они гарантированы.

```rust
// SAFETY: caller гарантирует, что новый базовый адрес замаплен и хранит
// валидный объект `T` (контракт `unsafe fn`); `relocated_raw` имеет размер
// и layout `*const T`, поэтому `transmute_copy` корректно собирает fat
// pointer из пары usize.
unsafe {
    let ptr: *const T = core::mem::transmute_copy(&relocated_raw);
    &*ptr
}
```

## Обработка ошибок

Ошибки представлены enum'ом с вариантами без данных или с минимальными данными;
каждый вариант имеет doc-комментарий. `#[derive(Debug)]` — повсеместно,
`core::fmt::Display` — там, где нужен человекочитаемый вывод.

В коде ядра `unwrap`/`expect`/`panic!` на достижимых путях запрещены: паника
роняет машину целиком. Ошибка возвращается через `Result`, а «невозможное»
состояние делается невыразимым типом (`NonZero`, newtype, замкнутый enum).

Несколько значений через публичный API возвращаются именованной структурой;
кортеж в публичной сигнатуре не используется.
