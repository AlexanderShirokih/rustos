# Тесты

Документ отвечает на два вопроса: где лежит новый тест и на каком уровне он
пишется. Команды прогона — в [commands.md](commands.md#тесты).

## Размещение

Интеграционные тесты, которым крейт — чёрный ящик, лежат в `tests/` рядом с
`src/`; юнит-тесты деталей реализации — в `#[cfg(test)] mod tests` того же
файла. Имя теста называет проверяемый сценарий:
`allocate_switches_to_next_region_when_exhausted`.

## Уровень

Уровень выбирается по тому, откуда наблюдаем проверяемый эффект; при равном
покрытии берётся уровень выше по списку:

1. **Host-тест** (`cargo test --workspace`) — эффект выражается через логику
   крейта и воспроизводится на моках, без настоящих MMU и scheduler'а.
2. **Userspace-тест** (`user/testrunner`) — эффект выражается через syscall-ABI.
3. **Kernel-тест** (`kernel/*/src/kernel_tests`) — эффект виден только с EL1:
   системные регистры, биты leaf-PTE, trap-vector.

Права страницы наблюдаются на третьем уровне: data abort в EL0 останавливает
машину, а не завершает процесс, поэтому проверить отказ доступа из userspace
нельзя.

## Прогоны под QEMU

`cargo xtask qemu-test` выполняет два прохода одним образом
(`user/testrunner/image.toml`):

| Проход     | Feature ядра   | Что тестирует     |
|------------|----------------|-------------------|
| `kernel`   | `kernel-tests` | тесты внутри ядра |
| `userland` | —              | тесты в userspace |

Под `kernel-tests` init-таском становится внутриядерный worker, и userland в
этом проходе не исполняется вовсе. Ядро пересобирается между проходами из-за
различия feature-флагов.

`testrunner` — корневой процесс userland-прохода: он ставит writer, шлющий лог
через `Bootstrap` в ядро, и exit-делегат, а поднимаемым процессам выдаёт
лог-сессии своего relay.

```rust
#[kernel_test]
fn userland_smoke() {
    let sum: u64 = (1..=10).sum();
    kernel_tests::kassert_eq!(sum, 55);
}
```

## Стресс-прогон

Единица прогона — эпоха: объявленное планом число шагов над пулом живых
объектов, пустым на её границах. Seed эпохи выводится из seed прогона и её
номера, поэтому падение повторяется прогоном одной эпохи. На границе прогон
гасит нагрузку и сверяет остаток бюджета страниц с базовой величиной;
расхождение роняет прогон. Утечка объекта, пережившего границу, сверке не
видна.

## Ночной набор

Дорогие для pull request проверки идут по расписанию в ночном окне: длительный
стресс-прогон, прогон под альтернативным контроллером прерываний и fuzzing по
целям. Диапазон seed стресса делится поровну между шардами при общей сборке.
Состав и параметры объявляет `.github/workflows/ci-extended-verification.yml`;
набор проверок pull request от них независим.

## Фикстуры

Потомок, которому мало одного exit-кода, поднимается фикстурой — отдельной
программой образа `testrunner`; их реестр — bin-таргеты `user/testrunner`.

Поверхность стандартной библиотеки проверяет `user/std-selftest`: `testrunner`
поднимает его управляемым компонентом, код выхода программы — итог её `assert!`,
а подробности провала уходят в журнал сообщением паники.
