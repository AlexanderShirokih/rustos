# Тесты

Команды прогона описаны в [commands.md](commands.md#тесты).

## Размещение

Интеграционные тесты публичного поведения лежат в `tests/` рядом с `src/`.
Юнит-тесты деталей реализации — в `#[cfg(test)] mod tests` того же файла.
Имя теста обозначает проверяемый сценарий.

Ошибки типизации проверяются через `trybuild`. Фикстуры лежат в
`tests/compile_fail/`, ожидаемая диагностика — в одноимённых `.stderr`.

Крейт с host-тестами объявляет `#![cfg_attr(not(test), no_std)]`.
Тестовый `extern crate std` ставится под `#[cfg(test)]`.

## Уровень

Уровень выбирается по наблюдаемому эффекту. При одинаковом покрытии
предпочитается более ранний уровень:

| Уровень | Что проверяет | Размещение |
|---------|---------------|------------|
| Host | Логику крейта с моделями зависимостей | Тесты крейта |
| Userspace | Поведение через syscall ABI | `user/testing/testrunner` |
| Kernel | Эффекты EL1: регистры, PTE, исключения | `kernel/*/src/kernel_tests` |

Прохождение host-теста не подтверждает работу MMU или планировщика на устройстве.

## Прогоны под QEMU

`cargo xtask qemu-test` выполняет kernel- и userland-проходы.
Kernel-проход собирается с `kernel-tests` и выполняет тесты внутри ядра.
Userland-проход запускает
[user/testing/testrunner](../user/testing/testrunner/Cargo.toml).

Вердикт учитывает завершение машины и TEST-маркеры.
Тест, неприменимый к текущей конфигурации, использует `test_harness::skip!`.
Маркер `[TEST-SKIP]` обозначает пропуск и учитывается отдельно от прохождения.

## Стресс-прогон

Операции над пулом объектов разбиваются на эпохи.
На границе эпохи нагрузка завершается и остаток бюджета страниц сравнивается
с исходной величиной. Расхождение завершает прогон с отказом.
Объект, переживший границу эпохи, этой проверкой не покрывается.

Seed задаёт последовательность операций. Порядок исполнения потоков
определяется планировщиком.

## Ночной набор

Дополнительные прогоны и их параметры определены в
[ci-extended-verification.yml](../.github/workflows/ci-extended-verification.yml).
Они включают длительный стресс, альтернативный контроллер прерываний и fuzzing.
Успех набора pull request не подтверждает прохождение ночного набора.

## Фикстуры

Фикстура — программа-потомок testrunner. Она нужна для второй стороны IPC,
отдельного адресного пространства или бюджета, завершения процесса и
сценариев композиции. Завершение самого testrunner заканчивает весь прогон.

Фикстура объявляется bin-таргетом в
[user/testing/testrunner/Cargo.toml](../user/testing/testrunner/Cargo.toml)
и программой в его [image.toml](../user/testing/testrunner/image.toml).
Её исполняемые данные находятся по пути `<path>/exec`.

Запуск выбирается по сценарию: загрузчик для отдельного процесса,
тестовый родитель для требований и бюджета, композиция rootkeeper для
связей и перезапусков.

Точку входа фикстуры объявляет атрибут крейта
[program-entry](../lib/program-entry/src/lib.rs). Фикстура, которая
работает со стартовой сессией как компонент, объявляет `program_entry::component`
и получает требования своего манифеста. Остальные фикстуры объявляют
`program_entry::process` и получают владельца своего стартового handle.

Код выхода задаёт значение функции. `Result` завершает фикстуру кодом
`runtime::SUCCESS_EXIT_CODE` либо `runtime::FAILED_EXIT_CODE`,
`runtime::ExitCode` — кодом, который сверяет тест. Паника завершает фикстуру
кодом `runtime::FAILED_EXIT_CODE`.
Данные сверх кода выхода передаются общим протоколом, разделяемой памятью
или журналом. Определение протокола используется обеими сторонами.

Стандартную библиотеку проверяет
[std-selftest](../user/testing/std-selftest/src/main.rs), библиотеку C —
[c-selftest](../user/testing/c-selftest/src/selftest.c), стандартную библиотеку
C++ — [cxx-selftest](../user/testing/cxx-selftest/src/selftest.cpp) и
[cxx-exit](../user/testing/cxx-exit/src/exit.cpp).
