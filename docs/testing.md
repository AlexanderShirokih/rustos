# Тесты

Документ отвечает на два вопроса. Где лежит новый тест и на каком уровне он
пишется? Команды прогона — в [commands.md](commands.md#тесты).

## Размещение

Интеграционные тесты, которым крейт — чёрный ящик, лежат в `tests/` рядом с
`src/`; юнит-тесты деталей реализации — в `#[cfg(test)] mod tests` того же
файла. Имя теста называет проверяемый сценарий:
`allocate_switches_to_next_region_when_exhausted`.

## Уровень

Уровень выбирается по тому, откуда наблюдаем проверяемый эффект; при равном
покрытии берётся уровень выше по списку:

1. **Host-тест** (`cargo test --workspace`) — эффект выражается через логику
   крейта и воспроизводится на моках, без настоящих MMU и scheduler'а.
2. **Userspace-тест** (`user/testing/testrunner`) — эффект выражается через syscall-ABI.
3. **Kernel-тест** (`kernel/*/src/kernel_tests`) — эффект виден только с EL1:
   системные регистры, биты leaf-PTE, trap-vector.

## Прогоны под QEMU

`cargo xtask qemu-test` выполняет два прохода одним образом
(`user/testing/testrunner/image.toml`):

| Проход     | Feature ядра   | Что тестирует     |
|------------|----------------|-------------------|
| `kernel`   | `kernel-tests` | тесты внутри ядра |
| `userland` | —              | тесты в userspace |

Под `kernel-tests` начальным процессом становится внутриядерный worker, и userland в
этом проходе не исполняется вовсе. Ядро пересобирается между проходами из-за
различия feature-флагов.

Вердикт userland-прохода приходит кодом выхода bootstrap-процесса, которым и
выключается машина. Лог UART при этом никто не разбирает. Одного кода возврата
всё же мало, и `xtask` дополнительно сверяет TEST-маркеры прогона.

`testrunner` — корневой процесс userland-прохода. Он ставит writer, шлющий лог
через `Bootstrap` в ядро, и exit-делегат, а поднимаемым процессам выдаёт
лог-сессии своего relay.

```rust
#[kernel_test]
fn userland_smoke() {
    let sum: u64 = (1..=10).sum();
    kernel_tests::kassert_eq!(sum, 55);
}
```

## Стресс-прогон

Единица прогона — эпоха. Это объявленное планом число шагов над пулом живых
объектов, и на границах эпохи пул пуст.

Seed эпохи выводится из seed прогона и её номера, так что падение повторяется
прогоном одной эпохи. На границе прогон гасит нагрузку и сверяет остаток бюджета
страниц с базовой величиной; расхождение завершает прогон отказом. Объект,
переживший границу, этой сверке не виден.

## Ночной набор

Проверки, слишком дорогие для pull request, идут по расписанию в ночном окне.
Это длительный стресс-прогон, прогон под альтернативным контроллером прерываний и
fuzzing по целям. Диапазон seed стресса делится поровну между шардами при общей
сборке.
Состав и параметры объявляет `.github/workflows/ci-extended-verification.yml`;
набор проверок pull request от них независим.

## Фикстуры

Фикстура — отдельная программа образа `testrunner`, которую тест запускает
потомком. Фикстура нужна сценарию со второй стороной канала в своём адресном
пространстве, с отдельным бюджетом потомка, с записью композиции или с завершением
процесса (выход, паника, отказ доступа к памяти). Тест исполняется в процессе
`testrunner`, и завершение этого процесса заканчивает прогон. Поэтому завершение
процесса проверяется на потомке.

Программа фикстуры — bin-таргет `user/testing/testrunner/Cargo.toml` с записью
`[[programs]]` в `image.toml` того же каталога. Поле `path` записи задаёт каталог
программы в образе, и тест находит программу по пути `<path>/program`.

Способ запуска выбирается по роли фикстуры в сценарии:

| Запуск                                                         | Фикстура получает                             | Тест наблюдает                                  |
|----------------------------------------------------------------|-----------------------------------------------|-------------------------------------------------|
| `userland_loader::load_entry`, обёртка `fixture::spawn_entry`  | один начальный handle                         | код выхода процесса                             |
| тестовый родитель `parent::Parent`                             | порт родителя, ответы на требования, бюджет   | уход потомка и его исход                        |
| `composition::Composition` с планом rootkeeper                 | запись плана                                  | требования, журнал, перезапуски и бюджет записи |

Код выхода фикстура передаёт при любом способе запуска. Данные сверх кода
передаются по протоколу: вызовами через начальный порт, записью в регион памяти,
который тест передал начальным handle, или строкой журнала. Протокол объявляет
модуль `*_protocol.rs`, подключённый и к фикстуре, и к `testrunner`. В модуле
лежат формат сообщений, раскладка разделяемой памяти и коды выхода фикстуры, и
обе стороны собираются из одного определения.

Поверхность стандартной библиотеки проверяет программа `user/testing/std-selftest`.
Это программа на `std`, и её проверки записаны через `assert!`. Тест
`std_selftest.rs` запускает её потомком тестового родителя с отдельной лог-сессией и
ждёт выхода с кодом ноль. Проваленная проверка завершает программу паникой. Сообщение
паники уходит в журнал через `stderr`, а тест получает ненулевой код выхода.
Примитивы платформенного слоя под `std` проверяют тесты `testrunner` напрямую.
