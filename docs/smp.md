# Поддержка SMP

Ядро исполняется на одном CPU: остальные остановлены в `secondary_main`. SMP
снимает это ограничение — образ один, привилегии CPU одинаковы, каждый
обслуживает syscall своего потока и своё прерывание. Асимметрия остаётся только
в загрузке: boot CPU строит глобальное состояние, которое остальные застают
готовым.

Документ фиксирует модель, порядок подъёма CPU, дисциплину, при которой
механизмы ядра остаются корректны при параллельном входе, и порядок внедрения.
Форматы сообщений и syscall ABI при этом не меняются
([syscalls.md](syscalls.md)).

## Основание

Часть подсистем спроектирована с расчётом на несколько CPU и переносится без
изменений.

| Механизм                               | Состояние                                                        |
|----------------------------------------|------------------------------------------------------------------|
| Per-CPU состояние планировщика (`Cpu`) | ready-queue, `current`, idle; таблица `cpus` — в scheduler inner  |
| CPU-local указатель                    | `TPIDR_EL1` через `install_cpu_local`/`cpu_local_ptr`             |
| Привязка потока                        | поле `cpu_affinity` у `Thread`, учитывается при постановке        |
| Взаимное исключение                    | `MutexCell` = `spin::Mutex` + маскирование IRQ на время секции    |
| ASID                                   | per-CPU активные теги, rollover резервирует их, flush по домену   |
| Инвалидация TLB                        | `is`-варианты `tlbi` — broadcast по inner-shareable домену        |
| Таймер                                 | `CNTV_*` — регистры принадлежат CPU, дедлайн программирует он сам |
| Таблицы страниц                        | `MutexCell<PageMapper>` для kernel-AS и user-AS                   |
| GICv3                                  | init поднимает redistributor и CPU interface, `GICD_IROUTER`      |
| Куча ядра                              | heap-фаза под локом с маскированием прерываний (этап 0)           |
| Аллокатор фреймов                      | стратегия лока меняется на границе MMU, тип — на переходе (этап 0)|
| Идентификация CPU                      | таблица `/cpus` в `hal-common`, логический `CpuId` (этап 1)       |
| Per-CPU блок                           | `CpuLocal` в `TPIDR_EL1`: идентификатор и состояние планировщика  |

Аппаратный broadcast `tlbi ...is` — причина, по которой в плане нет
IPI-shootdown: согласованность TLB между CPU обеспечивает железо, ядру
достаточно барьеров, которые уже стоят в маппере.

## Препятствия

Остальное написано в расчёте на единственный CPU. Список закрытый: он
перечисляет всё, что обязано измениться до подъёма второго CPU.

| Место                                           | Что ломается                                                                   |
|-------------------------------------------------|--------------------------------------------------------------------------------|
| `hal-aarch64/src/boot/boot_secondary.rs`        | заглушка: нет протокола старта, нет стека, нет входа в планировщик              |
| `.stack` в `linker/aarch64-linux.ld`            | единственный 64К-стек принадлежит boot CPU                                     |
| `drivers-aarch64/src/generic/gicv{2,3}`         | per-CPU часть контроллера инициализируется один раз; SGI не поддержаны          |
| `drivers-aarch64/src/generic/arm_generic_timer` | PPI таймера включается только на том CPU, что выполнил `bind`                   |
| `scheduler/src/scheduler.rs`                    | контекст сохраняется вне лока, а поток уже помечен `Ready`                      |
| `scheduler/src/service.rs`                      | `unblock` ставит поток в чужую очередь, не извещая её CPU                       |
| `kernelspace/src/power.rs`                      | `system_off` гасит машину, пока остальные CPU исполняют код                     |

Гонки в куче и аллокаторе фреймов были в этом списке первыми и закрыты
этапом 0: они не деградация производительности, а неопределённое поведение —
первое же параллельное `Box::new` разрушило бы список свободных блоков.
Нумерация CPU по `MPIDR[7:0]` закрыта этапом 1.

## Модель

### Симметрия

Все CPU исполняют один образ, работают на EL1 и равноправны: syscall
обслуживает тот CPU, на котором поток его выполнил, прерывание — тот, которому
его доставил контроллер. Выделенного под ядро CPU нет.

Boot CPU отличается только историей: он проходит pre-MMU фазу, строит таблицы
страниц, кучу, драйверы и планировщик. К моменту старта вторичных CPU это
состояние готово и дальше меняется на общих правилах.

### Идентификация

Логический `CpuId` — индекс `0..N-1`, назначаемый таблицей соответствия
`MPIDR affinity -> CpuId`. Таблица строится boot CPU из узлов `cpu@N` в FDT:
`reg` узла содержит affinity-значение (`Aff3:Aff2:Aff1:Aff0`), под которым CPU
известен и FDT, и PSCI, и контроллеру прерываний. Boot CPU получает индекс `0`
независимо от своего MPIDR.

Прямой вывод индекса из `MPIDR[7:0]` (Aff0) отбрасывается: на многокластерном
SoC — а среди целевых устройств проекта такие есть — Aff0 нумерует CPU внутри
кластера, и CPU разных кластеров получают одинаковый индекс. Один индекс на два
CPU означает общий слот `cpus[i]`, общий idle-поток и общий активный ASID.

После установки per-CPU блока `current_id` читает индекс из блока по
`TPIDR_EL1`; обращение к таблице остаётся только на пути старта, пока блок ещё
не установлен.

Верхнюю границу числа CPU задаёт сам `CpuId`: `MAX_CPUS` (16) объявлен рядом с
ним в `scheduler`, а конструктор идентификатора отказывает за этой границей.
Владелец один, и все, кто заводит per-CPU таблицы — топология, per-CPU блоки,
слоты активных ASID, таблица `cpus` планировщика, — ограничены им же по
построению, а не каждый своей константой.

### Per-CPU состояние

CPU принадлежат: `Cpu` планировщика (ready-queue, `current`, idle-поток),
загрузочный стек, аппаратный CPU-интерфейс контроллера прерываний и логический
`CpuId`.

Точка входа к ним — `CpuLocal`, блок платформенного слоя, чей адрес лежит в
`TPIDR_EL1`. Он хранит логический идентификатор и указатель на `Cpu`
планировщика: `install_cpu_local` кладёт туда состояние планировщика, а не
подменяет сам блок. Так идентификатор доступен и до bootstrap планировщика —
он нужен раньше, на пути старта CPU.

Правило доступа: per-CPU состояние читает и меняет либо владеющий CPU, либо
любой CPU под scheduler-локом. `TPIDR_EL1` — единственный способ узнать «своё»
состояние; fallback `current_cpu()` на поиск по `current_id()` существует ради
bootstrap-фазы и host-тестов и на подъём вторичных CPU не распространяется: CPU,
дошедший до планировщика, обязан иметь установленный блок.

Два свойства блока откладываются до этапа 2, потому что раньше не наблюдаемы.

`ArchCpu::install_cpu_local` не имеет канала отказа: он возвращает `()`, а
платформенная реализация при отсутствующем блоке молча выходит, после чего
`cpu_local_ptr` отдаёт `null`. Сегодня недостижимо — блок ставит boot-путь до
bootstrap планировщика, — но с подъёмом вторичных CPU становится достижимым для
каждого из них. Отказ добавляется вместе с ними: сигнатура трейта, его
default-реализация и моки меняются заодно, а таксономия ошибки выбирается по
тому, чем этот отказ является на самом деле (не `SpawnError`: спавн тут ни при
чём).

`CpuLocal` занимает 16 байт, и четыре блока делят строку кэша. Пока поля
read-mostly, false sharing не наблюдается; выравнивание на строку вводится тогда
же, когда в блок попадёт пишущееся состояние.

## Подъём вторичных CPU

### Протокол старта

Метод старта берётся из FDT, а не зашивается: узел `psci` с `method`
(`hvc`/`smc`) даёт вызов `CPU_ON`, `enable-method = "spin-table"` в узле
`cpu@N` — адрес в `cpu-release-addr`. Поддерживаются оба: среди целевых
устройств проекта встречаются оба варианта, а выбор стоит ровно одну ветку на
пути, который исполняется по одному разу на CPU.

`CPU_ON` принимает affinity целевого CPU, физический адрес точки входа и
`context_id`. В `context_id` передаётся логический `CpuId` — CPU узнаёт свой
индекс, не обращаясь к памяти. Spin-table требует записи точки входа по
`cpu-release-addr`, очистки этой строки кэша до точки когерентности и `sev`.

### Передача параметров

Стартующий CPU входит с выключенными MMU и кэшами: его обращения к памяти
некэшируемы и не видят строк, лежащих в кэше boot CPU. Поэтому handoff —
статический массив на `MAX_CPUS` элементов в `.bss`, адресуемый по индексу из
`context_id`, который boot CPU заполняет и очищает до точки когерентности перед
вызовом `CPU_ON`.

В handoff входит минимум, нужный до включения MMU: вершина выделенного стека,
физические адреса корней трансляции (higher и identity) и логический индекс.
Всё остальное CPU читает уже после включения MMU, обычными обращениями.

Вершина стека выравнивается на 16 байт: этого требует AAPCS64, и нарушение не
даёт диагностики — оно проявляется смещением всего, что лежит на стеке.

Identity-корень сегодня теряется: `BootHandoff` доносит до `primary_main` только
`higher_root_pa`, а `Mmu::disable_lower_half` обнуляет `TTBR0_EL1` boot CPU.
Сами таблицы при этом живы и их фреймы заняты — но адрес корня нужно дотянуть
через `BootHandoff` и сохранить: без identity-отображения стартующему CPU не с
чего исполнять код между входом и прыжком в higher half.

### Последовательность

CPU проходит фиксированную цепочку; каждый шаг опирается только на предыдущие.

1. Точка входа (naked): при старте на EL2 — спуск на EL1 тем же кодом, что у
   boot-протокола; `SP` — вершина стека из handoff (физический адрес); включение
   FP/SIMD.
2. `Mmu::enable` с корнями из handoff. Повторный `asid::init` идемпотентен.
3. Прыжок в higher half, `SP` и `PC` — виртуальные.
4. `VBAR_EL1` — общая таблица векторов.
5. Per-CPU часть контроллера прерываний и включение PPI таймера.
6. `bootstrap_secondary_cpu`: idle-поток, `Cpu`, `TPIDR_EL1`.
7. Публикация готовности для boot CPU.
8. `Scheduler::start` — первый switch. Дальше CPU живёт в планировщике.

Шаги 1–3 исполняются до того, как доступен `klog`: диагностика отказа на этом
участке невозможна, поэтому отказ выражается не сообщением, а неполучением
готовности на шаге 7.

### Место в загрузке

Подъём выполняется в `kmain` между `bootstrap_scheduler` и `init_task`. Раньше
нельзя: вторичному CPU нужны куча, контроллер прерываний, таймер и таблица
потоков. Позже — значит из потока, конкурируя с уже работающим планировщиком за
инициализацию.

Отказ CPU не фатален. Boot CPU ждёт готовности с тайм-аутом; не поднявшийся CPU
остаётся без слота в `cpus`, потоки на него не назначаются, загрузка
продолжается на поднявшихся. Число CPU нигде не считается известным заранее:
оно — результат подъёма, а не свойство конфигурации.

## Планировщик

### Общий лок

`SchedulerInner` остаётся под одним `MutexCell`: таблицы потоков и процессов,
очередь сна и per-CPU очереди защищены им же. Решение сознательное — критические
секции коротки, а hot-path (рандеву port, park/unblock, tick) и сейчас берёт
этот лок целиком, так что SMP не добавляет к нему новых захватов, только
конкурентов.

Дробление (отдельный лок на ready-queue каждого CPU, отдельный — на таблицу
потоков) не требует смены модели и остаётся открытым: оно оправдано, когда
профиль покажет contention, а не заранее.

### Владение контекстом

Регистровый контекст потока принадлежит тому CPU, который его исполнял, пока тот
не завершил `A::switch`. Переключение выполняется вне лока намеренно — лок,
удерживаемый на время switch, останавливает все остальные CPU, — и именно
поэтому между «поток помечен `Ready`» и «контекст сохранён» существует окно.

Из этого следуют два запрета:

- поток не становится runnable для другого CPU, пока его контекст не сохранён;
- освобождать `Thread` может только CPU, для которого этот поток не является ни
  `prev`, ни `next` текущего переключения.

В первой фазе оба соблюдаются привязкой: поток исполняется только на своём CPU,
а `reap_pending_threads` уже исключает `prev` и `next`. Миграция снимает это
основание и требует явного флага «поток на CPU»: снявший поток CPU сбрасывает
флаг после `switch`, забирающий — ждёт сброса. Пока флага нет, миграции нет.

### Пробуждение на другом CPU

`unblock_thread` ставит поток в очередь его affinity-CPU. Если это не текущий
CPU, тому отправляется reschedule-IPI: иначе поток ждёт чужого тика, а на CPU,
ушедшем в idle без запрограммированного дедлайна, — бессрочно.

IPI отправляется после выхода из-под scheduler-лока — тем же механизмом
отложенных действий, что уже применён к пробуждениям и разрушению capability
(`DeferredSignals`, `DeferredHandles`). Отправка из-под лока корректна, но
заставляет принимающий CPU спиниться в обработчике на локе, который держит
отправитель.

Гонка «IPI пришёл раньше, чем CPU дошёл до `wfi`» пробуждение не теряет:
прерывание, замаскированное в `PSTATE.I`, остаётся событием пробуждения для
`WFI`.

### Сон и тики

Очередь сна остаётся общей, пробуждение адресуется affinity-CPU разбуженного
потока. Каждый CPU программирует свой `CNTV` на минимум из конца собственного
кванта и ближайшего общего дедлайна.

Цена — лишний тик на CPU, чей дедлайн наступил не для него. Альтернатива
(очередь сна на каждом CPU) убирает этот тик, но добавляет IPI на каждую вставку
с чужой привязкой и вторую структуру с собственными инвариантами. Для кванта
в 10 мс обмен неравноценен.

### Выбор CPU

Назначение привязки — политика, и она отделена от механизма постановки в
очередь. Сейчас поток наследует CPU создателя; при N CPU это оставит всю работу
на том, кто её породил. Минимальная политика первой фазы: при создании потока
выбирается CPU с наименьшей длиной ready-queue.

Балансировка после создания (перенос, work stealing) в объём не входит: она
упирается в тот же флаг владения контекстом и рассматривается отдельно.

## Дисциплина блокировок

Правила ниже — условие корректности, а не рекомендация. На одном CPU их
нарушение приводило максимум к самоблокировке одного CPU; на SMP — к остановке
машины.

1. **Состояние, доступное более чем одному CPU, защищено `MutexCell`.**
   `NoLockCell` остаётся допустим только там, где принадлежность одному CPU
   доказуема из структуры кода. «Ядро однопоточное» перестаёт быть
   доказательством.
2. **До включения MMU спинлок не берётся.** Он построен на exclusive-инструкциях,
   а те применимы только к нормальной кэшируемой памяти: без трансляции
   обращения идут как к Device-памяти, где поведение `ldxr`/`stxr` не определено.
   Состояние pre-MMU фазы объявляется `NoLockCell`. Состояние, живущее по обе
   стороны включения MMU, меняет стратегию на переходе: владелец потребляет
   экземпляр с `NoLockCell` и собирает из его содержимого экземпляр с
   `MutexCell` (`PhysicalFrameAllocator::into_locked`). Рантайм-флага фазы нет:
   pre-MMU экземпляр после перехода недостижим по типу.
3. **Иерархия локов.** Scheduler-лок — внешний: под ним допустимо взять
   handle-таблицу процесса (так работает спавн). Обратный порядок запрещён:
   путь, держащий лок объекта capability, не вызывает планировщик, а
   откладывает вызов. Дисциплина уже сложилась — port снимает список
   пробуждений под своим локом и будит вне его, — и на SMP становится
   обязательной: обратный порядок даёт настоящий AB-BA между CPU.
4. **Под локом не переключают контекст.** `ScheduleAction` выносит переключение
   наружу; правило распространяется на любой новый путь.
5. **Спинлок, берущийся в обработчике прерывания, берётся с замаскированными
   IRQ.** `MutexCell` маскирует их сам; сырой `spin::Mutex` в ядре — только для
   состояния, недостижимого из обработчика.
6. **Рекурсивный захват запрещён.** `spin::Mutex` не реентерабелен.

Автоматической проверки порядка нет: иерархия держится на ревью и на том, что
точек взаимодействия между подсистемами немного и все они перечислены здесь.

## Прерывания и IPI

### Per-CPU инициализация

`InterruptsService` получает операцию инициализации текущего CPU: на GICv3 —
`ICC_SRE`, пробуждение redistributor, группы и приоритеты SGI/PPI, `ICC_PMR` и
`ICC_IGRPEN1`; на GICv2 — GICC. Сейчас всё это выполняет `init`, вызываемый
однократно из `Driver::run`.

Redistributor у GICv3 — свой фрейм на CPU. Маппится весь GICR-регион, а
соответствие «CPU — фрейм» устанавливается по `GICR_TYPER.Affinity_Value`, а не
по порядковому номеру: порядок фреймов не обязан совпадать с порядком узлов
`cpu@N` в FDT. Конец региона отмечен битом `Last` того же регистра.

### Маршрутизация

Линии делятся по природе, а не по политике:

| Класс | Номера | Владелец                                                      |
|-------|--------|---------------------------------------------------------------|
| SGI   | 0–15   | межпроцессорные сигналы, регистры банкованы по CPU            |
| PPI   | 16–31  | таймер; регистры банкованы, включение — операция каждого CPU  |
| SPI   | 32+    | внешние устройства, маршрутизируются распределителем          |

Регистрация обработчика (общая карта) отделяется от включения линии (действие
конкретного CPU): PPI таймера регистрируется один раз, а включается на каждом
CPU при подъёме. Маска CPU в его привязке инертна — маршрутизация относится
только к SPI.

SPI, выданные userspace-драйверам, маршрутизируются маской `ALL`: на GICv2 это
все CPU-интерфейсы, на GICv3 — `IRM=1`, «любому доступному PE». На одном CPU
разницы нет, на N — обработчик начинает исполняться на произвольном. Это
допустимо: обработчик в ядре маскирует линию и поднимает сигнал
IRQ-capability, а работу выполняет userspace-драйвер, которого планировщик
раскладывает по CPU сам. Явная раскладка линий — политика, и она вводится тогда,
когда появится профиль, её оправдывающий.

### IPI

Достаточно двух классов:

| IPI          | Назначение                                                |
|--------------|-----------------------------------------------------------|
| `Reschedule` | на CPU появился более приоритетный runnable-поток         |
| `Halt`       | остановка CPU при панике и `system_off`                   |

Третьего (удалённый вызов функции) не требуется: единственный кандидат —
TLB-shootdown — закрыт аппаратным broadcast.

Адресация — по логическому `CpuId`, с переводом в affinity по той же таблице
идентификации: GICv2 отправляет SGI через `GICD_SGIR` (маска CPU-интерфейсов),
GICv3 — через `ICC_SGI1R_EL1` (affinity). Тип `CpuMask(u8)` заменяется на
целевой тип уровня контракта (`ThisCpu` | `Cpu(CpuId)` | `AllButSelf` | `All`):
8-битная маска — специфика GICv2, а не свойство подсистемы.

Диспетчеризация SGI не проходит через общую карту обработчиков и её лок: номер
известен, обработчик фиксирован, регистры банкованы. Это оставляет
`dispatch_interrupt` с его глобальным локом только на пути внешних устройств.

### Остановка

`system_off` и `panic` рассылают `Halt` и дожидаются подтверждения, прежде чем
гасить машину. Без этого остальные CPU продолжают исполнять код — в том числе
трогать состояние, которое паникующий CPU уже печатает.

## Память

| Подсистема          | Состояние                                                                |
|---------------------|--------------------------------------------------------------------------|
| Аллокатор фреймов   | `NoLockCell` до включения MMU, `MutexCell` после; переход потребляет первый |
| Куча ядра           | heap-фаза под `MutexCell`, bump-фаза - без лока                          |
| Таблицы страниц     | без изменений: `MutexCell<PageMapper>`, барьеры и broadcast уже на месте |
| TLB                 | без изменений: `tlbi ...is` покрывает inner-shareable домен              |
| ASID                | без изменений: per-CPU активные теги и резервирование на rollover        |

Bump-фаза аллокатора остаётся без лока: она заканчивается до включения MMU, где
спинлок неприменим, и однопоточна по построению. Куче лок нужен только в
heap-фазе, которая целиком лежит после включения MMU, поэтому ей достаётся
обычный `MutexCell`.

Аллокатор фреймов — единственный, кто переживает переход: он создаётся в
bump-памяти pre-MMU и переиспользуется после. Стратегия лока у него меняется
вместе с фазой, и это выражено типом, а не рантайм-флагом:
`switch_to_heap_allocator` забирает `PhysicalFrameAllocator<NoLockCell<_>>` из
bump-памяти по значению и собирает из его битмапов
`PhysicalFrameAllocator<MutexCell<_>>` в статике ядра. Альтернатива —
глобальный флаг «локи взведены», по которому ячейка выбирает поведение, — была
отвергнута: она заводит второе, рантаймовое представление фазы MMU рядом с
существующим типовым (`MemorySetup<Early -> Installed -> Prepared -> Enabled>`),
связывает их только порядком строк в boot-пути и оставляет pre-MMU экземпляр
достижимым после перехода.

Путь паники обязан быть неаллоцирующим. Паника достижима из самого аллокатора,
а лок кучи маскирует IRQ, поэтому повторный вход в кучу заклинил бы CPU
насмерть вместо того, чтобы напечатать причину. Обработчик паники первым делом
переводит сток логов в режим без накопления (`BufferedWriter::stop_buffering`);
накопленный буфер при этом не освобождается, потому что освобождение — та же
куча.

Адрес символа линкера живёт в том пространстве, где исполняется код: до
включения MMU он физический (символ материализуется PC-relative), после —
виртуальный. Диапазоны секций ядра поэтому не строятся напрямую как физические
адреса, а проходят через `LinkTimeRange`, чей конструктор объявляет
принадлежность pre-MMU фазе `unsafe`-контрактом. На этапе 2 это правило
распространяется на вторичные CPU: их pre-MMU участок читает те же символы.

Стек pre-MMU фазы фиксирован и не растяжим: через него по значению проходит
`MemorySetup`, чей размер растёт вместе с числом регионов. `_start` заливает
область маркером, post-MMU фаза печатает высшую отметку и отказывает в загрузке,
если маркер не уцелел нигде — переполнение уходит в `.bss` и молча вешает
машину, а не даёт исключение.

Лок кучи обязан маскировать IRQ: аллокация возможна в обработчике прерывания, и
без маски CPU, прерванный внутри своей же критической секции, встанет на
собственном локе. Per-CPU кэш свободных блоков — очевидный следующий шаг, но
только по результатам профиля: он усложняет возврат памяти и не нужен, пока
contention не измерен.

## Userspace

Syscall ABI не меняется. Семантика port, reply и signal определена через
состояние объектов ядра под локом, и параллельность через контракт не
наблюдаема: рандеву остаётся рандеву, реплай — одноразовым, отзыв — каскадным.

Меняется наблюдаемое: потоки процесса действительно исполняются одновременно.
Код, опиравшийся на сериализацию планировщиком, перестаёт быть корректным.
Кольцевой буфер разделяемой памяти (`SpscRing`) на это рассчитан — индексы
публикуются `Release`, читаются `Acquire`, — а userspace-код, не использующий
атомики, требует пересмотра.

Сообщать число CPU через bootstrap-контракт и давать userspace управление
привязкой — отдельные решения. В объём внедрения SMP они не входят: ядро сначала
обязано корректно работать на N CPU, и только потом обсуждать, что из этого
показывать наружу.

## Этапы

Этапы упорядочены по зависимостям и приёмосдаточны поодиночке; однопроцессорная
сборка остаётся рабочей после каждого.

| Этап | Содержание                                                                     | Критерий                                                       |
|------|--------------------------------------------------------------------------------|----------------------------------------------------------------|
| 0    | Лок кучи, смена стратегии лока аллокатора фреймов на границе MMU               | поведение на одном CPU не изменилось, тесты зелёные            |
| 1    | Таблица `MPIDR -> CpuId` из FDT, `current_id` из per-CPU блока, `MAX_CPUS`     | host-тесты разбора `/cpus`, kernel-тест идентичности           |
| 2    | Старт вторичных CPU: PSCI и spin-table, стеки, MMU, векторы, GIC, таймер, idle | под `-smp 4` подняты 4 CPU, каждый в idle, система как раньше  |
| 3    | Планировщик на N CPU: выбор CPU, reschedule-IPI, отложенная отправка           | user-потоки исполняются на разных CPU, тесты зелёные           |
| 4    | `Halt` IPI, остановка на панике и `system_off`                                  | паника на любом CPU гасит машину                               |
| 5    | Миграция, балансировка, per-CPU кэш кучи                                        | вне первой поставки                                            |

Этап 0 отделён намеренно: он чинит гонки, которые существуют уже сейчас как
неопределённое поведение, и его цена не зависит от судьбы остальных этапов.

## Тестирование

Тестовая спека `devices/spec/qemu-aarch64-test.yaml` переводится на `-smp 4`:
однопроцессорный режим — частный случай, и держать его основным значит проверять
не тот путь, который выполняется на устройствах. Однопроцессорный прогон
остаётся доступен через спеку запуска.

Проверки по этапам:

| Что проверяется         | Как                                                                    |
|-------------------------|------------------------------------------------------------------------|
| Подъём CPU              | kernel-тест: число поднятых CPU равно числу узлов `cpu@N` в FDT        |
| Идентификация           | host-тест разбора `/cpus` на многокластерном FDT-фикстуре               |
| Реальная параллельность | kernel-тест: потоки на N CPU, наблюдаются все N значений `CpuId`       |
| Аллокатор под нагрузкой | kernel-тест: параллельные alloc/free с разных CPU, целостность кучи    |
| Кросс-CPU пробуждение   | kernel-тест: разбудить поток с чужой привязкой, CPU в idle просыпается |
| IPC между CPU           | userland-тест: клиент и сервер port'а с разной привязкой                |

Тест на параллельность обязан различать одновременность и чередование:
наблюдение нескольких `CpuId` это делает, а «оба потока продвинулись» — нет.

## Риски

| Риск                                         | Ответ                                                                    |
|----------------------------------------------|--------------------------------------------------------------------------|
| Взаимная блокировка по порядку локов         | зафиксированная иерархия, отложенные списки, отсутствие новых точек связи |
| Гонка, невидимая на одном CPU                | тесты по умолчанию на четырёх CPU                                        |
| Некогерентный handoff при выключенном MMU    | очистка до точки когерентности, минимум читаемого до включения MMU        |
| Совпадение индексов на многокластерном SoC   | идентификация по таблице из FDT, а не по Aff0                            |
| Длинная критическая секция на медленном CPU  | запрет переключения под локом, короткие секции                            |
| Потеря пробуждения при уходе в `wfi`         | IPI — событие пробуждения даже при замаскированном `PSTATE.I`             |

## Границы

Не входит в объём: горячее подключение и отключение CPU, миграция и
балансировка потоков, энергоэффективные политики big.LITTLE, per-CPU кучи, RCU и
lock-free структуры, NUMA, управление привязкой из userspace, вложенные
прерывания.
