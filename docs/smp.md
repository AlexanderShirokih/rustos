# Многопроцессорность

Ядро поднимает все CPU системы: образ один, привилегии одинаковы, отдельного
управляющего ядра нет. Boot CPU отличается тем, что проходит загрузку и
поднимает остальных.

**Планировщик пока работает только на boot CPU.** Вторичные CPU доводятся до
рабочего состояния — MMU, таблицы трансляции, вектора исключений, per-CPU блок,
свой интерфейс контроллера прерываний — и останавливаются в idle с
замаскированными прерываниями. Потоки на них не исполняются, прерывания им не
доставляются: и то и другое требует per-CPU состояния планировщика, которого у
них ещё нет.

Документ описывает то, что есть: идентификация CPU, подъём вторичных ядер,
per-CPU состояние и дисциплина блокировок, обязательная для кода, который
станет исполняться более чем на одном CPU. Syscall ABI многопроцессорностью не
затронут ([syscalls.md](syscalls.md)).

## Идентификация CPU

У CPU два имени. Аппаратное — affinity из `MPIDR_EL1`, поля
`Aff3:Aff2:Aff1:Aff0`; служебные биты регистра (`U`, `MT`, RES1) в него не
входят. Логическое — `CpuId`, индекс в таблице топологии.

Логическими идентификаторами адресуются все per-CPU таблицы, поэтому они
плотные и начинаются с нуля. Aff0 на эту роль не годится: на многокластерном
SoC он нумерует ядро внутри кластера, и CPU разных кластеров получили бы один
индекс, а с ним общий слот планировщика, общий idle-поток и общий активный ASID.

Таблицу строит `hal_common::cpu::CpuTopology` из узла `/cpus`. Учитываются узлы
с `device_type = "cpu"`; отключённые через `status` отбрасываются. `reg`
читается по `#address-cells` узла `/cpus`: одна ячейка или две, где старшая
несёт `Aff3`. Отсутствие свойства значит две ячейки — так предписывает
Devicetree Specification §2.3.5; для `/cpus` свойство обязательно (§3.7),
поэтому путь достижим только на битом DT.

Boot CPU занимает индекс `0` независимо от позиции своего узла в дереве и
попадает в таблицу, даже если дерево его не описывает.

Верхнюю границу числа CPU задаёт `CpuId`: константа `MAX_CPUS` объявлена рядом
с ним в `scheduler`, а конструктор идентификатора за этой границей отказывает.
Владелец предела один, и все, кто заводит per-CPU таблицы — топология, per-CPU
блоки, слоты активных ASID, таблица `cpus` планировщика, — ограничены им по
построению.

## Per-CPU состояние

CPU принадлежат: `Cpu` планировщика (ready-queue, `current`, idle-поток),
загрузочный стек, интерфейс контроллера прерываний и логический `CpuId`.

Точка входа к ним — `CpuLocal`, блок платформенного слоя, чей адрес лежит в
`TPIDR_EL1`. Блок хранит логический идентификатор и указатель на `Cpu`
планировщика; `install_cpu_local` кладёт туда состояние планировщика, а не
подменяет сам блок. Поэтому идентификатор доступен CPU сразу после входа — до
того, как планировщик выдаст ему ready-queue.

`TPIDR_EL1` равен нулю, пока блок не установлен: `_start` и точка входа
вторичного CPU обнуляют регистр явно, потому что после reset он UNKNOWN.

Правило доступа: per-CPU состояние читает и меняет либо владеющий CPU, либо
любой CPU под scheduler-локом.

## Подъём вторичных CPU

### Протокол старта

Способ старта берётся из device tree, а не зашивается в код. Узел `psci` с
`method` (`hvc` или `smc`) даёт вызов `CPU_ON`; `enable-method = "spin-table"`
в узле `cpu@N` — адрес в `cpu-release-addr`. Поддержаны оба: среди целевых
устройств встречаются оба варианта.

Приоритет за узлом самого CPU: `enable-method` объявляет способ для этого
процессора, а `psci` остаётся общим значением по умолчанию для тех, чей узел
способа не объявил.

`CPU_ON` принимает affinity целевого CPU и физический адрес точки входа.
Spin-table требует записи точки входа по `cpu-release-addr`, вытеснения этой
строки кэша до точки когерентности и `sev`.

Разбор биндинга живёт в `hal_common::smp`, сам вызов — в платформенном слое.

### Передача параметров

Стартующий CPU входит с выключенными MMU и кэшами: его обращения к памяти
некэшируемы и не видят строк, лежащих в кэше boot CPU. Поэтому всё, что нужно
ему до включения MMU, boot CPU публикует через блок передачи параметров и
вытесняет до точки когерентности.

В блок входят логический идентификатор стартующего CPU и физические адреса
корней трансляции — identity и higher-half. Identity-отображение нужно ему,
чтобы пережить включение MMU: в этот момент PC ещё физический.

Идентификатор передаётся через блок, а не через регистр, потому что spin-table
не передаёт стартующему CPU ни одного параметра. Слот в блоке один: CPU
поднимаются по одному, и следующий не стартует, пока предыдущий не доложил о
выходе в post-MMU код.

Загрузочные стеки вторичных CPU лежат в `.bss` — стартующий CPU находит свой
PC-относительно, до включения MMU и до всякой аллокации. Границы стека кратны
наибольшей строке кэша среди целевых ядер: перед переключением CPU
инвалидирует стек, а эта операция разрушающая и действует на строку целиком.

### Последовательность

Стартующий CPU:

1. переходит с EL2 на EL1, если вошёл на EL2, и обнуляет `TPIDR_EL1`;
2. читает свой идентификатор из блока передачи параметров;
3. сбрасывает строки кэша над своим стеком и переключается на него;
4. включает MMU корнями из блока и уходит в higher half, переводя стек на
   виртуальный адрес;
5. отключает identity-отображение, ставит `VBAR_EL1` и per-CPU блок;
6. настраивает свой интерфейс контроллера прерываний;
7. докладывает о готовности и уходит в idle.

Идентификатор из блока сверяется с логическим номером, который CPU получает по
собственному affinity из таблицы топологии. Расхождение значит, что слот занят
уже другим CPU.

Отметка о готовности идёт последней: пока её нет, boot CPU держит слот
параметров за этим CPU. Любой отказ на шагах 2-6 уводит CPU в idle без отметки,
boot CPU дожидается таймаута и прекращает подъём, а не переходит к следующему
CPU: слот остался за CPU, состояние которого неизвестно. По той же причине
подъём прекращается и когда команда старта отвергнута.

### Место в загрузке

Подъём идёт после инициализации драйверов и до старта планировщика. Раньше
нельзя: стартующий CPU настраивает свой интерфейс контроллера прерываний, а тот
требует уже настроенного distributor.

Прерывания на вторичном CPU остаются замаскированными, пока планировщик не
выдаст ему per-CPU состояние: обработчик без него работать не может.

CPU, не получивший ни per-CPU блока, ни своего интерфейса контроллера
прерываний, о готовности не докладывает и остаётся в idle. Boot CPU видит
отказ и останавливает подъём: слот параметров описывает ровно один стартующий
CPU, и переназначить его, пока прежний владелец может быть жив, значит отдать
двум CPU общий стек и общий per-CPU блок.

## Прерывания

### Per-CPU инициализация

Redistributor GICv3 принадлежит CPU: у каждого свой. Свой фрейм CPU находит
перебором до отмеченного `Last`, сверяя `GICR_TYPER.Affinity_Value` со своим
affinity, — порядок фреймов задаёт железо, и он не обязан совпадать с
нумерацией ядра. Перебор ограничен размером отображённой области.

Найденное смещение — единственный адрес redistributor для этого CPU: по нему
идут и настройка, и последующие включение линии, приоритет и триггер SGI/PPI.

Расстояние между фреймами берётся из `redistributor-stride`, если device tree
его объявил, иначе — два фрейма по 64 KB. Отображается первая объявленная
область Redistributor'ов; CPU, чей фрейм лежит вне её, себя не находит и в
работу не идёт.

Affinity владельца фрейма (`GICR_TYPER.Affinity_Value`) — четыре байта подряд,
а в `MPIDR_EL1` между `Aff3` и `Aff2` лежат служебные биты, поэтому перед
сравнением значение из регистра упаковывается в раскладку `GICR_TYPER`.

CPU будит свой redistributor, настраивает SGI/PPI и включает интерфейс
(`ICC_SRE_EL1`, `ICC_PMR_EL1`, `ICC_BPR1_EL1`, `ICC_IGRPEN1_EL1`). Distributor
общий и настраивается однократно boot CPU.

Per-CPU часть объявляет каждый контроллер: у GICv2 это CPU interface
(`GICC_PMR`, `GICC_BPR`, `GICC_CTLR`), чьи регистры банкированы по CPU.
Контроллер, не нашедший своей per-CPU части, сообщает об отказе, и CPU в работе
не участвует.

Регистры таймера `CNTV_*` банкированы по CPU: дедлайн программирует то ядро,
на котором таймер сработает.

### Инвалидация TLB

Инвалидация идёт `is`-вариантами `tlbi` — broadcast по inner-shareable домену.
Согласованность TLB между CPU обеспечивает железо, IPI-shootdown ядру не нужен;
достаточно барьеров, которые уже стоят в маппере.

## Память

Стратегия блокировки аллокатора фреймов меняется на границе включения MMU и
выражена типом. До MMU он объявлен `NoLockCell`, после — `MutexCell`; переход
потребляет pre-MMU экземпляр и собирает из его битмапов новый
(`PhysicalFrameAllocator::into_locked`). Pre-MMU экземпляр после перехода
недостижим.

Bump-фаза глобального аллокатора идёт без лока: она заканчивается до включения
MMU и однопоточна по построению. Куче лок нужен только в heap-фазе, которая
целиком лежит после включения MMU.

Адрес символа линкера живёт в том пространстве, где исполняется код: до
включения MMU он физический (символ материализуется PC-relative), после —
виртуальный. Диапазоны секций ядра поэтому проходят через `LinkTimeRange`, чей
конструктор объявляет принадлежность pre-MMU фазе `unsafe`-контрактом.

Аллокатор ASID удерживает активный тег каждого CPU и на rollover резервирует их
в новой generation, чтобы не переиспользовать ASID, активный сейчас на другом
CPU.

## Дисциплина блокировок

Правила — условие корректности. На одном CPU их нарушение приводило максимум к
самоблокировке одного CPU; на нескольких — к остановке машины.

1. **Состояние, доступное более чем одному CPU, защищено `MutexCell`.**
   `NoLockCell` допустим только там, где принадлежность одному CPU доказуема из
   структуры кода. «Ядро однопоточное» доказательством не является.

2. **До включения MMU спинлок не берётся.** Он построен на
   exclusive-инструкциях, а те применимы только к нормальной кэшируемой памяти:
   без трансляции обращения идут как к Device-памяти, где поведение
   `ldxr`/`stxr` не определено.

3. **Иерархия локов.** Scheduler-лок внешний: под ним допустимо взять
   handle-таблицу процесса. Обратный порядок запрещён — путь, держащий лок
   объекта capability, не вызывает планировщик, а откладывает вызов. Обратный
   порядок даёт AB-BA между CPU.

4. **Под локом не переключают контекст.** `ScheduleAction` выносит переключение
   наружу.

5. **Спинлок, берущийся в обработчике прерывания, берётся с замаскированными
   IRQ.** `MutexCell` маскирует их сам; сырой `spin::Mutex` — только для
   состояния, недостижимого из обработчика.

6. **Путь паники не аллоцирует и не берёт неограниченных локов пути записи.**
   Паника достижима из самого аллокатора и из кода, уже держащего лок логгера
   или буфера, а ожидание такого лока — молчаливое зависание вместо
   диагностики. Причина печатается отдельным стоком (`klog::set_panic_stdout`)
   мимо кучи и накопителя, панической стороной writer'а
   (`Writer::write_all_panic`): ожидание там ограничено, просроченный захват
   переходит силой. Печать однократна — стек ядра не имеет защитной страницы, и
   паника на самом пути печати затёрла бы соседнюю память рекурсией.

## Стек загрузки

Стек pre-MMU фазы фиксирован и не растяжим: через него по значению проходит
`MemorySetup`, чей размер растёт вместе с числом регионов. `_start` заливает
область маркером, post-MMU фаза печатает высшую отметку и отказывает в загрузке,
если маркер не уцелел нигде: переполнение уходит в `.bss` и молча вешает машину,
не давая исключения.

Вторичные CPU этот путь не проходят и получают отдельные стеки поменьше.

## Userspace

Семантика port, reply и signal определена через состояние объектов ядра под
локом, и параллельность через контракт не наблюдаема: рандеву остаётся рандеву,
реплай — одноразовым, отзыв — каскадным.

Наблюдаемое изменится, когда планировщик заработает на нескольких CPU: потоки
процесса станут исполняться одновременно, и код, опиравшийся на сериализацию
планировщиком, перестанет быть корректным. Кольцевой буфер разделяемой памяти
(`SpscRing`) на это рассчитан — индексы публикуются `Release`, читаются
`Acquire`, — а userspace-код без атомик требует пересмотра.

Число CPU наружу не сообщается, привязка потоков к CPU userspace недоступна.
