# Userland

Userspace-программы работают в отдельных процессах поверх syscall ABI ядра.
Каждая программа содержит весь свой код; динамическая загрузка и разделяемые
библиотеки не поддерживаются.

## Образ

`userland.img` содержит программы и файлы с абсолютными путями. Состав
задаёт TOML-манифест, передаваемый команде сборки через `--image`.
Основной образ описан в
[user/system/rootkeeper/image.toml](../user/system/rootkeeper/image.toml).

Запись `[[programs]]` выбирает пакет Cargo, исполняемую цель и каталог
программы в образе:

```toml
[[programs]]
package = "rootkeeper"
path = "/rootkeeper"
boot = true
```

Ровно одна программа помечается `boot = true`; ядро запускает её первой.
Исполняемые данные лежат в записи `<path>/exec`.

Если у пакета несколько bin-таргетов, ключ `bin` выбирает один из них.
Идентичность программы — `<package>::<bin>`; краткая форма `<bin>`
допустима, когда это имя принадлежит одному пакету образа. План загрузки
ссылается на идентичность программы, а `path` задаёт её размещение.

Запись `[[files]]` задаёт путь файла в образе и источник на хосте.
Файлы размещаются внутри каталогов программ. Источник без подстановок
обозначает один файл. При подстановках `?`, `*`, `**` и `**/`
совпавшие файлы сохраняют относительные пути от корня обхода.
Пример с файлами — [files-demo/image.toml](../user/examples/files-demo/image.toml).

Повтор одного пути с одинаковыми байтами объединяется в одну запись;
различное содержимое по одному пути останавливает сборку.
Дополнительные файлы задаются флагом `--file path=source`
([commands.md](commands.md#userland)).

Секция `[plan]` выбирает исходный файл плана загрузки. Сборщик проверяет
план и размещает его в образе вместе с индексом экспортов программ.
Свойства компонентов и правила запуска определены в
[rootkeeper.md](rootkeeper.md).

Формат архива и его проверка находятся в
[lib/userland-image/src/image.rs](../lib/userland-image/src/image.rs),
формат программы — в [lib/userland/src/program.rs](../lib/userland/src/program.rs).

## Жизненный цикл

Ядро загружает начальную программу из образа и передаёт ей bootstrap-канал.
Компонент, запущенный родителем, получает стартовую сессию к этому родителю.

Загрузчик создаёт адресное пространство, устанавливает сегменты и стек,
затем запускает первый поток. Предел памяти компонента покрывает его образ,
кучу и стеки потоков. Загрузку через syscall ABI описывает
[syscalls.md](syscalls.md#process-spawning).

### Протокол ComponentStartup

Стартовая сессия использует контракт
[ComponentStartup](../lib/component-abi/src/startup.rs).
Компонент запрашивает подключения к требуемым сервисам и принимает заявки
на собственные экспорты.

Требование `session` запрашивает одну сессию. Требование `all` позволяет
найти подходящие экспорты, выбрать один и открыть его сессию. Правила
сопоставления и запуска провайдера задаёт
[rootkeeper](rootkeeper.md#связывание).

Сессия журнала `Log` под именем `log` — неявное требование.
Рантайм запрашивает её при старте. Если родитель отказал, программа
продолжает работать без журнала.

### Манифест компонента

Программа объявляет требования, экспорты и необходимые признаки машины
макросом `component_manifest!`. Сборщик извлекает декларацию из ELF,
а родитель читает её из программы образа.

Декларация определяет доступные компоненту связи. Подключение открывается
запросом по стартовой сессии. Экспорты программы доступны поиску после
публикации всех требуемых признаков
([rootkeeper.md](rootkeeper.md#связывание)).

Синтаксис макроса и API требований определены в
[lib/component-startup](../lib/component-startup/src/declare.rs);
формат декларации — в
[lib/component-abi/src/manifest.rs](../lib/component-abi/src/manifest.rs).
Пример объявления — [driver-pl031](../user/system/driver-pl031/src/main.rs).

### Старт компонента

Рантайм настраивает состояние процесса и журнал. Программа получает поля
объявленных требований без обращения к родителю и открывает связь `session`
вызовом поля. Отказ этого вызова, включая отсутствие совпадений, называет
требование.

API запроса и правила повторения определены в
[lib/component-startup/src/request.rs](../lib/component-startup/src/request.rs).

### Обслуживание экспорта

Провайдер создаёт порт сервиса, принимает у родителя заявки на свой экспорт
и отвечает каждой заявке сессией либо отказом. Прикладные операции идут по
выданной сессии непосредственно между импортёром и провайдером.

Обслуживание заявок и владение ответом определены в
[lib/component-startup/src/export.rs](../lib/component-startup/src/export.rs).

## Контракт Bootstrap

[Bootstrap](../lib/bootstrap-abi/src/bootstrap_session.rs) — канал начального
процесса к ядру. Он предоставляет доступ к системным полномочиям и образу
userland. Передача этого канала делегирует весь набор его полномочий.

Для доступа к устройствам ядро выдаёт отдельную сессию `Hardware`.
Rootkeeper предоставляет её компоненту `platform`, который выдаёт
драйверам ресурсы устройств
([rootkeeper.md](rootkeeper.md#провижининг-устройств)). Сведения о системе
ядро выдаёт сессией [`SystemInfo`](../lib/bootstrap-abi/src/system_info_session.rs).

## Как написать процесс

Программе нужны bin-таргет в workspace `user/`, линкер-скрипт,
размер стека и запись в манифесте образа. Линкер-скрипт создаёт
`userland_build::emit_linker_script()` из `build.rs`.
Размер стека задаётся в `[package.metadata.userland] stack_size`
манифеста пакета.

Команды сборки и запуска описаны в [commands.md](commands.md#userland),
размещение тестовых программ — в [testing.md](testing.md#фикстуры).

### Программа на стандартной библиотеке

Программа объявляет обычный `main`. Точка входа стандартной библиотеки
настраивает рантайм и стандартный вывод. `stdout` и `stderr` поступают
в системный журнал.

Требования объявляются макросом `component_manifest!` из крейта
`components` и выдаются вызовом `components::requirements`.
Примеры — [hello-std](../user/examples/hello-std/src/main.rs) и
[clock-std](../user/examples/clock-std/src/main.rs).

Для `std::fs` программа получает сессию `Namespace` и устанавливает её
корнем файловых путей через `std::os::molecular::install_filesystem_root`.
Пример — [files-demo](../user/examples/files-demo/src/main.rs).
Поддерживаемые файловые операции описаны в [filesystem.md](filesystem.md).

### Программа на C

Программа на C — пакет Cargo, корень которого вызывает
`c_library::c_program!()`. Её C-исходники компилирует
`userland_build::CSources` из `build.rs`. Крейт
[c-library](../lib/c-library/src/lib.rs) даёт программе точку входа, кучу,
завершение, файлы по абсолютным путям, часы и сон и потоки POSIX; `stdout` и
`stderr` поступают в системный журнал.
Файлы требуют файлового корня — сессии `Namespace`, которую программа получает
требованием манифеста и устанавливает через `c_library::install_filesystem_root`.
Конструкторы C выполняются до установки корня, и операции с путями в них дают
`ENOTCONN`.
Пример — [hello-c](../user/examples/hello-c/src/hello.c).

### Freestanding-программа

Программа на `no_std` объявляет точку входа атрибутом
[`program_entry::component`](../lib/program-entry/src/lib.rs) на функции,
которая получает требования своего манифеста. Программа без стартовой
сессии компонента, например корень композиции, объявляет атрибут
`program_entry::process` и получает владельца своего стартового handle. Код выхода
процесса следует результату функции. Программа использует `runtime` напрямую.

```rust
#![no_std]
#![no_main]

use component_startup::{StartupError, component_manifest};
use rtc_abi::rtc;
use runtime::log_fmt;

component_manifest! {
    struct ClockStartup {
        requirements: { rtc: session(rtc::Protocol) },
    }
}

#[program_entry::component]
fn run(requirements: ClockStartup) -> Result<(), StartupError> {
    let ClockStartup { rtc, .. } = requirements;
    if let Ok(seconds) = rtc.open()?.client().now() {
        log_fmt(format_args!("rtc reads {seconds}"));
    }
    Ok(())
}
```

Правила единственного рантайма в процессе заданы в
[workspace.md](workspace.md#состояние-процесса).
