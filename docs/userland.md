# Userland

Userspace-процесс несёт весь свой код и работает поверх syscall ABI ядра:
динамической загрузки и разделяемых библиотек система не знает. Код программ
лежит в `user/`, а упакованы они в один образ, который ядро получает от
загрузчика и из которого поднимает первый процесс.

## Образ

`userland.img` — плоский архив именованных блобов с одной таблицей. Программа не
отдельный вид записи: это запись, содержимое которой начинается своей магией.

Состав образа задаёт TOML-манифест, путь к которому передаётся в `--image` (по
умолчанию `user/rootkeeper/image.toml`):

```toml
version = 1

[plan]
source = "user/rootkeeper/system.toml"

[stage1]
source = "user/rootkeeper/stage1.toml"

[[mount_tables]]
source = "user/rootkeeper/namespace.toml"

[[programs]]
package = "rootkeeper"
path = "/boot/rootkeeper"
boot = true

[[files]]
path = "/boot/rootkeeper/assets"
source = "user/rootkeeper/assets/**/*.txt"
```

`[[programs]]` и `[[files]]` различаются только тем, откуда инструмент берёт
байты: из собранного ELF пакета либо с диска. Запись файла лежит в каталоге
своей программы — записи вне каталогов образ не принимает. `boot = true` стоит
ровно у одной программы: её запись инструмент проставляет в `boot_index`
заголовка образа, соглашения об имени пути нет.

Элемент `[[programs]]` объявляет идентичность программы и её размещение. Имя
cargo bin-таргета инструмент берёт из `cargo metadata`: единственный bin-таргет
пакета `package` либо таргет, названный ключом `bin`. Пакет с несколькими
bin-таргетами требует явного `bin`; пакет без bin-таргетов манифест отвергает.
По этому имени артефакт собирается и отыскивается. Идентичность имеет две формы:
квалифицированную `<package>::<bin>`, уникальную в пределах образа, и краткую
`<bin>`.

Размещение задаёт `path`: запись образа ложится по объявленному пути и лежит под
его последним компонентом. Описания композиции называют программу идентичностью
([rootkeeper.md](rootkeeper.md#план-загрузки)), которую сборка разрешает в запись
реестра: квалифицированную форму — всегда, краткую — пока её объявил ровно один
пакет образа. Неоднозначная краткая ссылка отвергается перечислением этих
пакетов. Компонент без ключа `name` зовётся той формой, которой записана ссылка.

Секции `[plan]`, `[stage1]` и `[[mount_tables]]` называют host-описания, которые
инструмент проверяет, компилирует и кладёт в образ обычными записями: план
ступени 0 ([rootkeeper.md](rootkeeper.md#план-загрузки)), ступень 1
([rootkeeper.md](rootkeeper.md#ступени-загрузки)) и дерево имён файловой
подсистемы ([filesystem.md](filesystem.md#дерево-имён-загрузки)). Ступень 1 и
дерево имён без `[plan]` манифест отвергает: связывать их слоты и разрешать
имена экземпляров не с чем.

Манифест отвечает на вопрос, что лежит в образе, план — на вопрос, что и с
какими аргументами поднимает rootkeeper.

Источник без подстановок даёт одну запись по пути `path`; каталог сам по себе
источником не является. Источник с подстановкой делится по первому компоненту,
её содержащему: слева корень обхода, справа шаблон, а каждый принятый файл
ложится под `path` вместе со своим путём от корня обхода.

| Шаблон | Что принимает                                       |
|--------|-----------------------------------------------------|
| `?`    | один символ внутри компонента                       |
| `*`    | любую последовательность символов внутри компонента |
| `**`   | любую последовательность, разделители включая       |
| `**/`  | любую цепочку каталогов, в том числе пустую         |

Обход рекурсивен, а его порядок — по имени записи каталога, поэтому состав
образа не зависит от файловой системы сборки. Один путь, заполненный несколько
раз одним и тем же содержимым, даёт одну запись; тот же путь с разным
содержимым сборку отвергает. Файлы поверх манифеста добавляет флаг
`--file path=source` ([commands.md](commands.md#userland)).

Размер стека программы фиксируется в разделе `[package.metadata.userland]` её
`Cargo.toml`:

```toml
[package.metadata.userland]
stack_size = 65536
```

### Формат файла

Заголовок образа занимает 24 B, за ним идёт таблица записей, байты путей и
данные записей.

| Поле        | Смещение | Размер | Описание                                        |
|-------------|----------|--------|-------------------------------------------------|
| magic       | 0        | 8 B    | `USRLIMG\0`                                     |
| version     | 8        | u16 LE | версия формата (текущая: 1)                     |
| entry_count | 10       | u16 LE | число записей таблицы (>= 1)                    |
| boot_index  | 12       | u16 LE | запись, с которой ядро поднимает первый процесс |
| reserved    | 14       | u16 LE | ноль                                            |
| total_size  | 16       | u64 LE | полный размер файла в байтах                    |

Запись таблицы занимает 28 B:

| Поле        | Смещение | Размер | Описание                                     |
|-------------|----------|--------|----------------------------------------------|
| path_offset | 0        | u64 LE | смещение байт пути в файле                   |
| path_len    | 8        | u16 LE | длина пути (UTF-8, без нуля)                 |
| alias_of    | 10       | u16 LE | номер записи, чьё окно повторено, плюс один  |
| data_offset | 12       | u64 LE | смещение данных, кратно `USERLAND_PAGE_SIZE` |
| data_size   | 20       | u64 LE | длина данных в байтах                        |

Записи отсортированы строго по возрастанию пути: на этом стоит двоичный поиск, а
строгость порядка запрещает дубликаты. Путь — непустой ASCII не длиннее
`USERLAND_ENTRY_PATH_CAPACITY` (255 байт), оканчивающийся непустым компонентом.

Нулевой `alias_of` означает собственное окно данных: такие окна лежат в порядке
таблицы и не пересекаются. Ненулевой объявляет запись повтором окна более ранней
записи — одинаковое содержимое хранится в образе один раз.

### Формат программы

Заголовок программы (32 B) и дескрипторы сегментов занимают первую страницу
записи — отсюда предел в 101 сегмент на программу. Данные сегментов начинаются
со смещения `USERLAND_PAGE_SIZE` внутри записи и выровнены на него.

| Поле          | Смещение | Размер | Описание                  |
|---------------|----------|--------|---------------------------|
| magic         | 0        | 8 B    | `USRPROG\0`               |
| entry_va      | 8        | u64 LE | точка входа в VA процесса |
| stack_size    | 16       | u64 LE | размер стека в байтах     |
| segment_count | 24       | u16 LE | число сегментов           |
| reserved      | 26       | 6 B    | ноль                      |

Дескриптор сегмента занимает 40 B; сегменты и их `va_base` выровнены на страницу
(`USERLAND_PAGE_SIZE = 4096`).

| Поле        | Смещение | Размер | Описание                                      |
|-------------|----------|--------|-----------------------------------------------|
| file_offset | 0        | u64 LE | смещение данных сегмента от начала записи     |
| file_size   | 8        | u64 LE | размер данных в файле                         |
| va_base     | 16       | u64 LE | базовый VA в адресном пространстве процесса   |
| mem_size    | 24       | u64 LE | размер в памяти (>= file_size; разница — BSS) |
| flags       | 32       | u32 LE | права: 0=RW, 1=RO, 2=RX                       |
| reserved    | 36       | u32 LE | ноль                                          |

Инструмент сборки читает ELF каждой программы и раскладывает её
`PT_LOAD`-сегменты в содержимое записи.

## Жизненный цикл

После инициализации ядро берёт запись по `boot_index`, разбирает её содержимое
как программу, создаёт bootstrap-порт и корневой `Resource`, раскладывает
сегменты в новое адресное пространство и стартует первый поток. Имя процесса —
последний компонент пути его записи (`/boot/filesystem-ramfs` →
`filesystem-ramfs`), не длиннее 64 байт.

Точка входа процесса — `_start`, которой в регистре `x0` приходит raw HandleId
начальной capability:

```rust
#[unsafe(no_mangle)]
pub extern "C" fn _start(startup: Handle) -> ! { /* ... */ }
```

Для первого процесса начальная capability — bootstrap-порт ядра. Низкоуровневый
`userland_loader::load_entry` позволяет userspace-загрузчику передать дочернему
процессу произвольный хэндл.

### Startup-порт дочернего процесса

Стандартный запуск дочернего приложения выполняет
`userland_loader::launch_entry`: загрузчик создаёт `Port` без значка, серверную
сторону передаёт процессу в `x0`, а клиентскую передаёт callback'у для одного
кадра прикладного типизированного IPC-контракта:

```rust
let process = launch_entry(&program, None, &resource, |startup| -> Result<()> {
    driver_args::Client::new(PortTransport::client(startup.handle()))
        .provide(device, service)?;
    Ok(())
})?;
```

Ошибка callback'а завершает потомка через `ProcessTerminate` и освобождает его
таблицу хэндлов и metering-бюджет; отказ самого cleanup заменяет исходную
ошибку, чтобы вызывающий не получил ложного подтверждения отката.

Одноразовый получатель принимает кадр через `runtime::receive_startup` — функция
закрывает серверную сторону startup-порта после диспетчеризации:

```rust
let DriverState { device, service } =
    receive_startup(startup, driver_args::dispatch)?.ok_or(Error::Start)?;
```

Тип аргументов и владение передаваемыми capability остаются частью прикладного
IPC-контракта. Если тот же порт после стартового кадра несёт admin-команды,
`launch_entry_retained` возвращает `InitializedProcess` с полями `process` и
`startup`; порт обслуживают обычным `PortTransport`, а клиентская сторона такого
порта минтится под значком, поэтому исчезновение поднявшего процесса приходит
потомку как `SenderGone` ([port.md](port.md#уход-значка)).

Процесс называет второй аргумент, а `None` берёт имя самой записи. Запись с
программой лежит в каталоге компонента под именем `program`, поэтому вызывающий,
поднимающий компонент, берёт имя каталога через `component_name`.

### Стартовая транзакция компонента

Компонент композиции принимает не один стартовый кадр, а транзакцию: сначала
базовый кадр с его лог-сессией и серверными сторонами control- и service-портов,
следом — capability слотов в порядке объявления
([rootkeeper.md](rootkeeper.md#связывание)). Слоты едут отдельными кадрами того
же одноразового startup-порта: кадр IPC несёт не больше `MESSAGE_MAX_HANDLES`
капабилити, и базовый кадр занимает их полностью.

Контракт транзакции и её приёмник живут в `lib/component-abi`. Срок прикладному
callback общий loader не задаёт: конечный send timeout и подтверждение возврата
бюджета — контракт managed startup
([rootkeeper.md](rootkeeper.md#managed-startup)).

### Манифест компонента

Свои связи компонент объявляет в коде — макросом `component_manifest!` из
`lib/component-abi`. Объявление называет слоты по порядку транзакции: имя, вид
и то, чем композиция слот наполняет — семейство совместимостей у устройства,
имя протокола у импорта.

| Ключ                   | Что объявляет                                              |
|------------------------|------------------------------------------------------------|
| `slots`                | слоты по порядку приёма                                    |
| `exports`              | протокол, который компонент обслуживает на service-порту   |
| `controls`             | протокол, который компонент обслуживает на control-порту   |
| `establishes_sessions` | сессии своего service-порта компонент заводит сам          |

Порты разные, поэтому `exports` и `controls` объявляются порознь. Один порт
несёт один протокол, поэтому `controls` вместе с `establishes_sessions` сборка
отвергает, а установление сессий без `exports` отвергает как бессмысленное.

Импорт протокола принимает необязательный `instance` — имя
экземпляра-провайдера; без него сборка ищет единственного провайдера в
композиции ([rootkeeper.md](rootkeeper.md#связывание)). Слот-каталог называет
`instance` обязательно: протокола у него нет, а провайдеров сессий композиция
несёт несколько. Имя своего каталога компонент не выбирает — его берёт
композиция из записи его программы.

```rust
component_manifest! {
    struct ImageFileSystemStartup {
        exports: "FileSystem",
        establishes_sessions: true,
        slots: { image: userland },
    }
}

component_manifest! {
    struct RtcStartup {
        slots: {
            line: irq(compatible = ["arm,pl031"]),
            window: mmio(compatible = ["arm,pl031"]),
        },
    }
}

component_manifest! {
    struct FileReaderStartup {
        slots: { files: service(protocol = "FileSystem", instance = "ramfs") },
    }
}
```

Список совместимостей — заявка драйвера на семейство устройств: подходит любая
из строк, а выбор между ними принадлежит описанию платформы конкретной машины.
Номер ресурса (`resource`, по умолчанию `0`) выбирает линию либо окно среди
ресурсов устройства — это знание драйвера о железе, а не решение композиции.

Из одного объявления берутся приёмник и манифест. Приёмник — структура с полями
`log`, `control`, `service` и названными слотами; её `receive` принимает
транзакцию целиком и отвергает ту, что объявлению не отвечает. Манифест — запись
в секции `.component.manifest` собранной программы: артефакт сборки, а не запись
образа. Сборщик читает её из ELF каждой программы, на которую ссылается план, и
по ней строит слоты компонента. Секция необязательна — программа без неё
объявляет пустое.

Заголовок манифеста занимает 16 B, за ним идут имя протокола service-порта, имя
протокола control-порта и записи слотов по порядку приёма:

| Поле        | Смещение | Размер | Описание                                             |
|-------------|----------|--------|------------------------------------------------------|
| magic       | 0        | 8 B    | `CMPMFST\0`                                          |
| version     | 8        | u16 LE | версия формата (текущая: 1)                          |
| slot_count  | 10       | u16 LE | число слотов                                         |
| export_len  | 12       | u8     | длина протокола service-порта; ноль — без экспорта   |
| flags       | 13       | u8     | бит 0: компонент заводит сессии сам                  |
| control_len | 14       | u8     | длина протокола control-порта; ноль — без объявления |
| reserved    | 15       | 1 B    | ноль                                                 |

Заголовок слота занимает 4 B, за ним идут его имена — длина `u8` и байты
каждого:

| Поле       | Смещение | Размер | Описание                                                                   |
|------------|----------|--------|----------------------------------------------------------------------------|
| kind       | 0        | u8     | 0 userland, 1 irq, 2 mmio, 3 service, 4 directory, 5 supervisor, 6 control |
| resource   | 1        | u16 LE | номер ресурса устройства                                                   |
| name_count | 3        | u8     | число имён слота                                                           |

У устройства имена — строки совместимости (хотя бы одна), у импорта протокола —
его имя и за ним необязательное имя экземпляра, у каталога — имя
экземпляра-провайдера; у `userland` и `supervisor` имён нет.

## Контракт Bootstrap

Bootstrap — типизированный канал между корневым процессом и ядром, определённый
в `lib/bootstrap-abi`. Через него корневой процесс запрашивает корневые
capability. Капа канала остаётся у него: она открывает весь набор корневых
полномочий сразу, и её передача потомку равнозначна передаче их всех.

Boot FDT канал выдаёт регионом поверх страниц с блобом. Загрузчик кладёт блоб по
произвольному адресу, не обязательно с начала страницы, поэтому вместе с капой
региона контракт отдаёт смещение первого байта блоба от её начала.

## Журнал

Строки в системный журнал процесс шлёт по контракту `Log` из `lib/log-abi`.
Сервером контракта служит relay из `lib/log-relay` в корневом процессе: он
пересылает принятые строки ядру по bootstrap-каналу. Потомкам достаются
лог-сессии его порта. Свою лог-капу процесс отдаёт платформенному слою через
`runtime::install_log` вместе с тегом своих строк и дальше пишет их через
`log_line` и `log_fmt`. Программа на стандартной библиотеке лог-сессию не
устанавливает: её забирает точка входа, а тег такой программе даёт значок
сессии.

## Часы

Монотонные часы процесса — `runtime::Instant`. Syscall они не требуют: ядро
открывает EL0 архитектурный счётчик времени и его частоту, а платформенный слой
переводит тики в наносекунды. Программировать таймер процесс по-прежнему не может.

Точка отсчёта у часов общая с дедлайнами `timeout_ns` блокирующих вызовов,
поэтому разность двух замеров сравнима с переданным тайм-аутом.

## Как написать процесс

Программа образа существует в двух формах. На стандартной библиотеке пишутся
компоненты композиции: точку входа и приём стартового набора им отдаёт
платформенный слой. Freestanding-форма — свои `_start` и `panic_handler` без
`main` — обслуживает запуск мимо стартовой транзакции компонента: корневой
процесс, `testrunner` и его фикстуры.

Что нужно новому процессу в обеих формах помимо кода:

- линкер-скрипт: точка входа `_start`, базовый адрес образа (`0x00400000`),
  выравнивание секций `.text/.rodata/.data/.bss` на страницу, границы таблицы
  тестов в `.rodata` и незагружаемая секция `.component.manifest`. Скрипт кладёт
  в сборку `userland_build::emit_linker_script()` из `build.rs`;
- раздел `[package.metadata.userland]` с размером стека;
- членство в workspace `user/`;
- включение пакета в TOML-манифест образа с путём записи.

### Программа на стандартной библиотеке

Точка входа принимает стартовый набор capability до `main` и оставляет от него
лог-сессию. Исходник — обычный `fn main`, а `println!` уходит в системный журнал
под именем компонента:

```rust
fn main() {
    println!("hello");
}
```

Свой манифест такая программа кладёт формой `component_manifest!` без структуры:
приёмник транзакции ей не нужен, набор она получает от платформенного слоя.

```rust
component_abi::component_manifest! {
    slots: { rtc: service(protocol = "Rtc") },
}
```

Набор выдаёт модуль `std::os::molecular`: серверные стороны control- и
service-портов и слоты в порядке объявления. Capability названы сырым
идентификатором, а типы контрактов приходят программе её собственными
зависимостями ([workspace.md](workspace.md#таргеты-сборки)). Программа надевает
на идентификатор свои обёртки:

```rust
let startup = std::os::molecular::startup().expect("composition startup set");
let session = startup.slots().next().expect("the Rtc session slot");
let clock = rtc::Client::new(PortTransport::client(Handle::from_nonzero(session)));
println!("rtc reads {}", clock.now()?);
```

Образцы — `hello-std` и `clock-std` в `user/`. Стеки потоков программа берёт из
своей кучи, и предел памяти компонента покрывает их наравне с ней. Отсюда же
граница: платформенное состояние процесса держит копия внутри `std`, а
зависимостями программа берёт крейты без состояния - объекты ядра и обёртки
вызовов ([workspace.md](workspace.md#один-рантайм-в-процессе)). Лог-сессия
принадлежит `std`, и строка в журнал идёт `println!`.

### Freestanding-программа

Свои `_start`, `panic_handler` и глобальный аллокатор (`runtime::process_heap!`)
программа объявляет сама, а платформенный слой берёт из `lib/runtime`.
Стартовую транзакцию компонента она принимает приёмником из своего
`component_manifest!` (`driver-pl031` в `user/`); низкоуровневый `load_entry`
кладёт ей в `x0` одну начальную capability:

```rust
#![no_std]
#![no_main]

use runtime::{PortTransport, thread_exit};
use syscall::Handle;

runtime::process_heap!();

#[unsafe(no_mangle)]
pub extern "C" fn _start(log: Handle) -> ! {
    let client = log_abi::log::Client::new(PortTransport::client(log));
    let result = client.write_str("init", "process started");

    thread_exit(u64::from(result.is_err()))
}

#[panic_handler]
fn panic(_info: &core::panic::PanicInfo<'_>) -> ! {
    loop { core::hint::spin_loop() }
}
```
