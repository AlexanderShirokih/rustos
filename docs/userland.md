# Userland

Userspace-процесс содержит весь свой код и работает поверх syscall ABI ядра.
Система не поддерживает динамическую загрузку и разделяемые библиотеки. Код
программ лежит в `user/`, а упакованы они в один образ, который ядро получает от
загрузчика и из которого поднимает начальный процесс.

## Образ

`userland.img` — плоский архив именованных блобов с одной таблицей. В формате
нет отдельного вида записи под программу. Программа — это обычная запись, чьё
содержимое начинается своей магией.

Состав образа задаёт TOML-манифест, путь к которому передаётся в `--image` (по
умолчанию `user/system/rootkeeper/image.toml`):

```toml
version = 1

[plan]
source = "user/system/rootkeeper/system.toml"

[[programs]]
package = "rootkeeper"
path = "/rootkeeper"
boot = true

[[files]]
path = "/rootkeeper/assets"
source = "user/system/rootkeeper/assets/**/*.txt"
```

`[[programs]]` и `[[files]]` различаются одним — откуда инструмент берёт байты.
Программа приходит из собранного ELF пакета, файл читается с диска. Запись файла
лежит в каталоге своей программы; записей вне каталогов образ не принимает.
`boot = true` стоит ровно у одной программы, и её номер инструмент проставляет в
`boot_index` заголовка образа. Само имя пути при этом ничем не закреплено.

Элемент `[[programs]]` объявляет две вещи — идентичность программы и её
размещение.

Идентичность строится на имени cargo bin-таргета, которое инструмент берёт из
`cargo metadata`. Это либо единственный bin-таргет пакета `package`, либо
таргет, названный ключом `bin`. Пакет с несколькими bin-таргетами требует явного
`bin`, а пакет вовсе без bin-таргетов манифест отвергает. По этому же имени
артефакт собирается и потом отыскивается. Форм у идентичности две:
квалифицированная `<package>::<bin>`, уникальная в пределах образа, и краткая
`<bin>`.

Размещение задаёт `path` — каталог программы в образе. Программа лежит в нём
записью `program`. Описания композиции называют программу именно
идентичностью ([rootkeeper.md](rootkeeper.md#план-загрузки)), а сборка разрешает
её в запись реестра. Квалифицированная форма разрешается всегда, краткая — пока
её объявил ровно один пакет образа. Неоднозначную краткую ссылку сборка
отвергает, перечислив эти пакеты. Компонент без ключа `name` зовётся той формой,
которой записана ссылка.

Секция `[plan]` называет host-описание, которое инструмент проверяет,
компилирует и размещает в образе обычной записью. Это план запуска
([rootkeeper.md](rootkeeper.md#план-загрузки)).

Разделение труда простое. Манифест отвечает, что лежит в образе. План отвечает,
что и с какими аргументами rootkeeper поднимает.

Источник без подстановок даёт одну запись по пути `path`; каталог сам по себе
источником не считается. Источник с подстановкой делится по первому компоненту,
который её содержит. Слева от него — корень обхода, справа — шаблон, а каждый
принятый файл ложится под `path` вместе со своим путём от корня обхода.

| Шаблон | Что принимает                                       |
|--------|-----------------------------------------------------|
| `?`    | один символ внутри компонента                       |
| `*`    | любую последовательность символов внутри компонента |
| `**`   | любую последовательность, разделители включая       |
| `**/`  | любую цепочку каталогов, в том числе пустую         |

Обход рекурсивен и идёт по имени записи каталога, а не в порядке, который вернула
файловая система. Поэтому состав образа от машины сборки не зависит. Один путь,
заполненный несколько раз одним и тем же содержимым, даёт одну запись; тот же
путь с разным содержимым сборку останавливает. Флаг `--file path=source`
добавляет файлы поверх манифеста ([commands.md](commands.md#userland)).

Размер стека программы фиксируется в разделе `[package.metadata.userland]` её
`Cargo.toml`:

```toml
[package.metadata.userland]
stack_size = 65536
```

### Формат файла

Заголовок образа занимает 24 B, за ним идёт таблица записей, байты путей и
данные записей.

| Поле        | Смещение | Размер | Описание                                        |
|-------------|----------|--------|-------------------------------------------------|
| magic       | 0        | 8 B    | `USRLIMG\0`                                     |
| version     | 8        | u16 LE | версия формата (текущая: 1)                     |
| entry_count | 10       | u16 LE | число записей таблицы (>= 1)                    |
| boot_index  | 12       | u16 LE | запись начального процесса                      |
| reserved    | 14       | u16 LE | ноль                                            |
| total_size  | 16       | u64 LE | полный размер файла в байтах                    |

Запись таблицы занимает 28 B:

| Поле        | Смещение | Размер | Описание                                     |
|-------------|----------|--------|----------------------------------------------|
| path_offset | 0        | u64 LE | смещение байт пути в файле                   |
| path_len    | 8        | u16 LE | длина пути (UTF-8, без нуля)                 |
| alias_of    | 10       | u16 LE | номер записи, чьё окно повторено, плюс один  |
| data_offset | 12       | u64 LE | смещение данных, кратно `USERLAND_PAGE_SIZE` |
| data_size   | 20       | u64 LE | длина данных в байтах                        |

Записи отсортированы строго по возрастанию пути. На этом стоит двоичный поиск, а
строгость порядка заодно запрещает дубликаты. Путь — непустой ASCII не длиннее
`USERLAND_ENTRY_PATH_CAPACITY` (255 байт), оканчивающийся непустым компонентом.

Нулевой `alias_of` означает собственное окно данных. Такие окна лежат в порядке
таблицы и не пересекаются. Ненулевой объявляет запись повтором окна более ранней
записи, и одинаковое содержимое хранится в образе один раз.

### Формат программы

Заголовок программы (32 B) и дескрипторы сегментов занимают первую страницу
записи — отсюда предел в 101 сегмент на программу. Данные сегментов начинаются
со смещения `USERLAND_PAGE_SIZE` внутри записи и выровнены на него.

| Поле          | Смещение | Размер | Описание                  |
|---------------|----------|--------|---------------------------|
| magic         | 0        | 8 B    | `USRPROG\0`               |
| entry_va      | 8        | u64 LE | точка входа в VA процесса |
| stack_size    | 16       | u64 LE | размер стека в байтах     |
| segment_count | 24       | u16 LE | число сегментов           |
| reserved      | 26       | 6 B    | ноль                      |

Дескриптор сегмента занимает 40 B; сегменты и их `va_base` выровнены на страницу
(`USERLAND_PAGE_SIZE = 4096`).

| Поле        | Смещение | Размер | Описание                                      |
|-------------|----------|--------|-----------------------------------------------|
| file_offset | 0        | u64 LE | смещение данных сегмента от начала записи     |
| file_size   | 8        | u64 LE | размер данных в файле                         |
| va_base     | 16       | u64 LE | базовый VA в адресном пространстве процесса   |
| mem_size    | 24       | u64 LE | размер в памяти (>= file_size; разница — BSS) |
| flags       | 32       | u32 LE | права: 0=RW, 1=RO, 2=RX                       |
| reserved    | 36       | u32 LE | ноль                                          |

Инструмент сборки читает ELF каждой программы и раскладывает её
`PT_LOAD`-сегменты в содержимое записи.

## Жизненный цикл

После инициализации ядро берёт запись по `boot_index`, разбирает её содержимое
как программу, создаёт bootstrap-порт и корневой `Resource`, раскладывает
сегменты в новое адресное пространство и стартует первый поток. Имя процесса —
имя каталога его программы (`/rootkeeper/program` → `rootkeeper`), не
длиннее 64 байт.

Точка входа процесса — `_start`, которой raw HandleId начальной capability
приходит в регистре `x0`:

```rust
#[unsafe(no_mangle)]
pub extern "C" fn _start(startup: Handle) -> ! { /* ... */ }
```

У начального процесса эта capability — bootstrap-порт ядра, у компонента
композиции — стартовая сессия к родителю. `userland_loader::load_entry` запускает
программу и передаёт потомку начальную capability, которую называет вызывающий.

Второй аргумент `load_entry` задаёт имя процесса. Rootkeeper называет процесс
компонента именем экземпляра из записи плана
([rootkeeper.md](rootkeeper.md#план-загрузки)). Ядро называет начальный процесс
именем каталога его программы, которое возвращает `component_name`.

### Протокол ComponentStartup

Контракт стартовой сессии — `component_startup` в `lib/component-abi`. Родитель
принимает три запроса компонента:

| Запрос    | Ответ                                                                  |
|-----------|------------------------------------------------------------------------|
| `session` | сессия требования от провайдера через `accept` либо от самого родителя |
| `region`  | регион образа требования с правом чтения до конца incarnation          |
| `accept`  | следующая заявка импортёра на экспорт вызывающего                      |

Кроме требований манифеста компонент всегда запрашивает сессию протокола `Log`
под именем `log`. Манифест это требование не объявляет. Запрос делает
`runtime::start_component` по стартовой сессии и ставит полученную сессию в
состояние процесса. У программы на стандартной библиотеке `start_component`
вызывает точка входа `std`, у freestanding-программы — её `_start`. При отказе
родителя компонент работает без журнала.

### Старт компонента

Функция `request` объявления `component_manifest!` запрашивает у родителя
требования в порядке объявления. Каждый запрос ждёт ответа не дольше
`STARTUP_REQUEST_TIMEOUT`. На `IpcError::PeerClosed` повторяется только запрос
требования `session`. Первый отказ требования завершает старт значением
`StartupError` с именем требования.

### Обслуживание экспорта

Провайдер сам создаёт порт своего экспорта. Цикл `serve_export::<P>(parent, open)`
забирает у родителя заявки импортёров операцией `accept` и передаёт область
каждой заявки обработчику `open`. `open` возвращает сессию либо отказ
`SessionError`, и результат уходит импортёру ответом на его запрос `session`.

Цикл завершается первым отказом `accept` либо ошибкой IPC и возвращает
`ExportError`, после чего программа выходит (образец — `driver-pl031` в `user/`).

### Манифест компонента

Компонент объявляет свои связи макросом `component_manifest!` из
`lib/component-startup`. У объявления два ключа:

| Ключ           | Что объявляет                |
|----------------|------------------------------|
| `requirements` | требования в порядке запроса |
| `exports`      | протоколы экспортов          |

Требование относится к одному из двух видов:

| Вид       | Что объявляет манифест | Что получает компонент           |
|-----------|------------------------|----------------------------------|
| `region`  | ничего                 | read-only регион userland-образа |
| `session` | тип протокола          | сессию этого протокола           |

Описание композиции задаёт провайдера и область требования `session`
([rootkeeper.md](rootkeeper.md#связывание)).

Экспорт называет протокол. У экспорта нет поля в приёмнике, и провайдер сам
создаёт порт экспорта ([«Обслуживание экспорта»](#обслуживание-экспорта)).

```rust
component_manifest! {
    struct ImageFileSystemStartup {
        requirements: { namespace: session(namespace_admin::Protocol), image: region },
        exports: [file_system::Protocol],
    }
}

component_manifest! {
    struct RtcStartup {
        requirements: { platform: session(platform::Protocol) },
        exports: [rtc::Protocol],
    }
}
```

Объявление порождает приёмник, функцию старта
([«Старт компонента»](#старт-компонента)) и запись манифеста в секции
`.component.manifest` собранной программы.

Приёмник — структура с полем `parent` и полем на каждое требование. Вид
требования задаёт тип поля: `session` — сессия протокола, `region` — регион
памяти. Поле `parent` — клиент стартовой сессии.

Сборщик читает запись манифеста из ELF каждой программы, на которую ссылается
план, и строит по ней требования компонента. У программы без этой секции
манифест пуст.

Заголовок манифеста занимает 16 B. За ним идут протоколы экспортов в порядке
объявления, каждый как длина `u8` и байты, затем записи требований в порядке
запроса:

| Поле              | Смещение | Размер | Описание                    |
|-------------------|----------|--------|-----------------------------|
| magic             | 0        | 8 B    | `CMPMFST\0`                 |
| version           | 8        | u16 LE | версия формата (текущая: 1) |
| requirement_count | 10       | u16 LE | число требований            |
| export_count      | 12       | u8     | число экспортов             |
| reserved          | 13       | 3 B    | ноль                        |

Запись требования начинается байтом вида: 0 region, 1 session. За ним идёт имя
требования, у сессии затем идентификатор протокола, каждое как длина `u8` и
байты. Имя требования совпадает с именем поля в объявлении и не повторяется в
записи.

## Контракт Bootstrap

Bootstrap — типизированный канал между корневым процессом и ядром, определённый в
`lib/bootstrap-abi`. Через него корневой процесс запрашивает корневые capability.
Капу самого канала он никому не отдаёт. Она открывает весь набор корневых
полномочий сразу, и передать её потомку значит передать их все разом. Канал
выдаёт отдельную капу контракта `Hardware`, которая открывает только полномочия
на устройства.

## Как написать процесс

Программа на стандартной библиотеке объявляет обычный `main`, а
freestanding-программа сама объявляет `_start` и `panic_handler`.

Компонент объявляет `component_manifest!` и запрашивает требования у родителя.

Новому процессу кроме кода нужны:

- линкер-скрипт: точка входа `_start`, базовый адрес образа (`0x00400000`),
  выравнивание секций `.text/.rodata/.data/.bss` на страницу, границы таблицы
  тестов в `.rodata` и незагружаемая секция `.component.manifest`.
  `userland_build::emit_linker_script()` из `build.rs` размещает скрипт в
  сборке;
- раздел `[package.metadata.userland]` с размером стека.

### Программа на стандартной библиотеке

Точка входа настраивает потоки стандартного вывода и вызывает `main`.
Программа без требований не объявляет манифест.

Программа с требованиями объявляет их `component_manifest!` из крейта
`components` и передаёт функцию `request` манифеста в
`components::requirements`. `main` возвращает отказ требования значением, и
`std` пишет его строкой `Error: ...` в журнал и завершает процесс кодом 1:

```rust
use components::{StartupError, component_manifest};
use rtc_abi::rtc;

component_manifest! {
    struct ClockStartup {
        requirements: { rtc: session(rtc::Protocol) },
    }
}

fn main() -> Result<(), StartupError> {
    let requirements = components::requirements(ClockStartup::request)?;
    println!("rtc reads {:?}", requirements.rtc.client().now());
    Ok(())
}
```

Программы-образцы лежат в `user/examples/`. Корень путей `std::fs` —
сессия требования `session(namespace::Protocol)`, которую программа один раз
передаёт в `std::os::molecular::install_filesystem_root`. Стеки потоков выделяются с
метеринг-ресурса процесса, и предел памяти компонента покрывает их наравне с кучей.

`std` хранит единственную копию платформенного состояния процесса и потоки
`stdout` и `stderr`, поэтому `println!` пишет строку прямо в журнал.

### Freestanding-программа

Программа сама объявляет свои `_start`, `panic_handler` и глобальный аллокатор
(`runtime::process_heap!`), а платформенный слой берёт из `lib/runtime`.
`_start` передаёт свой handle в `runtime::start_component` и функции `request`
из `component_manifest!` (образец — `driver-pl031` в `user/`):

```rust
#![no_std]
#![no_main]
#![allow(unsafe_code)]

runtime::process_heap!();

use component_startup::component_manifest;
use runtime::{log_line, process_exit, start_component};
use syscall::{Handle, kind};

const LOG_TAG: &str = "probe";
const FAILED_EXIT_CODE: u64 = 1;

component_manifest! {
    struct ProbeStartup {}
}

#[unsafe(no_mangle)]
pub extern "C" fn _start(parent: Handle<kind::Port>) -> ! {
    start_component(parent, LOG_TAG);
    if ProbeStartup::request(parent).is_err() {
        process_exit(FAILED_EXIT_CODE)
    }
    log_line("started");
    process_exit(0)
}

#[panic_handler]
fn panic(_info: &core::panic::PanicInfo<'_>) -> ! {
    process_exit(FAILED_EXIT_CODE)
}
```

Команды сборки образа и запуска — в [commands.md](commands.md), тесты — в
[testing.md](testing.md).
