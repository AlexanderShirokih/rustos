# Userland

Userspace-процесс содержит весь свой код и работает поверх syscall ABI ядра.
Система не поддерживает динамическую загрузку и разделяемые библиотеки. Код
программ лежит в `user/`, а упакованы они в один образ, который ядро получает от
загрузчика и из которого поднимает первый процесс.

## Образ

`userland.img` — плоский архив именованных блобов с одной таблицей. Программа не
отдельный вид записи. Это запись, содержимое которой начинается своей магией.

Состав образа задаёт TOML-манифест, путь к которому передаётся в `--image` (по
умолчанию `user/rootkeeper/image.toml`):

```toml
version = 1

[plan]
source = "user/rootkeeper/system.toml"

[stage1]
source = "user/rootkeeper/stage1.toml"

[[mount_tables]]
source = "user/rootkeeper/namespace.toml"

[[programs]]
package = "rootkeeper"
path = "/boot/rootkeeper"
boot = true

[[files]]
path = "/boot/rootkeeper/assets"
source = "user/rootkeeper/assets/**/*.txt"
```

`[[programs]]` и `[[files]]` различаются только тем, откуда инструмент берёт
байты: из собранного ELF пакета либо с диска. Запись файла лежит в каталоге
своей программы — образ не принимает записи вне каталогов. `boot = true` стоит
ровно у одной программы. Инструмент проставляет её запись в `boot_index`
заголовка образа; нет соглашения об имени пути.

Элемент `[[programs]]` объявляет идентичность программы и её размещение.
Инструмент берёт имя cargo bin-таргета из `cargo metadata`: единственный
bin-таргет пакета `package` либо таргет, названный ключом `bin`. Пакет с
несколькими bin-таргетами требует явного `bin`; манифест отвергает пакет без
bin-таргетов. По этому имени артефакт собирается и отыскивается. Идентичность
имеет две формы: квалифицированную `<package>::<bin>`, уникальную в пределах
образа, и краткую `<bin>`.

Размещение задаёт `path`. Запись образа ложится по объявленному пути и лежит
под его последним компонентом. Описания композиции называют программу
идентичностью ([rootkeeper.md](rootkeeper.md#план-загрузки)), которую сборка
разрешает в запись реестра: квалифицированную форму — всегда, краткую — пока её
объявил ровно один пакет образа. Неоднозначная краткая ссылка отвергается
перечислением этих пакетов. Компонент без ключа `name` зовётся той формой,
которой записана ссылка.

Секции `[plan]`, `[stage1]` и `[[mount_tables]]` называют host-описания,
которые инструмент проверяет, компилирует и размещает в образе обычными
записями: план ступени 0 ([rootkeeper.md](rootkeeper.md#план-загрузки)),
ступень 1 ([rootkeeper.md](rootkeeper.md#ступени-загрузки)) и дерево имён
файловой подсистемы ([filesystem.md](filesystem.md#дерево-имён-загрузки)).
Манифест отвергает ступень 1 и дерево имён без `[plan]`, потому что связывать
их слоты и разрешать имена экземпляров не с чем.

Манифест отвечает на вопрос, что лежит в образе, план — на вопрос, что и с
какими аргументами rootkeeper поднимает.

Источник без подстановок даёт одну запись по пути `path`; каталог сам по себе
не является источником. Источник с подстановкой делится по первому компоненту,
который её содержит: слева корень обхода, справа шаблон, а каждый принятый
файл ложится под `path` вместе со своим путём от корня обхода.

| Шаблон | Что принимает                                       |
|--------|-----------------------------------------------------|
| `?`    | один символ внутри компонента                       |
| `*`    | любую последовательность символов внутри компонента |
| `**`   | любую последовательность, разделители включая       |
| `**/`  | любую цепочку каталогов, в том числе пустую         |

Обход рекурсивен, а его порядок — по имени записи каталога, поэтому состав
образа не зависит от файловой системы сборки. Один путь, заполненный несколько
раз одним и тем же содержимым, даёт одну запись; тот же путь с разным
содержимым отвергает сборку. Флаг `--file path=source` добавляет файлы поверх
манифеста ([commands.md](commands.md#userland)).

Размер стека программы фиксируется в разделе `[package.metadata.userland]` её
`Cargo.toml`:

```toml
[package.metadata.userland]
stack_size = 65536
```

### Формат файла

Заголовок образа занимает 24 B, за ним идёт таблица записей, байты путей и
данные записей.

| Поле        | Смещение | Размер | Описание                                        |
|-------------|----------|--------|-------------------------------------------------|
| magic       | 0        | 8 B    | `USRLIMG\0`                                     |
| version     | 8        | u16 LE | версия формата (текущая: 1)                     |
| entry_count | 10       | u16 LE | число записей таблицы (>= 1)                    |
| boot_index  | 12       | u16 LE | запись, с которой ядро поднимает первый процесс |
| reserved    | 14       | u16 LE | ноль                                            |
| total_size  | 16       | u64 LE | полный размер файла в байтах                    |

Запись таблицы занимает 28 B:

| Поле        | Смещение | Размер | Описание                                     |
|-------------|----------|--------|----------------------------------------------|
| path_offset | 0        | u64 LE | смещение байт пути в файле                   |
| path_len    | 8        | u16 LE | длина пути (UTF-8, без нуля)                 |
| alias_of    | 10       | u16 LE | номер записи, чьё окно повторено, плюс один  |
| data_offset | 12       | u64 LE | смещение данных, кратно `USERLAND_PAGE_SIZE` |
| data_size   | 20       | u64 LE | длина данных в байтах                        |

Записи отсортированы строго по возрастанию пути, поэтому на этом стоит
двоичный поиск, а строгость порядка запрещает дубликаты. Путь — непустой ASCII
не длиннее `USERLAND_ENTRY_PATH_CAPACITY` (255 байт), оканчивающийся непустым
компонентом.

Нулевой `alias_of` означает собственное окно данных. Такие окна лежат в
порядке таблицы и не пересекаются. Ненулевой объявляет запись повтором окна
более ранней записи — одинаковое содержимое хранится в образе один раз.

### Формат программы

Заголовок программы (32 B) и дескрипторы сегментов занимают первую страницу
записи — отсюда предел в 101 сегмент на программу. Данные сегментов начинаются
со смещения `USERLAND_PAGE_SIZE` внутри записи и выровнены на него.

| Поле          | Смещение | Размер | Описание                  |
|---------------|----------|--------|---------------------------|
| magic         | 0        | 8 B    | `USRPROG\0`               |
| entry_va      | 8        | u64 LE | точка входа в VA процесса |
| stack_size    | 16       | u64 LE | размер стека в байтах     |
| segment_count | 24       | u16 LE | число сегментов           |
| reserved      | 26       | 6 B    | ноль                      |

Дескриптор сегмента занимает 40 B; сегменты и их `va_base` выровнены на страницу
(`USERLAND_PAGE_SIZE = 4096`).

| Поле        | Смещение | Размер | Описание                                      |
|-------------|----------|--------|-----------------------------------------------|
| file_offset | 0        | u64 LE | смещение данных сегмента от начала записи     |
| file_size   | 8        | u64 LE | размер данных в файле                         |
| va_base     | 16       | u64 LE | базовый VA в адресном пространстве процесса   |
| mem_size    | 24       | u64 LE | размер в памяти (>= file_size; разница — BSS) |
| flags       | 32       | u32 LE | права: 0=RW, 1=RO, 2=RX                       |
| reserved    | 36       | u32 LE | ноль                                          |

Инструмент сборки читает ELF каждой программы и раскладывает её
`PT_LOAD`-сегменты в содержимое записи.

## Жизненный цикл

После инициализации ядро берёт запись по `boot_index`, разбирает её содержимое
как программу, создаёт bootstrap-порт и корневой `Resource`, раскладывает
сегменты в новое адресное пространство и стартует первый поток. Имя процесса —
последний компонент пути его записи (`/boot/filesystem-ramfs` →
`filesystem-ramfs`), не длиннее 64 байт.

Точка входа процесса — `_start`, которой raw HandleId начальной capability
приходит в регистре `x0`:

```rust
#[unsafe(no_mangle)]
pub extern "C" fn _start(startup: Handle) -> ! { /* ... */ }
```

Для первого процесса начальная capability — bootstrap-порт ядра. Низкоуровневый
`userland_loader::load_entry` позволяет userspace-загрузчику передать дочернему
процессу произвольный хэндл.

### Startup-порт дочернего процесса

`userland_loader::launch_entry` выполняет стандартный запуск дочернего
приложения: загрузчик создаёт `Port` без значка, серверную сторону передаёт
процессу в `x0`, а клиентскую передаёт callback'у для одного кадра прикладного
типизированного IPC-контракта:

```rust
let process = launch_entry(&program, None, &resource, |startup| -> Result<()> {
    driver_args::Client::new(PortTransport::client(startup.handle()))
        .provide(device, service)?;
    Ok(())
})?;
```

Ошибка callback'а завершает потомка через `ProcessTerminate` и освобождает его
таблицу хэндлов и metering-бюджет; отказ самого cleanup заменяет исходную
ошибку, чтобы вызывающий не получил ложного подтверждения отката.

Одноразовый получатель принимает кадр через `runtime::receive_startup` — функция
закрывает серверную сторону startup-порта после диспетчеризации:

```rust
let DriverState { device, service } =
    receive_startup(startup, driver_args::dispatch)?.ok_or(Error::Start)?;
```

Тип аргументов и владение передаваемыми capability остаются частью прикладного
IPC-контракта. Если тот же порт после стартового кадра содержит admin-команды,
`launch_entry_retained` возвращает `InitializedProcess` с полями `process` и
`startup`; порт обслуживают обычным `PortTransport`, а клиентская сторона такого
порта минтится под значком, поэтому исчезновение поднявшего процесса приходит
потомку как `SenderGone` ([port.md](port.md#уход-значка)).

Процесс называет второй аргумент, а `None` берёт имя самой записи. Запись с
программой лежит в каталоге компонента под именем `program`, поэтому
вызывающий, который поднимает компонент, берёт имя каталога через
`component_name`.

### Стартовая транзакция компонента

Компонент композиции принимает не один стартовый кадр, а транзакцию: сначала
базовый кадр с его лог-сессией и серверными сторонами control- и service-портов,
следом — capability слотов в порядке объявления
([rootkeeper.md](rootkeeper.md#связывание)). Слоты передаются отдельными кадрами
того же одноразового startup-порта, потому что кадр IPC содержит не больше
`MESSAGE_MAX_HANDLES` капабилити, и базовый кадр занимает их полностью.

Контракт транзакции находится в `lib/component-abi`, её приёмник — в
`lib/component-client`. Общий loader не задаёт срок прикладному callback:
конечный send timeout и подтверждение возврата бюджета — контракт managed startup
([rootkeeper.md](rootkeeper.md#managed-startup)).

### Манифест компонента

Компонент объявляет свои связи в коде — макросом `component_manifest!` из
`lib/component-client`. Объявление одно на обе формы программы и называет слоты
по порядку транзакции: имя, вид и то, чем композиция наполняет слот — семейство
совместимостей у устройства, имя протокола у импорта.

| Ключ                   | Что объявляет                                              |
|------------------------|------------------------------------------------------------|
| `slots`                | слоты по порядку приёма                                    |
| `exports`              | протокол, который компонент обслуживает на service-порту   |
| `controls`             | протокол, который компонент обслуживает на control-порту   |
| `establishes_sessions` | сессии своего service-порта компонент сам создаёт          |

Порты разные, поэтому `exports` и `controls` объявляются порознь. Один порт
содержит один протокол, поэтому сборка отвергает `controls` вместе с
`establishes_sessions`, а установление сессий без `exports` отвергает как
бессмысленное.

Импорт протокола принимает необязательный `instance` — имя
экземпляра-провайдера; без него сборка ищет единственного провайдера в
композиции ([rootkeeper.md](rootkeeper.md#связывание)). Слот-каталог называет
`instance` обязательно, потому что у него нет протокола, а композиция содержит
несколько провайдеров сессий. Компонент не выбирает имя своего каталога — его
берёт композиция из записи его программы.

```rust
component_manifest! {
    struct ImageFileSystemStartup {
        exports: "FileSystem",
        establishes_sessions: true,
        slots: { image: userland },
    }
}

component_manifest! {
    struct RtcStartup {
        slots: {
            line: irq(compatible = ["arm,pl031"]),
            window: mmio(compatible = ["arm,pl031"]),
        },
    }
}

component_manifest! {
    struct FileReaderStartup {
        slots: { files: service(protocol = "FileSystem", instance = "ramfs") },
    }
}
```

Список совместимостей — заявка драйвера на семейство устройств. Подходит любая
из строк, а выбор между ними принадлежит описанию платформы конкретной машины.
Номер ресурса (`resource`, по умолчанию `0`) выбирает линию либо окно среди
ресурсов устройства — это знание драйвера о железе, а не решение композиции.

Из одного объявления берутся приёмник и манифест. Приёмник — структура с полями
`control`, `service` и названными слотами; её `receive` принимает транзакцию
целиком, отдаёт лог-сессию вместе с этой структурой и отвергает транзакцию,
объявлению не отвечающую. Каждое поле владеет своей capability, и отвергнутая
транзакция закрывает всё, что успела доставить. Манифест — артефакт сборки,
запись в секции `.component.manifest` собранной программы. Сборщик читает её из
ELF каждой программы, на которую ссылается план, и по ней строит слоты
компонента. Секция необязательна — программа без неё
объявляет пустое.

Заголовок манифеста занимает 16 B, за ним идут имя протокола service-порта, имя
протокола control-порта и записи слотов по порядку приёма:

| Поле        | Смещение | Размер | Описание                                             |
|-------------|----------|--------|------------------------------------------------------|
| magic       | 0        | 8 B    | `CMPMFST\0`                                          |
| version     | 8        | u16 LE | версия формата (текущая: 1)                          |
| slot_count  | 10       | u16 LE | число слотов                                         |
| export_len  | 12       | u8     | длина протокола service-порта; ноль — без экспорта   |
| flags       | 13       | u8     | бит 0: компонент сам создаёт сессии                  |
| control_len | 14       | u8     | длина протокола control-порта; ноль — без объявления |
| reserved    | 15       | 1 B    | ноль                                                 |

Заголовок слота занимает 4 B, за ним идут его имена — длина `u8` и байты
каждого:

| Поле       | Смещение | Размер | Описание                                                                   |
|------------|----------|--------|----------------------------------------------------------------------------|
| kind       | 0        | u8     | 0 userland, 1 irq, 2 mmio, 3 service, 4 directory, 5 supervisor, 6 control |
| resource   | 1        | u16 LE | номер ресурса устройства                                                   |
| name_count | 3        | u8     | число имён слота                                                           |

У устройства имена — строки совместимости (хотя бы одна), у импорта протокола —
его имя и за ним необязательное имя экземпляра, у каталога — имя
экземпляра-провайдера; у `userland` и `supervisor` нет имён.

## Контракт Bootstrap

Bootstrap — типизированный канал между корневым процессом и ядром, определённый
в `lib/bootstrap-abi`. Через него корневой процесс запрашивает корневые
capability. Капа канала остаётся у него, потому что она открывает весь набор
корневых полномочий сразу, и её передача потомку равнозначна передаче их всех.

Boot FDT канал выдаёт регионом поверх страниц с блобом. Загрузчик размещает
блоб по произвольному адресу, не обязательно с начала страницы, поэтому вместе
с капой региона контракт отдаёт смещение первого байта блоба от её начала.

## Журнал

Процесс шлёт строки в системный журнал по контракту `Log` из `lib/log-abi`.
Relay из `lib/log-relay` в корневом процессе служит сервером контракта. Он
пересылает принятые строки ядру по bootstrap-каналу. Лог-сессии его порта
достаются потомкам. Процесс отдаёт свою лог-капу платформенному слою через
`runtime::install_log` вместе с тегом своих строк и дальше пишет их через
`log_line` и `log_fmt`. Программа на стандартной библиотеке не устанавливает
лог-сессию: точка входа забирает её, а значок сессии даёт такой программе тег.

## Часы

Монотонные часы процесса — `runtime::Instant`. Они не требуют syscall, потому
что ядро открывает EL0 архитектурный счётчик времени и его частоту, а
платформенный слой переводит тики в наносекунды. Процесс по-прежнему не может
программировать таймер.

Точка отсчёта у часов общая с дедлайнами `timeout_ns` блокирующих вызовов,
поэтому разность двух замеров сравнима с переданным тайм-аутом.

## Как написать процесс

Программа образа существует в двух формах. На стандартной библиотеке пишутся
компоненты композиции. Платформенный слой отдаёт им точку входа и приём
стартового набора. Freestanding-форма — свои `_start` и `panic_handler` без
`main` — обслуживает запуск мимо стартовой транзакции компонента: корневой
процесс, `testrunner` и его фикстуры.

Что нужно новому процессу в обеих формах помимо кода:

- линкер-скрипт: точка входа `_start`, базовый адрес образа (`0x00400000`),
  выравнивание секций `.text/.rodata/.data/.bss` на страницу, границы таблицы
  тестов в `.rodata` и незагружаемая секция `.component.manifest`.
  `userland_build::emit_linker_script()` из `build.rs` размещает скрипт в
  сборке;
- раздел `[package.metadata.userland]` с размером стека;
- членство в workspace `user/`;
- включение пакета в TOML-манифест образа с путём записи.

### Программа на стандартной библиотеке

Точка входа вызывает `main` и оставляет программе стартовый handle. Компонент
сам принимает стартовую транзакцию — тем же объявлением, каким её создаёт
freestanding-программа. Приём обязателен и компоненту без слотов, потому что он
закрывает стартовое рандеву композиции и приносит лог-сессию, по которой идут
`stdout` и `stderr`.

`component_client_std::receive` забирает handle и отдаёт программе принятые
ресурсы. Вызов идёт первым действием `main`: до лог-сессии вывод не доходит до
журнала, и программа называет отказ приёма кодом выхода:

```rust
component_client::component_manifest! {
    struct ClockStartup {
        slots: { rtc: service(protocol = "Rtc") },
    }
}

let Ok(startup) = component_client_std::receive(ClockStartup::receive) else {
    process::exit(NO_STARTUP_EXIT_CODE);
};
let clock = rtc::Client::new(PortTransport::client(&startup.rtc));
println!("rtc reads {}", clock.now()?);
```

Образцы — `hello-std` и `clock-std` в `user/`. Программа берёт стеки потоков из
своей кучи, и предел памяти компонента покрывает их наравне с ней. Отсюда же
граница. Копия внутри `std` держит платформенное состояние процесса, а
программа берёт крейты без состояния зависимостями — объекты ядра и обёртки
вызовов ([workspace.md](workspace.md#один-рантайм-в-процессе)). `std` держит
потоки `stdout` и `stderr`, и строка идёт в журнал `println!`.

### Freestanding-программа

Программа сама объявляет свои `_start`, `panic_handler` и глобальный аллокатор
(`runtime::process_heap!`), а платформенный слой берёт из `lib/runtime`. Она
принимает стартовую транзакцию компонента тем же приёмником из своего
`component_manifest!` (`driver-pl031` в `user/`), передавая ему handle из
`_start` и отдавая лог-сессию своей копии платформенного слоя; низкоуровневый
`load_entry` размещает ей в `x0` одну начальную capability:

```rust
#![no_std]
#![no_main]

use runtime::{PortTransport, thread_exit};
use syscall::Handle;

runtime::process_heap!();

#[unsafe(no_mangle)]
pub extern "C" fn _start(log: Handle) -> ! {
    let client = log_abi::log::Client::new(PortTransport::client(log));
    let result = client.write_str("init", "process started");

    thread_exit(u64::from(result.is_err()))
}

#[panic_handler]
fn panic(_info: &core::panic::PanicInfo<'_>) -> ! {
    loop { core::hint::spin_loop() }
}
```

[testing.md](testing.md).
