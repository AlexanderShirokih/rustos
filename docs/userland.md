# Userland

Userland — init radmisk контейнер, который принимает управление от ядра и начинает инициализацию всей userspace-системы.
Userspace-процесс — freestanding-бинарь, который несёт весь свой код и работает
поверх syscall ABI ядра. С ядром он общается через системные вызовы. Код программ userland лежит в `user/`.

## Состав

Userspace опирается на несколько крейтов из `lib/`:

| Крейт                | Роль                                                           |
|----------------------|----------------------------------------------------------------|
| `lib/runtime`        | svc-обёртки syscall ABI; глобальная куча; транспорты IPC; sync |
| `lib/ipc`            | кодек кадров и типы контрактов поверх транспортов              |
| `lib/userland`       | модель образа: сегменты, права, точка входа, валидация         |
| `lib/userland-image` | бинарный формат `userland.img` (encode/decode)                 |
| `lib/bootstrap-abi`  | контракт `Bootstrap` — канал корневого процесса к ядру         |
| `lib/component-abi`  | контракт `ComponentStartup` и манифест компонента композиции   |
| `lib/device-resolver`| описание платформы: селектор устройства - линии и MMIO-окна    |
| `lib/device-resolver-aarch64` | биндинги контроллеров прерываний платформы           |
| `lib/managed-component` | примитив managed-запуска: экземпляр, резерв бюджета, роли   |
| `lib/log-abi`        | контракт `Log` — запись строки в системный журнал              |
| `lib/log-relay`      | лог-порт и его relay: пересылка строк доверенному стоку        |

## Образ

Userland упакован в один бинарный образ `userland.img` — плоский архив
именованных блобов с одной таблицей. Ядро получает его как blob и из него
поднимает первый процесс. Программа не отдельный вид записи: это запись,
содержимое которой начинается своей магией.

### Структура файла

| Поле        | Смещение | Размер | Описание                                        |
|-------------|----------|--------|-------------------------------------------------|
| magic       | 0        | 8 B    | `USRLIMG\0`                                     |
| version     | 8        | u16 LE | версия формата (текущая: 1)                     |
| entry_count | 10       | u16 LE | число записей таблицы (>= 1)                    |
| boot_index  | 12       | u16 LE | запись, с которой ядро поднимает первый процесс |
| reserved    | 14       | u16 LE | ноль                                            |
| total_size  | 16       | u64 LE | полный размер файла в байтах                    |

За заголовком (24 B) идёт таблица записей, за ней байты путей, затем данные
записей.

### Запись таблицы

| Поле        | Смещение | Размер | Описание                                     |
|-------------|----------|--------|----------------------------------------------|
| path_offset | 0        | u64 LE | смещение байт пути в файле                   |
| path_len    | 8        | u16 LE | длина пути (UTF-8, без нуля)                 |
| alias_of    | 10       | u16 LE | номер записи, чьё окно повторено, плюс один  |
| data_offset | 12       | u64 LE | смещение данных, кратно `USERLAND_PAGE_SIZE` |
| data_size   | 20       | u64 LE | длина данных в байтах                        |

Запись таблицы занимает 28 B. Записи отсортированы строго по возрастанию пути:
на этом стоит двоичный поиск, а строгость порядка запрещает дубликаты путей.

Путь — непустой ASCII не длиннее `USERLAND_ENTRY_PATH_CAPACITY` (255 байт),
оканчивающийся непустым компонентом.

Нулевой `alias_of` означает собственное окно данных: такие окна лежат в порядке
таблицы и не пересекаются. Ненулевой `alias_of` объявляет запись повтором окна
более ранней записи с собственным окном — одинаковое содержимое хранится в
образе один раз. Границы повтора совпадают с границами повторяемого окна; любое
расхождение образ отвергает.

### Содержимое программы

| Поле          | Смещение | Размер | Описание                  |
|---------------|----------|--------|---------------------------|
| magic         | 0        | 8 B    | `USRPROG\0`               |
| entry_va      | 8        | u64 LE | точка входа в VA процесса |
| stack_size    | 16       | u64 LE | размер стека в байтах     |
| segment_count | 24       | u16 LE | число сегментов           |
| reserved      | 26       | 6 B    | ноль                      |

Заголовок программы (32 B) и дескрипторы сегментов занимают первую страницу
записи — отсюда предел в 101 сегмент на программу. Данные сегментов начинаются
со смещения `USERLAND_PAGE_SIZE` внутри записи и выровнены на него.

### Сегмент

| Поле        | Смещение | Размер | Описание                                      |
|-------------|----------|--------|-----------------------------------------------|
| file_offset | 0        | u64 LE | смещение данных сегмента от начала записи     |
| file_size   | 8        | u64 LE | размер данных в файле                         |
| va_base     | 16       | u64 LE | базовый VA в адресном пространстве процесса   |
| mem_size    | 24       | u64 LE | размер в памяти (>= file_size; разница — BSS) |
| flags       | 32       | u32 LE | права: 0=RW, 1=RO, 2=RX                       |
| reserved    | 36       | u32 LE | ноль                                          |

Дескриптор сегмента занимает 40 B. Сегменты и их `va_base` выровнены на
страницу (`USERLAND_PAGE_SIZE = 4096`).

Инструмент сборки читает ELF каждой программы, раскладывает её `PT_LOAD`-сегменты
в содержимое записи и склеивает записи в `userland.img`. Состав образа задаёт
TOML-манифест, путь к которому передаётся в `--image` (по умолчанию
`user/rootkeeper/image.toml`):

```toml
version = 1

[plan]
source = "user/rootkeeper/system.toml"

[[programs]]
package = "rootkeeper"
path = "/boot/rootkeeper"
boot = true

[[files]]
path = "/boot/rootkeeper/sample"
source = "user/rootkeeper/sample.txt"

[[files]]
path = "/boot/rootkeeper/assets"
source = "user/rootkeeper/assets/**/*.txt"
```

`[[programs]]` и `[[files]]` различаются только тем, откуда инструмент берёт
байты: из собранного ELF пакета либо с диска. Запись файла лежит в каталоге своей
программы: записи вне каталогов образ не принимает. `boot = true` стоит ровно у
одной программы: её запись инструмент и проставляет в `boot_index` заголовка
образа, соглашения об имени пути нет.

Секция `[plan]` называет host-side описание загрузочной композиции, а повторяемая
`[[mount_tables]]` — описания деревьев имён файловой подсистемы, которые читает
маршрутизатор. Инструмент проверяет их, компилирует и кладёт в образ обычными
записями. Ключ `source` — путь TOML от корня проекта. Путь записи в образе у плана
задаёт необязательный `path` со значением `/boot/rootkeeper/plan` по умолчанию, а
дерево имён ложится по своему известному пути, и выбора у манифеста нет.

```toml
[plan]
source = "user/rootkeeper/system.toml"

[[mount_tables]]
source = "user/rootkeeper/namespace.toml"
```

Манифест отвечает на вопрос, что лежит в образе, план — на вопрос, что и с какими
аргументами поднимает rootkeeper ([rootkeeper.md](rootkeeper.md#план-загрузки)), а
дерево имён принадлежит файловой подсистеме
([filesystem.md](filesystem.md#дерево-имён-загрузки)).

Источник без подстановок — файл, дающий одну запись по пути `path`. Каталог сам
по себе источником не является: его файлы отбирает подстановка.

Источник с подстановкой делится по первому компоненту, её содержащему: слева
корень обхода, справа шаблон. Каждый принятый шаблоном файл ложится под `path`
вместе со своим путём от корня обхода. Обход рекурсивен, а его порядок — по
имени записи каталога, поэтому состав образа не зависит от файловой системы
сборки. Пустой каталог записей не даёт: дерево образа выводится из путей, и
каталога без файлов в нём нет. Записи каталога, кроме файлов и подкаталогов,
сборку отвергают.

| Шаблон | Что принимает                                          |
|--------|--------------------------------------------------------|
| `?`    | один символ внутри компонента                          |
| `*`    | любую последовательность символов внутри компонента    |
| `**`   | любую последовательность, разделители включая          |
| `**/`  | любую цепочку каталогов, в том числе пустую            |

Отсюда `assets/*` берёт файлы самого каталога, `assets/**` — всё его дерево, а
`assets/**/*.txt` — файлы дерева с нужным расширением.

Файлы поверх манифеста добавляет флаг `--file path=source`, повторяемый по числу
файлов ([commands.md](commands.md#userland)). Источник ему задаётся по тем же
правилам, подстановки включая.

Один путь, заполненный несколько раз одним и тем же содержимым, даёт одну
запись: перекрытие шаблона с отдельным `[[files]]` или `--file` ошибкой не
является. Тот же путь с разным содержимым сборку отвергает.

Размер стека программы фиксируется в разделе `[package.metadata.userland]` её
`Cargo.toml`:

```toml
[package.metadata.userland]
stack_size = 65536
```

## Жизненный цикл

После инициализации ядро читает blob `userland.img`, берёт запись по `boot_index` и разбирает её содержимое как
программу, создаёт bootstrap-порт, корневой `Resource` capability, раскладывает сегменты в новое адресное
пространство и стартует первый поток.
Имя процесса — последний компонент пути его записи (`/boot/filesystem-ramfs` →
`filesystem-ramfs`), не длиннее предела имени процесса (64 байта); превышение — отказ
запуска. То же имя выводит и userspace-загрузчик, спавня программу из образа.

Точка входа процесса — `_start`, которой в регистре `x0` приходит raw HandleId
начальной capability:

```rust
#[unsafe(no_mangle)]
pub extern "C" fn _start(startup: Handle) -> ! { /* ... */ }
```

Для первого процесса начальная capability — bootstrap-порт ядра. Низкоуровневый
`userland_loader::load_entry` позволяет userspace-загрузчику передать дочернему
процессу произвольный хэндл.

### Startup-порт дочернего процесса

Стандартный запуск дочернего приложения выполняет
`userland_loader::launch_entry`: загрузчик создаёт `Port` без значка, серверную
сторону передаёт процессу в `x0`, а клиентскую передаёт callback'у для одного
кадра прикладного типизированного IPC-контракта:

```rust
let process = launch_entry(&program, None, &resource, |startup| -> Result<()> {
    driver_args::Client::new(PortTransport::client(startup.handle()))
        .provide(device, service)?;
    Ok(())
})?;
```

Если callback возвращает ошибку, `launch_entry` завершает потомка через
`ProcessTerminate` и ждёт его с конечным сроком. Это освобождает его таблицу
хэндлов и metering-бюджет. Отказ самого cleanup заменяет исходную ошибку
callback: вызывающий не получает ложного подтверждения отката. После успешной
отправки `launch_entry` закрывает startup-порт и возвращает `Process`.

Одноразовый получатель принимает этот кадр через `runtime::receive_startup`.
Функция закрывает серверную сторону startup-порта после диспетчеризации:

```rust
let DriverState { device, service } =
    receive_startup(startup, driver_args::dispatch)?.ok_or(Error::Start)?;
```

Тип аргументов и владение передаваемыми capability остаются частью прикладного
IPC-контракта. Если тот же порт после стартового кадра несёт admin-команды,
`launch_entry_retained` после успешной отправки возвращает `InitializedProcess`
с полями `process` и `startup`; порт обслуживают обычным `PortTransport`.
Клиентская сторона такого порта минтится под значком, поэтому исчезновение
поднявшего процесса приходит потомку как `SenderGone` очередным приёмом
([port.md](port.md#уход-значка)). Значка без множества отправителей аргумент не
принимает: он типизирован `NonZeroU64`, а «без значка» выражается отсутствием
значения.

Процесс называет второй аргумент, а `None` берёт имя самой записи. Запись с
программой лежит в каталоге компонента под именем `program`, поэтому вызывающий,
который поднимает компонент, берёт имя каталога: его даёт `component_name`. Имя
экземпляра композиции приходит планом
([rootkeeper.md](rootkeeper.md#план-загрузки)).

`load_entry` остаётся низкоуровневым путём для программ с произвольной начальной
capability.

### Стартовая транзакция компонента

Компонент композиции принимает не один стартовый кадр, а транзакцию: сначала
базовый кадр с его лог-сессией и серверными сторонами control- и service-портов,
следом — capability слотов в порядке объявления
([rootkeeper.md](rootkeeper.md#связывание)). Слоты едут отдельными кадрами того же
одноразового startup-порта: кадр IPC несёт не больше `MESSAGE_MAX_HANDLES`
капабилити, и базовый кадр занимает их полностью.

Слот `userland` явно выдаёт read-only регион образа тем компонентам, которым нужен контейнер записей
([filesystem.md](filesystem.md#дерево-имён-загрузки)). Контракт транзакции и её
приёмник живут в `lib/component-abi`.

### Манифест компонента

Свои связи компонент объявляет в коде — макросом `component_manifest!` из
`lib/component-abi`. Объявление называет слоты по порядку транзакции: имя, вид
(`userland`, `irq`, `mmio`, `service`, `directory`, `supervisor`) и то, чем композиция слот
наполняет — семейство совместимостей у устройства, имя протокола у сервиса. Ключ
`exports` называет протокол, который компонент обслуживает на своём
service-порту.

```rust
component_manifest! {
    struct ImageFileSystemStartup {
        slots: { image: userland },
    }
}

component_manifest! {
    struct RtcStartup {
        slots: {
            line: irq(compatible = ["arm,pl031"]),
            window: mmio(compatible = ["arm,pl031"]),
        },
    }
}
```

Список совместимостей — заявка драйвера на семейство устройств: подходит любая
из строк, а выбор между ними принадлежит описанию платформы конкретной машины.
Номер ресурса (`resource`, по умолчанию `0`) выбирает линию либо окно среди
ресурсов устройства — это знание драйвера о железе, а не решение композиции.

Каталог аргумента не принимает: имя своего каталога компонент не выбирает. Слот
выдаёт сессию файловой системы с этим каталогом в роли корня: по ней компонент
открывает свои записи по именам, известным его коду, и листает свой корень, а
наружу из каталога не выходит - `..` отвергают правила пути
([rootkeeper.md](rootkeeper.md#связывание)).

Из одного объявления берутся приёмник и манифест. Приёмник — структура с
полями `log`, `control`, `service` и названными слотами; её `receive`
принимает транзакцию целиком поверх
`receive_startup_transaction` и отвергает ту, что объявлению не отвечает.
Манифест — запись в секции `.component.manifest` собранной программы.

| Поле       | Смещение | Размер | Описание                          |
|------------|----------|--------|-----------------------------------|
| magic      | 0        | 8 B    | `CMPMFST\0`                       |
| version    | 8        | u16 LE | версия формата (текущая: 2)       |
| slot_count | 10       | u16 LE | число слотов                      |
| export_len | 12       | u8     | длина имени протокола; ноль - без экспорта |
| reserved   | 13       | 3 B    | ноль                              |

За заголовком (16 B) идёт имя экспортируемого протокола, за ним — записи слотов
по порядку приёма:

| Поле       | Смещение | Размер | Описание                          |
|------------|----------|--------|-----------------------------------|
| kind       | 0        | u8     | 0 userland, 1 irq, 2 mmio, 3 service, 4 directory, 5 supervisor |
| resource   | 1        | u16 LE | номер ресурса устройства          |
| name_count | 3        | u8     | число имён слота                  |

За заголовком слота (4 B) идут его имена: длина `u8` и байты каждого. У
устройства это строки совместимости (хотя бы одна), у сервиса — имя протокола
(ровно одно); у userland-образа, supervisor и каталога `name_count` равен нулю.

Манифест — артефакт сборки, а не запись образа: секция не отображается в
адресное пространство процесса и в `userland.img` не попадает. Сборщик образа
читает её из ELF каждой программы, на которую ссылается план, и по ней строит
слоты компонента: устройство переносится в план набором совместимостей, а
импортированный протокол связывается с единственным его экспортёром в
композиции ([rootkeeper.md](rootkeeper.md#связывание)). Программа плана без этой
секции ломает сборку.

Срок прикладному callback общий loader не задаёт: конечный send timeout и
подтверждение возврата бюджета — контракт managed startup
([rootkeeper.md](rootkeeper.md#managed-startup)).

Подробности Resource-модели — в [architecture.md](architecture.md) и
[syscalls.md](syscalls.md).

## Контракт Bootstrap

Bootstrap — типизированный канал между bootstrap-процессом и ядром. Контракт определён в `lib/bootstrap-abi`.
Через него корневой процесс запрашивает корневые capability.

Капа этого канала остаётся у корневого процесса: она открывает весь набор корневых полномочий сразу, и её
передача потомку равнозначна передаче их всех.

## Журнал

Строки в системный журнал процесс шлёт по контракту `Log` из `lib/log-abi`. Сервером контракта служит relay из
`lib/log-relay` в корневом процессе: он пересылает принятые строки ядру по bootstrap-каналу. Потомкам достаются
лог-сессии его порта, сам bootstrap-канал остаётся у корневого процесса. Свою лог-капу процесс отдаёт рантайму
через `runtime::install_log` и дальше пишет строки через `log_line` и `log_fmt`.

## Часы

Монотонные часы процесса — `runtime::Instant`. Syscall они не требуют: ядро открывает EL0 архитектурный
счётчик времени и его частоту, а рантайм переводит тики в наносекунды. Программировать таймер процесс
по-прежнему не может.

Точка отсчёта у часов общая с дедлайнами `timeout_ns` блокирующих вызовов, поэтому разность двух замеров
сравнима с переданным тайм-аутом.

## Как написать процесс

Программа userland — бинарь без стандартной библиотеки и без `main`, с
собственными `_start` и `panic_handler`.

```rust
#![no_std]
#![no_main]

use runtime::{PortTransport, thread_exit};
use syscall::Handle;

#[unsafe(no_mangle)]
pub extern "C" fn _start(log: Handle) -> ! {
    let client = log_abi::log::Client::new(PortTransport::client(log));
    let result = client.write_str("init", "process started");

    thread_exit(u64::from(result.is_err()))
}

#[panic_handler]
fn panic(_info: &core::panic::PanicInfo<'_>) -> ! {
    loop { core::hint::spin_loop() }
}
```

Что нужно новому процессу помимо кода:

- линкер-скрипт: точка входа `_start`, базовый адрес образа (`0x00400000`),
  выравнивание секций `.text/.rodata/.data/.bss` на страницу (4 KiB), границы
  таблицы тестов в `.rodata` и незагружаемая секция `.component.manifest`. Скрипт
  кладёт в сборку `userland_build::emit_linker_script()` из `build.rs`;
- раздел `[package.metadata.userland]` с размером стека (`stack_size`);
- членство в workspace `user/`;
- включение пакета в TOML-манифест образа с путём записи в образе.

### Программа на стандартной библиотеке

Программе на `std` точка входа и приём стартового набора capability достаются от
платформенного слоя: `_start` принимает набор до `main` и оставляет от него
лог-сессию. Поэтому исходник такой программы — обычный `fn main`, а `println!`
уходит в системный журнал под именем компонента:

```rust
fn main() {
    println!("hello");
}
```

Собирается она так же, как остальные программы образа, и объявляет то же самое —
кроме кода: `hello-std` в `user/` служит образцом.

#### Свой манифест и стартовый набор

Программа без секции манифеста объявляет пустое: ни слотов, ни экспорта. Свой
манифест она кладёт формой `component_manifest!` без структуры — приёмник
транзакции программе на `std` не нужен, набор она получает от платформенного
слоя:

```rust
component_abi::component_manifest! {
    slots: { rtc: service(protocol = "Rtc") },
}
```

Набор выдаёт модуль `std::os::molecular`: серверные стороны control- и
service-портов и слоты в порядке объявления. Capability названы сырым
идентификатором, а типы контрактов приходят программе её собственными
зависимостями ([architecture.md](architecture.md#таргеты-сборки)). Программа
надевает на идентификатор свои обёртки:

```rust
let startup = std::os::molecular::startup().expect("composition startup set");
let session = startup.slots().next().expect("the Rtc session slot");
let clock = rtc::Client::new(PortTransport::client(Handle::from_nonzero(session)));
println!("rtc reads {}", clock.now()?);
```

Рабочий пример — `clock-std` в `user/`. Отсюда же следует граница: состояние
`molecular-rt`, взятого программой в зависимости, — своё, не то, что внутри
`std`. Лог-сессия живёт в копии `std`, и строка в журнал идёт `println!`, а не
`molecular_rt::log`.

## Тесты

Интеграционные тесты ядра выполняются двумя проходами.

Первый проход — kernel-сторона: ядро собирается с фичей `kernel-tests`, тесты выполняются в пространстве ядра.

Второй проход — userspace-сторона: собирается `testrunner` как обычный userland-контейнер (`user/testrunner/image.toml`),
и те же `#[kernel_test]`-функции прогоняются в userspace. `testrunner` — корневой процесс прохода: он
устанавливает writer, шлющий лог через `Bootstrap` в ядро, и exit-делегат, а поднимаемым процессам выдаёт
лог-сессии своего relay.

Выбор прохода для нового теста — в [code-style.md](code-style.md).

Образ `testrunner` включает, в частности, следующие программы-фикстуры,
спавнимые тестами как отдельные процессы:

| Программа            | Назначение                                                                         |
|----------------------|------------------------------------------------------------------------------------|
| `spawn-fixture`      | минимальный потомок: закрывает стартовый хэндл и выходит его кодом                 |
| `startup-fixture`    | принимает стандартный типизированный startup-кадр и проверяет его значение         |
| `port-fixture`       | обслуживает запрос-ответ по bootstrap-порту: слот в `.bss`, маппинг чужого региона |
| `log-client-fixture` | пробует полномочия bootstrap-контракта по выданной ей лог-капе                     |

```rust
#[kernel_test]
fn userland_smoke() {
    let sum: u64 = (1..=10).sum();
    kernel_tests::kassert_eq!(sum, 55);
    kernel_tests::kassert!(sum.is_multiple_of(5));
}
```
