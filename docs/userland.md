# Userland

Userland — все процессы, работающие вне ядра: драйверы, сервисы и прикладной
код. Каждый процесс изолирован собственным адресным пространством и обладает
ровно теми полномочиями, чьи хэндлы получил при старте или принял по каналу.
Ядро предоставляет только механизмы (потоки, память, порты, сигналы, хэндлы);
поведение системы определяют userspace-процессы, взаимодействующие через
каналы.

Userspace-процесс — freestanding-бинарь: он несёт весь свой код и работает
поверх syscall ABI ядра. С ядром он общается через syscall. Программы
userland лежат в `user/`.

## Состав

Userspace опирается на несколько крейтов из `lib/`:

| Крейт                | Роль                                                           |
|----------------------|----------------------------------------------------------------|
| `lib/runtime`        | svc-обёртки syscall ABI; глобальная куча; транспорты IPC; sync |
| `lib/syscall`        | wire-типы ABI: номера операций, коды ошибок, права, флаги      |
| `lib/ipc`            | кодек кадров и типы контрактов поверх транспортов              |
| `lib/userland`       | модель образа: сегменты, права, точка входа, валидация         |
| `lib/userland-image` | бинарный формат `userland.img` (encode/decode)                 |
| `lib/bootstrap-abi`  | контракт `Bootstrap` — канал процесса к ядру                   |

Прикладной код процесса зависит от `runtime`, `syscall`, `ipc` и нужных
контрактов. Форматом образа и его сборкой занимается host-инструментарий.

## lib/runtime

`runtime` — слой userland поверх syscall ABI. Дает API доступа к системным вызовам. Полный перечень
операций ядра и их семантика — в [syscalls.md](syscalls.md).

### Хэндлы

Объектный API делает владение хэндлом явным через тип. `OwnedHandle` владеет
хэндлом и закрывает его на drop; он не копируется и не клонируется — владелец
один. Доступны явный `close`, `duplicate` (независимый хэндл с подмножеством
прав и значком `badge`, требует право `DUPLICATE`) и `into_raw` — извлечение
сырого хэндла с подавлением drop, через которое проходят все операции, чья
семантика потребляет хэндл. `BorrowedHandle` — заимствование хэндла на время
одного вызова, привязанное к времени жизни владельца.

### Типизированные объекты

Поверх хэндлов лежат обёртки объектов ядра. Каждая владеет своим `OwnedHandle`
и закрывает его на drop; `from_handle`/`into_handle` явно принимают и отдают
владение:

- `Signal` — сигнальный объект (wait/set/notify, park/wake потоков);
- `Port` и `Reply` — синхронный rendezvous-эндпоинт и одноразовый reply-хэндл;
- `Process` и `Thread` — процесс и поток: создание, запуск, join по терминации,
  exit-код, terminate;
- `Resource`, `MemoryRegion`, `Mapping`, `AnonymousMapping` — метеринг-ресурс,
  регион памяти и его маппинги; маппинги освобождают регион на drop.

`spawn` запускает поток в текущем процессе по fn-указателю, выделяя стек, и
возвращает `JoinHandle`; `join` ждёт терминации и освобождает стек.

Возврат нормализуется в `runtime::Result<T>`: `Error` различает известную ошибку
syscall и нераспознанный код, чтобы дрейф ABI или баг декодирования не
маскировался под рабочую ошибку.

### Сырые svc-обёртки

Сырой слой даёт по одной функции на операцию ядра, реэкспортированной из
`runtime` напрямую: синхронный IPC (`port_create`, `port_send`, `port_recv`,
`port_call`, `port_reply`, `ipc_buffer_addr`), хэндлы (`handle_close`,
`handle_duplicate`), процессы и потоки (`process_*`, `thread_*`), память
(`memory_*`), прерывания (`irq_mint`, `irq_ack`). Возврат знаковый:
отрицательное значение — код ошибки. Слой остаётся доступен для низкоуровневых
тестов и кода, которому нужна точная семантика syscall.

### Куча и синхронизация

Глобальный аллокатор процесса — куча поверх syscall памяти: `alloc` (`Box`,
`Vec`, `String`) доступен всегда. Куча безопасна для многопоточного процесса.
Аллокатор использует хэндл на корневой `Resource` процесса, который ядро
передаёт при запуске (см. раздел "Жизненный цикл").

Для синхронизации потоков доступны `Mutex<T>` и `Condvar`, реализованные поверх
Signal-syscall. Гарантии — стандартный мьютекс с уведомлением; `Mutex` и
`Condvar` уничтожают только после завершения всех способных заблокироваться
на них потоков.

### Транспорты

Контракты IPC процесс держит через транспорт. Доступны два транспорта:
`PortTransport` (поверх синхронного Port + per-thread IPC-буфера) и
`RingTransport` (поверх SPSC-кольца в разделяемой памяти). Устройство
контрактов и транспортов описано в [ipc.md](ipc.md).

## Образ

Все программы userland упакованы в один бинарный образ `userland.img`. Ядро
получает его как blob и из него поднимает первый процесс. Образ самодостаточный:
заголовок, метаданные записей и payload с байтами сегментов, все целые
little-endian.

### Структура файла

| Поле             | Смещение | Размер  | Описание                          |
|------------------|----------|---------|-----------------------------------|
| magic            | 0        | 8 B     | `USRLIMG\0`                       |
| version          | 8        | u16 LE  | версия формата (текущая: 1)       |
| entry_count      | 10       | u16 LE  | число программ в образе (>= 1)    |
| total_size       | 12       | u64 LE  | полный размер файла в байтах      |

За заголовком (20 B) следуют записи (entry), затем payload-секция.

### Запись (entry)

| Поле           | Смещение | Размер | Описание                           |
|----------------|----------|--------|------------------------------------|
| payload_offset | 0        | u64 LE | смещение payload программы в файле |
| payload_size   | 8        | u64 LE | размер payload в байтах            |
| entry_va       | 16       | u64 LE | точка входа в VA процесса          |
| stack_size     | 24       | u64 LE | размер стека в байтах              |
| segment_count  | 32       | u16 LE | число сегментов                    |
| name_len       | 34       | u16 LE | длина имени (UTF-8, без нуля)      |

За заголовком записи (36 B) идут дескрипторы сегментов, затем имя (UTF-8).

### Сегмент

| Поле        | Смещение | Размер | Описание                                      |
|-------------|----------|--------|-----------------------------------------------|
| file_offset | 0        | u64 LE | смещение данных сегмента в payload            |
| file_size   | 8        | u64 LE | размер данных в файле                         |
| va_base     | 16       | u64 LE | базовый VA в адресном пространстве процесса   |
| mem_size    | 24       | u64 LE | размер в памяти (>= file_size; разница — BSS) |
| flags       | 32       | u32 LE | права: 0=RW, 1=RO, 2=RX                       |

Сегменты и их `va_base` выровнены на страницу (`USERLAND_PAGE_SIZE = 4096`).

Первая программа в образе является bootstrap-процессом. Образ собирается на host:
инструмент читает ELF каждой программы, раскладывает её секции по сегментам с
правами и склеивает записи в `userland.img`. Состав образа задаёт TOML-манифест
в `user/images/`:

```toml
version = 1

[[programs]]
package = "rootkeeper"
```

Признак bootstrap-программы и размер стека фиксируются в разделе
`[package.metadata.userland]` её `Cargo.toml`:

```toml
[package.metadata.userland]
bootstrap = true
stack_size = 65536
```

## Жизненный цикл

После инициализации ядро запускает высокоприоритетный init-таск. Init читает
blob `userland.img`, декодирует первую запись (bootstrap-entry), создаёт
bootstrap-порт, корневой `Resource` и корневой `IrqControl`, раскладывает
сегменты в новое адресное пространство и стартует первый поток.

Точка входа процесса — `_start`, которой в регистре `x0` приходит raw HandleId
bootstrap-порта (handle[0]):

```rust
#[unsafe(no_mangle)]
pub extern "C" fn _start(bootstrap_handle: usize) -> ! { /* ... */ }
```

Процесс получает три начальных хэндла:

- handle[0] — клиентский конец bootstrap-порта (Port), переданный в `x0`
- handle[1] — корневой `Resource`, полномочие на выделение памяти;
  аллокатор процесса (`memory_allocate`) получает его через `process_resource_self`
- handle[2] — корневой `IrqControl`, полномочие выдавать линии прерываний;
  делегируется драйверам передачей/дублированием

Подробности Resource-модели — в [architecture.md](architecture.md) и
[syscalls.md](syscalls.md).

Ядро параллельно держит серверный конец bootstrap-порта в kernel-задаче-логгере,
которая декодирует кадры контракта `Bootstrap` и зеркалит их в klog. Когда
bootstrap-процесс завершается, ядро читает его exit-код и вызывает
`system_off(exit_code)`.

Таким образом, смерть bootstrap-процесса — штатное завершение всей системы, а
его exit-код становится кодом выхода машины. Это используют тесты: процесс
отрабатывает, выходит с кодом, машина гаснет, host-обвязка читает код как вердикт.

## Контракт Bootstrap

Bootstrap — единственный типизированный канал между bootstrap-процессом и ядром.
Контракт определён в `lib/bootstrap-abi` и содержит одну операцию:

```
Bootstrap::log(message: Str<LOG_MESSAGE_MAX>) [cast]
```

`log` — односторонняя (`#[cast]`) отправка: клиент шлёт строку в klog, ответа нет.
`LOG_MESSAGE_MAX` совпадает с `ipc::wire::FIELD_DATA_MAX`.

## Как написать процесс

Программа userland — бинарь без стандартной библиотеки и без `main`, с
собственными `_start` и `panic_handler`. `rootkeeper` — минимальный полный
пример: залогировать строку через bootstrap-порт и выйти.

```rust
#![no_std]
#![no_main]

use bootstrap::{BootstrapClient, LOG_MESSAGE_MAX};
use ipc::wire::Str;
use runtime::{PortTransport, thread_exit};
use syscall::Handle;

#[unsafe(no_mangle)]
pub extern "C" fn _start(bootstrap_handle: usize) -> ! {
    let bootstrap = Handle::new(bootstrap_handle as u32).expect("bootstrap handle is non-zero");
    let client = BootstrapClient::new(PortTransport::client(bootstrap));
    let result = client
        .log(Str::<LOG_MESSAGE_MAX>::new("rootkeeper started").expect("startup log must fit"));

    thread_exit(u64::from(result.is_err()))
}

#[panic_handler]
fn panic(_info: &core::panic::PanicInfo<'_>) -> ! {
    loop { core::hint::spin_loop() }
}
```

Что нужно новому процессу помимо кода:

- линкер-скрипт `link.ld`: точка входа `_start`, базовый адрес образа
  (`0x00400000`) и выравнивание секций `.text/.rodata/.data/.bss` на страницу
  (4 KiB). Скрипт подключается из `build.rs` через `cargo:rustc-link-arg=-T`;
- `Cargo.toml` с `forced-target = "aarch64-unknown-none"` (через
  `cargo-features = ["per-package-target"]`): бинарь всегда собирается под
  bare-metal без `--target`;
- раздел `[package.metadata.userland]` нужен, если процесс — кандидат в
  bootstrap (`bootstrap = true`, `stack_size`);
- зависимости `runtime`, `syscall`, `ipc` и нужные контракты;
- включение пакета в TOML-манифест образа (`user/images/<имя>.toml`).

Вывод и обмен с другими процессами идут через порты и контракты. Стартовый
bootstrap-порт — частный случай: на нём объявлен контракт `Bootstrap`, и его
хэндл процесс получает в `x0` сырым. В примере он передаётся прямо в транспорт;
если нужно владение с закрытием на drop, сырой хэндл усыновляют в `OwnedHandle`
через `from_raw`.

## Тесты

Интеграционные тесты ядра выполняются двумя проходами над одним и тем же
production-ядром.

Первый проход — kernel-сторона: ядро собирается с фичей `kernel-tests`, тесты
выполняются в kernel-контексте.

Второй проход — userland-сторона: в образ кладётся `testrunner` как
bootstrap-процесс (`user/images/test.toml`), и те же `#[kernel_test]`-функции
прогоняются в userspace против обычного ядра. `testrunner` устанавливает writer,
шлющий строки лога кадрами контракта `Bootstrap` в ядро, и exit-делегат,
дофлушивающий лог перед завершением потока. По окончании прогона процесс выходит
с кодом-вердиктом — машина гаснет этим кодом.

```rust
#[kernel_test]
fn userland_smoke() {
    let sum: u64 = (1..=10).sum();
    kernel_tests::kassert_eq!(sum, 55);
    kernel_tests::kassert!(sum.is_multiple_of(5));
}
```

Второй проход проверяет полный путь через реальный syscall ABI и загрузку образа.
Критерий, какой тест где живёт, и детали обоих проходов — в
[commands.md](commands.md).
