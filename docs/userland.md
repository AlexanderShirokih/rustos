# Userland

Userspace-процесс содержит весь свой код и работает поверх syscall ABI ядра.
Система не поддерживает динамическую загрузку и разделяемые библиотеки. Код
программ лежит в `user/`, а упакованы они в один образ, который ядро получает от
загрузчика и из которого поднимает первый процесс.

## Образ

`userland.img` — плоский архив именованных блобов с одной таблицей. В формате
нет отдельного вида записи под программу. Программа — это обычная запись, чьё
содержимое начинается своей магией.

Состав образа задаёт TOML-манифест, путь к которому передаётся в `--image` (по
умолчанию `user/rootkeeper/image.toml`):

```toml
version = 1

[plan]
source = "user/rootkeeper/system.toml"

[stage1]
source = "user/rootkeeper/stage1.toml"

[[mount_tables]]
source = "user/rootkeeper/namespace.toml"

[[programs]]
package = "rootkeeper"
path = "/boot/rootkeeper"
boot = true

[[files]]
path = "/boot/rootkeeper/assets"
source = "user/rootkeeper/assets/**/*.txt"
```

`[[programs]]` и `[[files]]` различаются одним — откуда инструмент берёт байты.
Программа приходит из собранного ELF пакета, файл читается с диска. Запись файла
лежит в каталоге своей программы; записей вне каталогов образ не принимает.
`boot = true` стоит ровно у одной программы, и её номер инструмент проставляет в
`boot_index` заголовка образа. Само имя пути при этом ничем не закреплено.

Элемент `[[programs]]` объявляет две вещи — идентичность программы и её
размещение.

Идентичность строится на имени cargo bin-таргета, которое инструмент берёт из
`cargo metadata`. Это либо единственный bin-таргет пакета `package`, либо
таргет, названный ключом `bin`. Пакет с несколькими bin-таргетами требует явного
`bin`, а пакет вовсе без bin-таргетов манифест отвергает. По этому же имени
артефакт собирается и потом отыскивается. Форм у идентичности две:
квалифицированная `<package>::<bin>`, уникальная в пределах образа, и краткая
`<bin>`.

Размещение задаёт `path`. Запись образа ложится по объявленному пути и лежит
под его последним компонентом. Описания композиции называют программу именно
идентичностью ([rootkeeper.md](rootkeeper.md#план-загрузки)), а сборка разрешает
её в запись реестра. Квалифицированная форма разрешается всегда, краткая — пока
её объявил ровно один пакет образа. Неоднозначную краткую ссылку сборка
отвергает, перечислив эти пакеты. Компонент без ключа `name` зовётся той формой,
которой записана ссылка.

Секции `[plan]`, `[stage1]` и `[[mount_tables]]` называют host-описания, которые
инструмент проверяет, компилирует и размещает в образе обычными записями. Это
план ступени 0 ([rootkeeper.md](rootkeeper.md#план-загрузки)), ступень 1
([rootkeeper.md](rootkeeper.md#ступени-загрузки)) и дерево имён загрузки
([rootkeeper.md](rootkeeper.md#политика-загрузки)). Ступень 1 и дерево имён
без `[plan]` манифест отвергает — связывать их слоты и разрешать
имена экземпляров тогда не с чем.

Разделение труда простое. Манифест отвечает, что лежит в образе. План отвечает,
что и с какими аргументами rootkeeper поднимает.

Источник без подстановок даёт одну запись по пути `path`; каталог сам по себе
источником не считается. Источник с подстановкой делится по первому компоненту,
который её содержит. Слева от него — корень обхода, справа — шаблон, а каждый
принятый файл ложится под `path` вместе со своим путём от корня обхода.

| Шаблон | Что принимает                                       |
|--------|-----------------------------------------------------|
| `?`    | один символ внутри компонента                       |
| `*`    | любую последовательность символов внутри компонента |
| `**`   | любую последовательность, разделители включая       |
| `**/`  | любую цепочку каталогов, в том числе пустую         |

Обход рекурсивен и идёт по имени записи каталога, а не в порядке, который вернула
файловая система. Поэтому состав образа от машины сборки не зависит. Один путь,
заполненный несколько раз одним и тем же содержимым, даёт одну запись; тот же
путь с разным содержимым сборку останавливает. Флаг `--file path=source`
добавляет файлы поверх манифеста ([commands.md](commands.md#userland)).

Размер стека программы фиксируется в разделе `[package.metadata.userland]` её
`Cargo.toml`:

```toml
[package.metadata.userland]
stack_size = 65536
```

### Формат файла

Заголовок образа занимает 24 B, за ним идёт таблица записей, байты путей и
данные записей.

| Поле        | Смещение | Размер | Описание                                        |
|-------------|----------|--------|-------------------------------------------------|
| magic       | 0        | 8 B    | `USRLIMG\0`                                     |
| version     | 8        | u16 LE | версия формата (текущая: 1)                     |
| entry_count | 10       | u16 LE | число записей таблицы (>= 1)                    |
| boot_index  | 12       | u16 LE | запись, с которой ядро поднимает первый процесс |
| reserved    | 14       | u16 LE | ноль                                            |
| total_size  | 16       | u64 LE | полный размер файла в байтах                    |

Запись таблицы занимает 28 B:

| Поле        | Смещение | Размер | Описание                                     |
|-------------|----------|--------|----------------------------------------------|
| path_offset | 0        | u64 LE | смещение байт пути в файле                   |
| path_len    | 8        | u16 LE | длина пути (UTF-8, без нуля)                 |
| alias_of    | 10       | u16 LE | номер записи, чьё окно повторено, плюс один  |
| data_offset | 12       | u64 LE | смещение данных, кратно `USERLAND_PAGE_SIZE` |
| data_size   | 20       | u64 LE | длина данных в байтах                        |

Записи отсортированы строго по возрастанию пути. На этом стоит двоичный поиск, а
строгость порядка заодно запрещает дубликаты. Путь — непустой ASCII не длиннее
`USERLAND_ENTRY_PATH_CAPACITY` (255 байт), оканчивающийся непустым компонентом.

Нулевой `alias_of` означает собственное окно данных. Такие окна лежат в порядке
таблицы и не пересекаются. Ненулевой объявляет запись повтором окна более ранней
записи, и одинаковое содержимое хранится в образе один раз.

### Формат программы

Заголовок программы (32 B) и дескрипторы сегментов занимают первую страницу
записи — отсюда предел в 101 сегмент на программу. Данные сегментов начинаются
со смещения `USERLAND_PAGE_SIZE` внутри записи и выровнены на него.

| Поле          | Смещение | Размер | Описание                  |
|---------------|----------|--------|---------------------------|
| magic         | 0        | 8 B    | `USRPROG\0`               |
| entry_va      | 8        | u64 LE | точка входа в VA процесса |
| stack_size    | 16       | u64 LE | размер стека в байтах     |
| segment_count | 24       | u16 LE | число сегментов           |
| reserved      | 26       | 6 B    | ноль                      |

Дескриптор сегмента занимает 40 B; сегменты и их `va_base` выровнены на страницу
(`USERLAND_PAGE_SIZE = 4096`).

| Поле        | Смещение | Размер | Описание                                      |
|-------------|----------|--------|-----------------------------------------------|
| file_offset | 0        | u64 LE | смещение данных сегмента от начала записи     |
| file_size   | 8        | u64 LE | размер данных в файле                         |
| va_base     | 16       | u64 LE | базовый VA в адресном пространстве процесса   |
| mem_size    | 24       | u64 LE | размер в памяти (>= file_size; разница — BSS) |
| flags       | 32       | u32 LE | права: 0=RW, 1=RO, 2=RX                       |
| reserved    | 36       | u32 LE | ноль                                          |

Инструмент сборки читает ELF каждой программы и раскладывает её
`PT_LOAD`-сегменты в содержимое записи.

## Жизненный цикл

После инициализации ядро берёт запись по `boot_index`, разбирает её содержимое
как программу, создаёт bootstrap-порт и корневой `Resource`, раскладывает
сегменты в новое адресное пространство и стартует первый поток. Имя процесса —
последний компонент пути его записи (`/boot/filesystem-ramfs` →
`filesystem-ramfs`), не длиннее 64 байт.

Точка входа процесса — `_start`, которой raw HandleId начальной capability
приходит в регистре `x0`:

```rust
#[unsafe(no_mangle)]
pub extern "C" fn _start(startup: Handle) -> ! { /* ... */ }
```

Для первого процесса начальная capability — bootstrap-порт ядра. Низкоуровневый
`userland_loader::load_entry` позволяет userspace-загрузчику передать дочернему
процессу произвольный хэндл.

### Startup-порт дочернего процесса

`userland_loader::launch_entry` выполняет стандартный запуск дочернего
приложения. Загрузчик создаёт `Port` без значка, серверную сторону передаёт
процессу в `x0`, а клиентскую передаёт callback'у для одного кадра прикладного
типизированного IPC-контракта:

```rust
let process = launch_entry(&program, None, &resource, |startup| -> Result<()> {
    driver_args::Client::new(PortTransport::client(startup.handle()))
        .provide(device, service)?;
    Ok(())
})?;
```

Ошибка callback'а завершает потомка через `ProcessTerminate` и освобождает его
таблицу хэндлов и metering-бюджет. Если отказала и сама уборка, наружу уходит её
ошибка вместо исходной — так вызывающий не получит ложного подтверждения отката.

Одноразовый получатель принимает кадр через `runtime::receive_startup` — функция
закрывает серверную сторону startup-порта после диспетчеризации:

```rust
let DriverState { device, service } =
    receive_startup(startup, driver_args::dispatch)?.ok_or(Error::Start)?;
```

Тип аргументов и владение передаваемыми capability остаются частью прикладного
IPC-контракта.

Бывает, что тот же порт после стартового кадра принимает ещё и admin-команды.
Тогда берут `launch_entry_retained`: он возвращает `InitializedProcess` с полями
`process` и `startup`, и порт дальше обслуживают обычным `PortTransport`.
Клиентская сторона такого порта минтится под значком, так что исчезновение
поднявшего процесса приходит потомку как `SenderGone`
([port.md](port.md#уход-значка)).

Имя процесса задаёт второй аргумент; `None` берёт имя самой записи. Запись с
программой лежит в каталоге компонента под именем `program`, и потому тот, кто
поднимает компонент, берёт имя каталога через `component_name`.

### Стартовая транзакция компонента

Компонент композиции принимает целую транзакцию, а не один стартовый кадр.
Сначала приходит базовый кадр с его лог-сессией и числом экспортов и слотов,
следом — серверные стороны портов экспортов в порядке объявления, а за ними
capability слотов в порядке объявления
([rootkeeper.md](rootkeeper.md#связывание)).

Экспорты и слоты идут отдельными кадрами того же startup-порта, потому что один
кадр IPC вмещает не больше `MESSAGE_MAX_HANDLES` капабилити. Сам startup-порт остаётся у
компонента на всю incarnation, и после транзакции супервизор запрашивает по нему
сессии экспортов операцией `open_session`. Компоненту без экспортов обслуживать
на нём нечего, и он паркуется вызовом `park`.

Контракт транзакции находится в `lib/component-abi`, её приёмник — в
`lib/component-startup`. Срок прикладному callback общий loader не задаёт.
Конечный send timeout и подтверждение возврата бюджета — это уже контракт managed
startup ([rootkeeper.md](rootkeeper.md#managed-startup)).

### Манифест компонента

Компонент объявляет свои связи в коде — макросом `component_manifest!` из
`lib/component-startup`. Объявление называет слоты по порядку транзакции. Для
каждого слота оно называет имя, вид и то, чем композиция его наполняет —
семейство совместимостей у устройства, имя протокола у импорта.

| Ключ                   | Что объявляет                                              |
|------------------------|------------------------------------------------------------|
| `slots`                | слоты по порядку приёма                                    |
| `exports`              | протоколы экспортов парами «имя поля — протокол»           |
| `establishes_sessions` | сессии своих экспортов компонент создаёт сам               |

Каждый экспорт получает свой порт, и один порт содержит один протокол.
Административный протокол объявляется таким же экспортом, как и любой другой.
Установление сессий без `exports` сборка отвергает как бессмысленное.

Импорт протокола принимает необязательный `instance` — имя экземпляра-провайдера.
Без него сборка ищет в композиции единственного провайдера
([rootkeeper.md](rootkeeper.md#связывание)). Слот-каталог называет `instance`
обязательно. У такого слота нет протокола, а провайдеров сессий в композиции
несколько.
Имя своего каталога компонент не выбирает — его берёт композиция из записи его
программы.

```rust
component_manifest! {
    struct ImageFileSystemStartup {
        exports: { service: "FileSystem" },
        establishes_sessions: true,
        slots: { image: userland },
    }
}

component_manifest! {
    struct RtcStartup {
        slots: {
            line: irq(compatible = ["arm,pl031"]),
            window: mmio(compatible = ["arm,pl031"]),
        },
    }
}

component_manifest! {
    struct FileReaderStartup {
        slots: { files: service(protocol = "FileSystem", instance = "ramfs") },
    }
}
```

Список совместимостей — заявка драйвера на целое семейство устройств. Подойдёт
любая из строк, а выбор между ними принадлежит описанию платформы конкретной
машины. Номер ресурса (`resource`, по умолчанию `0`) выбирает линию либо окно
среди ресурсов устройства. Это знание драйвера о железе, а не решение
композиции.

Из одного объявления берутся сразу две вещи — приёмник и манифест.

Приёмник — структура с полем `startup`, полями названных экспортов и полями
названных слотов. Тип каждого поля берётся из вида его слота, и импорт протокола
вместе с экспортом дают порт, окно `mmio` - регион памяти, линия `irq` - линию
прерывания.
Её `receive` принимает транзакцию целиком, отдаёт лог-сессию вместе с этой
структурой и отвергает транзакцию, объявлению не отвечающую. Каждое поле владеет
своей capability названного вида, и объектная операция чужого вида по такому
полю не компилируется. Отвергнутая транзакция закрывает всё, что успела
доставить.

Манифест — артефакт сборки, запись в секции `.component.manifest` собранной
программы. Сборщик читает её из ELF каждой программы, на которую ссылается план,
и по ней строит слоты компонента. Секция необязательна; программа без неё
объявляет пустой манифест.

Заголовок манифеста занимает 16 B, за ним идут протоколы экспортов в порядке
объявления — длина `u8` и байты каждого — и записи слотов по порядку приёма:

| Поле        | Смещение | Размер | Описание                                             |
|-------------|----------|--------|------------------------------------------------------|
| magic       | 0        | 8 B    | `CMPMFST\0`                                          |
| version     | 8        | u16 LE | версия формата (текущая: 1)                          |
| slot_count  | 10       | u16 LE | число слотов                                         |
| export_count| 12       | u8     | число экспортов                                      |
| flags       | 13       | u8     | бит 0: компонент сам создаёт сессии                  |
| reserved    | 14       | 2 B    | ноль                                                 |

Заголовок слота занимает 4 B, за ним идут его имена — длина `u8` и байты
каждого:

| Поле       | Смещение | Размер | Описание                                                                   |
|------------|----------|--------|----------------------------------------------------------------------------|
| kind       | 0        | u8     | 0 userland, 1 irq, 2 mmio, 3 service, 4 directory, 5 supervisor            |
| resource   | 1        | u16 LE | номер ресурса устройства                                                   |
| name_count | 3        | u8     | число имён слота                                                           |

У устройства имена — строки совместимости (хотя бы одна), у импорта протокола —
его имя и за ним необязательное имя экземпляра, у каталога — имя
экземпляра-провайдера; у `userland` и `supervisor` нет имён.

## Контракт Bootstrap

Bootstrap — типизированный канал между корневым процессом и ядром, определённый в
`lib/bootstrap-abi`. Через него корневой процесс запрашивает корневые capability.
Капу самого канала он никому не отдаёт. Она открывает весь набор корневых
полномочий сразу, и передать её потомку значит передать их все разом.

Boot FDT канал выдаёт регионом поверх страниц с блобом. Загрузчик кладёт блоб по
произвольному адресу, не обязательно с начала страницы, так что вместе с капой
региона контракт отдаёт смещение первого байта блоба от её начала.

## Журнал

Процесс шлёт строки в системный журнал по контракту `Log` из `lib/log-abi`.
Сервером контракта служит relay из `lib/log-relay` в корневом процессе. Принятые
строки он пересылает ядру по bootstrap-каналу, а лог-сессии его порта достаются
потомкам.

Свою лог-капу процесс отдаёт платформенному слою через `runtime::install_log`
вместе с тегом своих строк, а дальше пишет через `log_line` и `log_fmt`.
Программе на стандартной библиотеке делать этого не нужно. Лог-сессию за неё
забирает точка входа, а тег ей даёт значок сессии.

## Часы

Монотонные часы процесса — `runtime::Instant`. Ни одного syscall они не стоят.
Ядро открывает EL0 архитектурный счётчик времени вместе с его частотой, а
платформенный слой переводит тики в наносекунды. Программировать таймер процесс
по-прежнему не может.

Точка отсчёта у часов общая с дедлайнами `timeout_ns` блокирующих вызовов, так
что разность двух замеров сравнима с переданным тайм-аутом напрямую.

## Как написать процесс

Программа образа существует в двух формах.

На стандартной библиотеке пишутся компоненты композиции. Точку входа и приём
стартового набора им отдаёт платформенный слой.

Freestanding-форма — свои `_start` и `panic_handler`, без `main` — обслуживает
запуск мимо стартовой транзакции компонента. Так подняты корневой процесс,
`testrunner` и его фикстуры.

Что нужно новому процессу в обеих формах помимо кода:

- линкер-скрипт: точка входа `_start`, базовый адрес образа (`0x00400000`),
  выравнивание секций `.text/.rodata/.data/.bss` на страницу, границы таблицы
  тестов в `.rodata` и незагружаемая секция `.component.manifest`.
  `userland_build::emit_linker_script()` из `build.rs` размещает скрипт в
  сборке;
- раздел `[package.metadata.userland]` с размером стека;
- членство в workspace `user/`;
- включение пакета в TOML-манифест образа с путём записи.

### Программа на стандартной библиотеке

Точка входа вызывает `main` и оставляет программе стартовый handle. Стартовую
транзакцию компонент принимает сам — тем же объявлением, каким её создаёт
freestanding-программа. Приём обязателен даже компоненту без слотов. Он закрывает
стартовое рандеву композиции и приносит лог-сессию, по которой идут `stdout` и
`stderr`.

`component_startup_std::receive` забирает handle и отдаёт программе принятые
ресурсы. Вызов идёт первым действием `main`. До лог-сессии вывод в журнал не
попадает, так что об отказе приёма программе остаётся сообщить кодом выхода:

```rust
component_startup::component_manifest! {
    struct ClockStartup {
        slots: { rtc: service(protocol = "Rtc") },
    }
}

let Ok(startup) = component_startup_std::receive(ClockStartup::receive) else {
    process::exit(NO_STARTUP_EXIT_CODE);
};
let clock = rtc::Client::new(PortTransport::client(&startup.rtc));
println!("rtc reads {}", clock.now()?);
```

Образцы — `hello-std` и `clock-std` в `user/`. Стеки потоков программа берёт из
своей кучи, и предел памяти компонента покрывает их наравне с ней.

Отсюда же проходит важная граница. Платформенное состояние процесса держит копия
внутри `std`, и она должна быть одна. Крейты без состояния — объекты ядра и
обёртки вызовов — программа берёт обычными зависимостями
([workspace.md](workspace.md#один-рантайм-в-процессе)). Потоки `stdout` и
`stderr` тоже держит `std`, так что `println!` уводит строку прямо в журнал.

### Freestanding-программа

Программа сама объявляет свои `_start`, `panic_handler` и глобальный аллокатор
(`runtime::process_heap!`), а платформенный слой берёт из `lib/runtime`.
Стартовую транзакцию компонента она принимает тем же приёмником из своего
`component_manifest!` (образец — `driver-pl031` в `user/`). Приёмнику она передаёт
handle из `_start` и отдаёт лог-сессию своей копии платформенного слоя. Низкоуровневый
`load_entry` размещает ей в `x0` одну начальную capability:

```rust
#![no_std]
#![no_main]

use runtime::{PortTransport, thread_exit};
use syscall::Handle;

runtime::process_heap!();

#[unsafe(no_mangle)]
pub extern "C" fn _start(log: Handle) -> ! {
    let client = log_abi::log::Client::new(PortTransport::client(log));
    let result = client.write_str("init", "process started");

    thread_exit(u64::from(result.is_err()))
}

#[panic_handler]
fn panic(_info: &core::panic::PanicInfo<'_>) -> ! {
    loop { core::hint::spin_loop() }
}
```
