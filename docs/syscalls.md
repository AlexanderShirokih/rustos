# Системные вызовы

Syscall-слой принимает 16-битный номер операции и до шести аргументов
`u64`. Основной возврат — `i64`: неотрицательное значение означает
успех, отрицательное значение — `-(SyscallError as u32)`.

Вторичный возврат `u64` используется только операциями, которые явно
указаны в таблицах ниже. `HandleId` — ненулевой `u32`; `0` и значения
вне `u32` считаются неверным аргументом.

Номера операций определены в
[lib/syscall/src/syscallop.rs](../lib/syscall/src/syscallop.rs),
обёртки userspace — в [lib/syscall-user](../lib/syscall-user/src/lib.rs).
Ядро проверяет вид объекта за handle; несовпадение даёт `WrongType`.

## Права

Handle — идентификатор (`u32`) записи в таблице текущего процесса. Запись
содержит ссылку на объект ядра и маску разрешённых операций. Ядро проверяет
права при каждом syscall; нехватка нужного права даёт `AccessDenied`.

Дублирование создаёт производный handle на тот же объект с равными или меньшими
правами. Таблица вмещает 1024 записи; её заполнение даёт `OutOfHandles`.

| Право       |      Бит | Описание                                                                                                                 |
|-------------|---------:|--------------------------------------------------------------------------------------------------------------------------|
| `DUPLICATE` | `1 << 0` | разрешает создать новый handle на тот же объект с подмножеством прав                                                     |
| `TRANSFER`  | `1 << 1` | разрешает отдать доступ к объекту другому процессу                                                                       |
| `READ`      | `1 << 2` | чтение из объекта: `recv` на port, mapping памяти на чтение, ожидание сигналов, чтение метаданных                        |
| `WRITE`     | `1 << 3` | запись в объект: `send`/`call` на port, mapping памяти на запись, изменение сигналов, управление process/thread, минтинг |
| `EXECUTE`   | `1 << 4` | mapping памяти с правом исполнения                                                                                       |

## Сигналы

Сигналы представлены 32-битной маской состояния объекта. Назначение битов
определяется видом объекта.
`SignalWaitOne` принимает маску интересующих битов и блокирует вызывающий поток,
пока хотя бы один из них не поднимется.

Ожидание доступно для `Signal`, `Process`, `Thread` и `IrqLine`.
У процесса и потока бит `SIGNALED` означает завершение, у линии IRQ —
срабатывание прерывания. `SignalSet` меняет биты только у `Signal`.

| Объект             | Сигнал     |      Бит | Описание                   |
|--------------------|------------|---------:|----------------------------|
| `Signal`           | `SIGNALED` | `1 << 0` | событие наступило          |
| `Process`/`Thread` | `SIGNALED` | `1 << 0` | объект завершился          |
| `IrqLine`          | `SIGNALED` | `1 << 0` | сработало прерывание линии |

| Код | Имя                 | Условие                                                |
|----:|---------------------|--------------------------------------------------------|
|   1 | `BadSyscall`        | неизвестный номер операции                             |
|   2 | `KernelOriginated`  | syscall-trap сделан из kernel-контекста                |
|   3 | `InvalidArgument`   | неверный аргумент, указатель, размер или флаги         |
|   4 | `BadHandle`         | handle закрыт или не существует                        |
|   5 | `WrongType`         | handle указывает на объект другого типа                |
|   6 | `AccessDenied`      | у handle недостаточно прав                             |
|   7 | `ShouldWait`        | операция сейчас не может завершиться                   |
|   8 | `PeerClosed`        | на port некому принять кадр либо сторона ушла          |
|   9 | `Timeout`           | истёк тайм-аут ожидания                                |
|  10 | `BufferTooSmall`    | буфер получателя меньше сообщения                      |
|  11 | `MessageTooBig`     | сообщение превышает лимит                              |
|  12 | `OutOfHandles`      | таблица handle процесса заполнена                      |
|  13 | `OutOfMemory`       | не хватает памяти                                      |
|  14 | `NotFound`          | запрошенный VA-регион не найден                        |
|  15 | `Canceled`          | ожидаемый handle закрыт или передан до прихода сигнала |
|  16 | `ResourceExhausted` | бюджет `Resource` исчерпан либо порт накопил уходы     |
|  17 | `Revoked`           | capability отозван: закрыт предок по цепочке деривации |
|  18 | `SenderGone`        | отправители значка исчезли; значок в `IpcBuffer.badge` |
|  19 | `AlreadyBound`      | линия прерывания уже привязана                         |
|  20 | `OutOfMappings`     | таблица отображений адресного пространства заполнена   |

## Signal

`SignalSet` меняет биты объекта `Signal`. `SignalWaitOne` и
`SignalWaitMany` ждут события объектов с наблюдаемыми сигналами.

|     Op | Имя              | Аргументы                         | Возврат                                | Права            |
|-------:|------------------|-----------------------------------|----------------------------------------|------------------|
| `0x10` | `SignalSet`      | `handle`, `set`, `clear`, `count` | `0`                                    | `WRITE`          |
| `0x11` | `SignalWaitOne`  | `handle`, `signals`, `timeout_ns` | observed mask                          | `READ`           |
| `0x12` | `SignalWaitMany` | `items_va`, `count`, `timeout_ns` | primary=observed mask, secondary=index | `READ` на каждом |
| `0x13` | `SignalCreate`   | —                                 | `signal_h`                             | —                |

`SignalSet` принимает `count` как закрытый `WakeCount`-код:

|    `count` | Значение | Поведение                                     |
|-----------:|----------|-----------------------------------------------|
|        `0` | `None`   | выставить/снять биты, никого не будить        |
|        `1` | `One`    | разбудить одного ждущего в FIFO-порядке       |
| `u64::MAX` | `All`    | разбудить всех ждущих, чья маска пересекается |

Любое другое значение `count` возвращает `InvalidArgument`. Биты
выставляются/снимаются независимо от `count`.

`SignalCreate` создаёт `Signal` с правами
`READ | WRITE | DUPLICATE | TRANSFER`.

`signals` в `SignalWaitOne` берётся из нижних 32 бит аргумента; нулевая
маска возвращает `InvalidArgument`. `timeout_ns == 0` — poll без парковки.
Ненулевой `timeout_ns` — относительный тайм-аут в наносекундах. `Timeout`
приходит только по истечении срока. Пробуждение до него, не принёсшее сигнала,
возвращает поток в ожидание.

Аргумент `items_va` вызова `SignalWaitMany` указывает на массив 8-байтных записей
`[handle: u32, mask: u32]` (little-endian); `count` ограничен
`1..=WAIT_MANY_MAX_COUNT` (256), нулевая маска в записи — `InvalidArgument`.
Основной возврат содержит маску сработавшего объекта, вторичный — индекс
записи в массиве. Повторы `handle` в массиве допустимы.

Закрытие или передача handle, по которому выполняется
`SignalWaitOne` или `SignalWaitMany`, завершает ожидание с `Canceled`.
Повторное использование его слота новым handle не восстанавливает
прежнее ожидание.

## Port

`Port` доставляет сообщение при встрече отправителя и получателя.
Кадр находится в IPC-буфере вызывающего потока и содержит до
`IPC_BUFFER_DATA_MAX` байт данных и до `IPC_BUFFER_MAX_CAPS` handle.

Передача перемещает handle в таблицу получателя, сохраняя права и деривацию.
Другие handle и установленные маппинги отправителя сохраняются.

|     Op | Имя          | Аргументы              | Возврат              | Права   |
|-------:|--------------|------------------------|----------------------|---------|
| `0x23` | `PortCreate` | —                      | `port_h`             | —       |
| `0x24` | `PortSend`   | `handle`, `timeout_ns` | `0`                  | `WRITE` |
| `0x25` | `PortRecv`   | `handle`, `timeout_ns` | `reply_h` (либо `0`) | `READ`  |
| `0x26` | `PortCall`   | `handle`, `timeout_ns` | `0`                  | `WRITE` |
| `0x27` | `PortReply`  | `reply_handle`         | `0`                  | `WRITE` |

`PortCreate` создаёт порт. Роль его держателя задают права handle:
`READ` разрешает приём, `WRITE` — отправку и вызов с ответом.
Доступ другим процессам выдаётся дублированием и передачей handle.

`PortSend` блокирующе отправляет кадр из IPC-буфера текущего потока и ждёт, пока
встречный `recv` его примет. `PortRecv` блокирующе принимает кадр в
IPC-буфер текущего потока; если встречным был `call`, в возврат записывается
handle одноразового объекта `Reply`, иначе — `0`. Если перенос capability из
кадра отправителя не удался, `PortRecv` ждёт следующий кадр до того же срока.

`PortCall` — блокирующий запрос-ответ. Кадр уходит из IPC-буфера, и ответ
оказывается в нём же. Сервер вызывает `PortReply` с handle `Reply`, доставляя
кадр из своего IPC-буфера вызывающему потоку. `Reply` одноразов.

**Тайм-аут (`timeout_ns`).** Параметр ограничивает ожидание в
`PortSend`, `PortRecv` и `PortCall`:

- `PORT_TIMEOUT_INFINITE` (`u64::MAX`) — ждать бессрочно;
- `0` (`PORT_TIMEOUT_POLL`) — опрос без блокировки. Операция либо завершается
  немедленно (встречная сторона уже ждёт), либо возвращает `Timeout`;
- иначе — относительный тайм-аут в наносекундах.

При истечении тайм-аута (в т.ч. в режиме poll, когда нет встречной
стороны) syscall возвращает `Timeout` (`SYSCALL_RETURN_TIMEOUT = -9`).
Для `PortCall` тайм-аут покрывает всю операцию (ожидание получателя +
ожидание `reply`); если вызывающая сторона уходит по тайм-ауту, не
дождавшись ответа, сервер при попытке `PortReply` получит `PeerClosed`,
а IPC-буфер вызывателя не будет затронут.

**Доставка значка.** При приёме запроса `send` или `call` через `PortRecv`
ядро записывает в `IpcBuffer.badge` значок handle отправителя (`0`, если
значок отсутствует). Значок пишется получателю всегда, даже при пустом
теле; на стороне отправителя поле `badge` не читается, и ответ
`PortReply` его не передаёт.

**Живость сторон.** Порт считает своих держателей — capability с `READ`
(получатели) и capability со значком и `WRITE` (отправители этого значка).

На порту без получателей `PortSend` и `PortCall` сразу возвращают `PeerClosed`.
Уход последнего получателя завершает ожидающие `PortSend`, `PortCall` и
`PortRecv` с тем же кодом.

Уход последнего отправителя с данным значком возвращает очередному `PortRecv`
код `SenderGone`. Кадр при этом не доставляется, значок ушедшей стороны
записывается в `IpcBuffer.badge`, остальные поля буфера сохраняются. Механизм и
правила владения — в [port.md](port.md).

Содержимое кадра — байты и handle — записывается в IPC-буфер по адресу, который
возвращает `ThreadIpcBufferAddr` (op `0x55`). Формат типизированного IPC
поверх этого транспорта описан в [ipc.md](ipc.md).

## Handle

Вызовы этого раздела управляют временем жизни handle в таблице текущего
процесса. Закрытие удаляет запись из таблицы; если это была последняя
ссылка на объект, объект освобождается.

|     Op | Имя               | Аргументы                       | Возврат      | Права       |
|-------:|-------------------|---------------------------------|--------------|-------------|
| `0x30` | `HandleClose`     | `handle`                        | `0`          | —           |
| `0x31` | `HandleDuplicate` | `handle`, `new_rights`, `badge` | `new_handle` | `DUPLICATE` |

### Каскадный отзыв при `HandleClose`

Дублирование handle и нарезка памяти создают производные capability.
Передача через порт сохраняет цепочку деривации.

Закрытие handle или таблицы процесса отзывает его производные,
включая находящиеся в других процессах. Операции по ним дают `Revoked`.
Для памяти отзыв снимает связанные маппинги, для корня `IrqLine` —
отключает и отвязывает линию. Предки и соседние ветви сохраняют доступ.

Передача корневой capability делегирует владение целиком.
Передача производной оставляет владельцу предка возможность отзыва.
Закрытие уже отозванного handle освобождает его слот.

Выдача нового значка порта может дать `ResourceExhausted`,
если накопились непрочитанные `SenderGone`
([port.md](port.md#уход-значка)).

`new_rights` берётся из нижних 32 бит `arg1` (неизвестные биты отбрасываются) и
должен быть подмножеством прав исходного handle. `badge` занимает полные
64 бита `arg2`; `0` означает отсутствие нового значка. Присвоение значка
подчиняется правилам:

- исходный handle без значка и `arg2 != 0` — новый handle получает значок `arg2`;
- исходный handle без значка и `arg2 == 0` — новый handle остаётся без значка;
- исходный handle со значком и `arg2 == 0` — новый handle наследует значок;
- исходный handle со значком и `arg2 != 0` — вызов возвращает `BadHandle`.

Минт значка (`arg2 != 0` и `WRITE` в `new_rights`) делает значок живым на порту.
Непрочитанное событие его ухода снимается. Правила повторного использования
значков при нескольких получателях определены в [port.md](port.md).

Значок принадлежит handle; копии handle одного порта могут иметь разные
значки. При приёме сообщения ядро передаёт значок отправителя получателю
([Port](#port)).

## Process

Process-вызовы создают процесс, возвращают handle на текущий процесс и
позволяют наблюдать или принудительно завершать процесс по handle.

|     Op | Имя                   | Аргументы                                                                         | Возврат               | Права                                                                    |
|-------:|-----------------------|-----------------------------------------------------------------------------------|-----------------------|--------------------------------------------------------------------------|
| `0x40` | `ProcessCreate`       | `name_va`, `name_len`                                                             | `process_h`           | —                                                                        |
| `0x41` | `ProcessSelf`         | —                                                                                 | `process_h`           | —                                                                        |
| `0x42` | `ProcessLoadImage`    | `process_h`, `desc_va`, `desc_len`                                                | `0`                   | `WRITE` на `process_h`; `TRANSFER` + права по флагу на каждом region-handle |
| `0x43` | `ProcessExitCode`     | `process_h`                                                                       | `exit_code` как `u32` | `READ`                                                                   |
| `0x44` | `ProcessTerminate`    | `process_h`, `exit_code`                                                          | `0`                   | `WRITE`                                                                  |
| `0x45` | `ProcessStart`        | `process_h`, `entry_pc`, `user_sp`, `bootstrap_handle`, `priority`, `resource_h` | `thread_h`            | `WRITE` на `process_h`; `TRANSFER` на `bootstrap_handle`; `WRITE` и `DUPLICATE` на `resource_h` |
| `0x46` | `ProcessResourceSelf` | —                                                                                 | `resource_h`          | —                                                                        |
| `0x47` | `ResourceSplit`       | `resource_h`, `budget_pages`                                                      | `resource_h` (производный) | `WRITE` и `DUPLICATE` на `resource_h`                               |
| `0x48` | `ProcessExit`         | `exit_code`                                                                       | не возвращается       | —                                                                        |

Завершение процесса наблюдается ожиданием по `process_h`
(`SignalWaitOne`/`Many`, бит `SIGNALED`).

Необработанное исключение userspace-процесса завершает процесс так же, как
`ProcessTerminate`. Все потоки и capability процесса освобождаются, а
`ProcessExitCode` возвращает служебный отрицательный код как `u32`.
Конкретное значение не является частью ABI.

Уход последнего держателя capability процесса с правом `WRITE` завершает
процесс со служебным кодом, в том числе когда последний держатель — сам
процесс. Завершение освобождает его capability и может по тому же правилу
завершить другие процессы. Процесс, на который capability не выдавалась
ни разу, завершается только явно.

`ProcessCreate` копирует имя процесса из user-памяти, требует корректный UTF-8
и ограничение `1 <= name_len <= 64` байт. Пустое имя (`name_len == 0`)
отвергается (`InvalidArgument`).

`ProcessLoadImage` и `ProcessStart` описаны подробно в разделе
[Process Spawning](#process-spawning).

`ProcessStart` создаёт первый поток процесса и возвращает handle на него.
`bootstrap_handle` (x3) — `HandleId` обязательного стартового handle из таблицы
загрузчика. Ядро перемещает его в таблицу потомка и снимает право `TRANSFER`.
Значок и остальные права сохраняются.
`priority` (x4) задаёт нижними 8 битами приоритет потока, а биты [8..)
зарезервированы и обязаны быть нулевыми. `entry_pc` (x1) и `user_sp` (x2)
записываются в стартовый user-контекст первого потока. `resource_h` (x5) задаёт
`Resource`, из бюджета которого процесс выделяет память; нулевой `resource_h`
передаёт потомку ресурс вызывающего процесса.

`ProcessSelf` возвращает handle на текущий процесс. Эта capability держателем
не считается и время жизни процесса не продлевает.
`ProcessResourceSelf` возвращает handle на ресурс памяти текущего процесса.

`ResourceSplit` выделяет `budget_pages` страниц бюджета в отдельный `Resource` с
тем же потолком доступа (см. [Memory](#memory)). Глубина цепочки
производных ограничена восемью уровнями. Производный ресурс удерживает предков в
куче ядра даже после отзыва их handle. При достижении предела `ResourceSplit`
возвращает `ResourceExhausted`.

`ProcessTerminate` возвращает `AccessDenied` для текущего процесса даже
при наличии `WRITE`. Текущий процесс завершается через `ProcessExit`
либо после завершения своего последнего потока.

`ProcessExit` завершает все потоки текущего процесса, включая ожидающие,
и публикует `exit_code` как код выхода процесса. Вызов доступен каждому
потоку процесса без handle. `ThreadExit` завершает только вызывающий поток.

Завершение необратимо: `ProcessStart` и `ThreadCreate` на handle завершённого процесса возвращают `WrongType`.

Запуск процесса состоит из вызовов `ProcessCreate`, `ProcessLoadImage` и
`ProcessStart`. Потомок начинает исполняться после `ProcessStart`.

## Thread

Thread-вызовы создают поток в процессе, возвращают handle на текущий
поток и управляют завершением потока.

|     Op | Имя                       | Аргументы                                             | Возврат                | Права   |
|-------:|---------------------------|-------------------------------------------------------|------------------------|---------|
| `0x50` | `ThreadCreate`            | `process_h`, `entry_pc`, `user_sp`, `arg`, `priority` | `thread_h`             | `WRITE` |
| `0x51` | `ThreadSelf`              | —                                                     | `thread_h`             | —       |
| `0x52` | `ThreadExit`              | `exit_code`                                           | не возвращается        | —       |
| `0x53` | `ThreadExitCode`          | `thread_h`                                            | `exit_code` как `u32`  | `READ`  |
| `0x54` | `ThreadTerminate`         | `thread_h`, `exit_code`                               | `0`                    | `WRITE` |
| `0x55` | `ThreadIpcBufferAddr`     | —                                                     | `ipc_buffer_va`        | —       |
| `0x56` | `ThreadYield`             | —                                                     | `0`                    | —       |

`ThreadSelf` возвращает handle на текущий поток.

`ThreadYield` уступает остаток кванта. Поток встаёт в конец очереди
готовых своего приоритета. Если планировщик снова выбирает этот поток,
вызов возвращается ему же.

`ThreadTerminate` снимает поток, только если поток принадлежит процессу
вызывающего. На поток другого процесса вызов возвращает `AccessDenied` при любых
правах, а процесс целиком снимает `ProcessTerminate`. На handle текущего потока
вызов тоже возвращает `AccessDenied` даже при `WRITE`. Текущий поток завершает
`ThreadExit`.

`ThreadTerminate` не освобождает мьютексы, захваченные снятым потоком, в том числе
мьютекс кучи процесса, и они остаются занятыми навсегда. Условия безопасного
снятия — в [concurrency.md](concurrency.md).

`ThreadIpcBufferAddr` возвращает адрес IPC-буфера текущего потока в его
адресном пространстве. Программа использует его как указатель на `IpcBuffer`
для операций с портом ([Port](#port)).

Поток стартует с обнулённым регистровым состоянием: `arg` лежит в
регистре первого аргумента, прочие регистры общего назначения, указатель
локальных данных потока и регистры SIMD/FP — нули. Переключение контекста сохраняет регистровое состояние потока.
Syscall изменяет регистры возврата согласно ABI.

`exit_code` берётся из младших 32 бит аргумента и читается как `i32`.

## Memory

Вызовы памяти выделяют страницы и управляют отображениями в адресном
пространстве процесса:

- `MemoryAllocate` выделяет память без handle, `MemoryFree` освобождает
  отображение. Такая память доступна только текущему процессу.
- `MemoryCreateVirtual` возвращает handle региона. Регион можно отображать,
  создавать его срезы через `MemorySlice` и передавать другим процессам.
  Дублирование позволяет сузить права доступа.

| Op     | Имя                   | Аргументы                                                         | Возврат                                                                                       | Права                                                                                                               |
|-------:|-----------------------|-------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| `0x60` | `MemoryCreateVirtual` | `resource_h`, `size_bytes`, `access_mask`, `region_flags`         | `region_h`                                                                                    | `WRITE` на `Resource`; расходует `size/PAGE` бюджета (`ResourceExhausted` при нехватке)                             |
| `0x62` | `MemorySlice`         | `region_h`, `offset`, `size_bytes`, `access_mask`, `region_flags` | `region_h` (производный)                                                                      | `DUPLICATE` на регионе; окно `[offset, offset+size)` в границах региона, доступ не шире гранта; бюджет не расходует |
| `0x63` | `MemoryMap`           | `region_h`, `size_bytes`, `flags`                                 | `va`                                                                                          | права по `flags`                                                                                                     |
| `0x64` | `MemoryRemap`         | `va`, `size_bytes`, `flags`                                       | `0`                                                                                           | grant исходного mapping                                                                                             |
| `0x65` | `MemoryAllocate`      | `resource_h`, `size_bytes`, `flags`                               | `va`                                                                                          | `WRITE` на `Resource`; расходует `size/PAGE` бюджета (`ResourceExhausted` при нехватке)                             |
| `0x66` | `MemoryFree`          | `va`, `size_bytes`                                                | `0`                                                                                           | —                                                                                                                   |
| `0x67` | `MemoryRegionInspect` | `region_h`                                                        | primary=`size_bytes`, secondary=`base_pa \| (profile << 5) \| (kind_tag << 3) \| access_bits` | `READ`                                                                                                              |

`access_mask`: `R=1`, `W=2`, `X=4`; ноль — `InvalidArgument`; высокие биты отбрасываются.
`flags`: `0=ReadWrite`, `1=ReadOnly`, `2=ReadExecute`; `MemoryAllocate` принимает в дополнение
бит `MEMORY_ALLOCATE_GUARD_PAGE` (`1 << 8`); другие значения — `InvalidArgument`.
`region_flags`: `MemoryCreateVirtual` принимает `0` либо `MEMORY_REGION_CONTIGUOUS` (`1 << 0`),
`MemorySlice` принимает `0` либо `MEMORY_REGION_WRITE_COMBINING` (`1 << 1`); другие значения —
`InvalidArgument`.

`MemoryRegionInspect` укладывает три поля в один secondary-возврат. `base_pa`
выровнен на страницу, так что его младшие 12 бит свободны под остальные поля:

| Биты      | Поле          | Значения                                                                 |
|-----------|---------------|--------------------------------------------------------------------------|
| `[2:0]`   | `access_bits` | маска доступа региона (`R=1`, `W=2`, `X=4`)                              |
| `[4:3]`   | `kind_tag`    | `1` — `Virtual` (анонимные страницы), `2` — `Physical`                   |
| `[6:5]`   | `profile`     | `0` — `Cached`, `1` — `WriteCombining`, `2` — `Device`                   |
| `[11:7]`  | —             | ноль                                                                     |
| `[63:12]` | `base_pa`     | адрес первой страницы `Physical`- и непрерывного региона; `0` для прочих |

Значения `kind_tag` вне `1` и `2` не входят в текущий ABI.

`Resource` разрешает выделение памяти в пределах бюджета страниц по 4 KiB.
Успешный `MemoryCreateVirtual` или `MemoryAllocate` атомарно списывает
`size_bytes / PAGE_SIZE` страниц; размер должен делиться на размер страницы
нацело. Нехватка бюджета даёт `ResourceExhausted`, регион при этом не
создаётся. Ядро назначает корневой ресурс начальному процессу.
Handle своего ресурса процесс получает через `ProcessResourceSelf`.

Бюджет делится [`ResourceSplit`](#process). Вызов списывает
`budget_pages` страниц с исходного ресурса и создаёт производный со
своим счётчиком и тем же потолком доступа.
Handle производного ресурса входит в цепочку деривации исходного;
закрытие исходного handle [отзывает](#каскадный-отзыв-при-handleclose)
производные.

Производный ресурс возвращает бюджет родителю после освобождения всей
выделенной из него памяти. Регионы удерживают ресурс до возврата страниц,
даже если его handle уже закрыт.

`ProcessStart` с нулевым `resource_h` передаёт потомку ресурс вызывающего
процесса; их выделения расходуют общий бюджет. Ненулевой `resource_h`
выбирает ресурс потомка явно. Регионы сегментов и начального стека
предоставляет загрузчик. `ProcessResourceSelf` возвращает handle назначенного
процессу ресурса.

Явный `resource_h` требует `WRITE | DUPLICATE`.
Процесс сохраняет объект ресурса и права предоставленного гранта.
`ProcessResourceSelf` выдаёт handle с этими правами; запуск не добавляет
права `TRANSFER`.

Грант процесса удерживает объект ресурса независимо от исходного handle.
Закрытие этого handle не отзывает ресурс процесса и не возвращает
занятый им бюджет. Освобождение памяти и завершение процесса возвращают
бюджет по правилам ресурса.

`MemorySlice` создаёт срез с производной capability. Закрытие исходной
capability [отзывает](#каскадный-отзыв-при-handleclose) её срезы и снимает
связанные отображения. Права среза ограничены правами источника.
Срез handle только для чтения не получает `WRITE`; отсутствие `TRANSFER`
запрещает передачу среза через IPC и установку в другой процесс.

Срез виртуального региона разделяет его страницы и не расходует отдельный
бюджет. Страницы и полный бюджет исходного региона освобождаются после
освобождения всех регионов и отображений над этой памятью.

`MemoryMap` требует прав по флагу отображения: `READ` для RO,
`READ | WRITE` для RW, `READ | EXECUTE` для RX.
Размер должен совпадать с полным размером региона. Для поддиапазона
сначала создаётся `MemorySlice`.

Ядро зануляет страницы виртуального региона при первом отображении.

Повторный `MemoryMap` того же региона, в том числе в другом процессе,
сохраняет текущее содержимое. `MemoryAllocate` всегда возвращает занулённую
память. Физические регионы памяти устройств не зануляются.

С битом `MEMORY_REGION_CONTIGUOUS` вызов `MemoryCreateVirtual` выделяет
непрерывный регион из физически смежных страниц. `MemoryRegionInspect`
возвращает в `base_pa` адрес первой страницы непрерывного региона либо его
среза. Без свободного смежного участка нужной длины `MemoryCreateVirtual`
возвращает `OutOfMemory` и не расходует бюджет.

Ядро зануляет непрерывный регион при первом маппинге, в том числе данные,
которые устройство успело записать. Поэтому драйвер передаёт адрес устройству
после первого маппинга региона.

`MemoryMap` связывает отображение с использованной capability. Отображение
снимается при `MemoryFree`, закрытии capability или её
[отзыве](#каскадный-отзыв-при-handleclose). Закрытие предка снимает отображения
всего поддерева, в том числе в других процессах. Память `MemoryAllocate`
освобождается через `MemoryFree` или при завершении адресного пространства.

Бит `MEMORY_ALLOCATE_GUARD_PAGE` резервирует защитную страницу непосредственно под
маппингом `MemoryAllocate`. Ядро не отображает защитную страницу и не выдаёт её
другим маппингам процесса. Страница не расходует бюджет, и `MemoryFree` маппинга
освобождает её вместе с ним. Обращение к странице вызывает необработанное
исключение, которое завершает процесс ([Process](#process)).

### Профиль работы с памятью

Профиль задаёт, как процессор кэширует, объединяет и упорядочивает доступ к
странице. Профиль принадлежит региону: он выбран при создании, неизменен и
общий для всех маппингов этого региона во всех процессах.

| Профиль          | Кэш | Объединение записей | Порядок доступа | Назначение                           |
|------------------|-----|---------------------|-----------------|--------------------------------------|
| `Cached`         | да  | да                  | свободный       | обычная память процесса              |
| `WriteCombining` | нет | да                  | свободный       | фреймбуфер                           |
| `Device`         | нет | нет                 | сохраняется     | регистры устройства                  |

Виртуальный регион всегда имеет профиль `Cached`. Регионы устройств выдаются
драйверу с профилем `Device`.

Ядро не очищает и не инвалидирует кэш процессора для устройства. Поэтому драйвер
передаёт физический адрес `Virtual`-региона только устройству, когерентному с
кэшем процессора.

С битом `MEMORY_REGION_WRITE_COMBINING` вызов `MemorySlice` создаёт срез профиля
`WriteCombining` у региона `Device` либо `WriteCombining`. Для `Cached`-региона
вызов возвращает `InvalidArgument`. Линейная карта ядра отображает страницы
такого региона кэшируемыми, и второе отображение с иными атрибутами кэширования
нарушает когерентность.

`MemorySlice` сохраняет исходную capability. Один физический диапазон может
иметь одновременные отображения `Device` и `WriteCombining`. Оба профиля
некэшируемы, но `WriteCombining` разрешает спекулятивное чтение.
Для регистров, меняющих состояние при чтении, такой доступ меняет поведение
устройства.

Драйвер должен использовать один некэшируемый профиль окна устройства
за раз. Компонент `platform` закрепляет окно за одной сессией
([rootkeeper.md](rootkeeper.md#провижининг-устройств)).

Выбор профиля фреймбуфера реализован в
[driver-simplefb](../user/system/driver-simplefb/src/main.rs).

Запись через `WriteCombining` доходит до устройства пакетами и в
неопределённом порядке. Драйвер, которому нужен порядок между записями в
память и обращением к регистру, ставит между ними барьер.

`Cached` — единственный профиль, на котором работают exclusive-инструкции.
Примитивы синхронизации (`Futex`, `Mutex`) существуют
только в `Cached`-памяти.

## IRQ

Вызовы IRQ выдают userspace-драйверу capability аппаратной линии прерывания.
`IrqControl` разрешает выдачу линий своего диапазона. `IrqMint` возвращает
`IrqLine`; драйвер ждёт срабатывания линии через сигнальные операции.

|     Op | Имя       | Аргументы                         | Возврат      | Права                   |
|-------:|-----------|-----------------------------------|--------------|-------------------------|
| `0x70` | `IrqMint` | `irq_control_h`, `irq`, `trigger` | `irq_line_h` | `WRITE` на `IrqControl` |
| `0x71` | `IrqAck`  | `irq_line_h`                      | `0`          | `WRITE` на `IrqLine`    |

`IrqMint` создаёт `IrqLine` для линии `irq` (нижние 16 бит). Требует `WRITE` на
handle объекта `IrqControl` и попадания `irq` в его диапазон, иначе — `AccessDenied`.
Занятая линия даёт `AlreadyBound`; совместное владение линией не поддерживается.

`trigger` называет, как контроллер распознаёт активность линии. `1` — по фронту,
`2` — по уровню, иной код — `InvalidArgument`. Триггер настраивается до включения
линии, для обоих видов прерываний.

Корневой `IrqControl` создаётся ядром при старте над полосой линий, которую
сообщает контроллер платформы, и доступен держателю сессии `Hardware` (см.
[userland.md](userland.md)). Он делегируется через `TRANSFER`/`DUPLICATE`.

Порядок обслуживания:

- ждать срабатывания — `SignalWaitOne(irq_line_h, SIGNALED, …)`;
- при срабатывании ядро синхронно маскирует линию и поднимает `SIGNALED`;
- обслужив устройство, драйвер вызывает `IrqAck(irq_line_h)`: снимает бит `SIGNALED` и размаскирует линию.

Закрытие handle, который выдал `IrqMint`, отвязывает линию и отключает её на
контроллере, даже если у других процессов остались копии этого handle. Производные
отзываются вместе с handle минта. `IrqAck` по отозванной копии возвращает
`Revoked`. Закрытие копии линию не отвязывает.

## MMIO

Доступ к регистрам устройства предоставляет capability физического региона
(`RegionKind::Physical`). Ядро выдаёт её держателю сессии `Hardware`
(см. [userland.md](userland.md#контракт-bootstrap)), а компонент
`platform` выдаёт её копию драйверу.

Регион набора состоит из целых страниц, и окна с общей страницей входят в один
регион. Ядро выдаёт окно поверх RAM, только если оно целиком лежит в регионе,
который описание платформы исключает из отображения. Остальные окна поверх RAM и окна устройств, занятых драйверами ядра,
исключаются с предупреждением в журнале.

- `MemoryRegionInspect` отдаёт размер региона (primary) и его физическую базу
  `base_pa` (secondary, для сопоставления с устройством из описания
  платформы);
- `MemoryMap` маппит регистры в адресное пространство драйвера;
- доступ к регистрам — volatile-чтения/записи по полученному VA со смещением окна;
- прерывание линии устройства обслуживается через [IRQ](#irq).

Закрытие capability региона, её
[отзыв](#каскадный-отзыв-при-handleclose) или завершение процесса снимают
отображение; регистры устройства становятся недоступны.

## Process Spawning

`ProcessLoadImage` устанавливает описанные загрузчиком регионы в адресное
пространство потомка. `ProcessStart` передаёт стартовый handle и запускает
первый поток. Сигнатуры вызовов — в таблице
[Process](#process).

Стек потомка — обычный сегмент, он входит в описание образа. Регион под стек
предоставляет загрузчик наравне с регионами остальных сегментов. Регионы образа
удерживает процесс; его завершение освобождает эти ссылки.
Стек учитывается в `segment_count`.

`ProcessLoadImage` требует на region-handle `TRANSFER` и права по флагу
сегмента: `READ | WRITE` для `RW`, `READ` для `RO`, `READ | EXECUTE` для `RX`.
Установка региона делегирует потомку доступ к памяти, поэтому требует
`TRANSFER`.

### Layout `UserImageDescAbi` (40 B)

`desc_va` указывает на little-endian структуру размером `40` байт:

| Offset | Поле            | Тип   | Описание                                                   |
|-------:|-----------------|-------|------------------------------------------------------------|
|      0 | `version`       | `u32` | ABI-версия (`= 1`)                                         |
|      4 | `segment_count` | `u32` | `1..=16`                                                   |
|      8 | `segments_va`   | `u64` | user-указатель на массив `[UserSegmentAbi; segment_count]` |
|     16 | `entry_va`      | `u64` | PC первой инструкции в child AS                            |
|     24 | `user_vm_base`  | `u64` | база `user_vm`-аллокатора (4K-выровнена)                   |
|     32 | `user_vm_size`  | `u64` | размер `user_vm`-диапазона                                 |

### Layout `UserSegmentAbi` (32 B)

`segments_va` указывает на массив `segment_count` записей по `32` байта:

| Offset | Поле            | Тип   | Описание                                    |
|-------:|-----------------|-------|---------------------------------------------|
|      0 | `region_handle` | `u32` | `HandleId` региона в loader-таблице         |
|      4 | `flags`         | `u32` | `0=RW`, `1=RO`, `2=RX`                      |
|      8 | `va_base`       | `u64` | база сегмента в child AS (4K-выровнена)     |
|     16 | `mapped_size`   | `u64` | `== region.size_bytes()`                    |
|     24 | `reserved`      | `u64` | `0`                                         |

Некорректная версия ABI, нулевой/слишком большой `segment_count`,
невыровненные адреса, несовпадающий размер региона, ненулевой `reserved`
или несовместимый `access_mask` региона возвращают `InvalidArgument` /
`AccessDenied`.

### Порядок запуска

Загрузчик создаёт регионы копируемых сегментов и стека, записывает содержимое
сегментов, затем создаёт процесс и передаёт описание сегментов в
`ProcessLoadImage`.
Стек включается в список сегментов.

`ProcessStart` запускает первый поток и перемещает обязательный
стартовый handle в таблицу потомка. До этого вызова код потомка
не исполняется. Загрузчик наблюдает завершение через сигнал
процесса и получает код через `ProcessExitCode`.

Загрузчик userland реализован в
[lib/userland-loader](../lib/userland-loader/src/lib.rs).
