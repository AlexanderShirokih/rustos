# Системные вызовы

Syscall-слой принимает 16-битный номер операции и до шести аргументов
`u64`. Основной возврат — `i64`: неотрицательное значение означает
успех, отрицательное значение — `-(SyscallError as u32)`.

Вторичный возврат `u64` используется только операциями, которые явно
указаны в таблицах ниже. `HandleId` — ненулевой `u32`; `0` и значения
вне `u32` считаются неверным аргументом.

Каждая операция реестра имеет обёртку в `lib/runtime` и прямые тесты в
`user/testing/testrunner`. Обёртка снимается вместе с самой операцией. По ABI идёт
`HandleId`; вид объекта за номером записи проверяет ядро, отвечая `WrongType`.

## Права

Handle — числовой идентификатор (`u32`) в таблице текущего процесса, ссылающийся
на объект ядра. Вместе со ссылкой handle хранит маску прав, то есть набор
разрешённых операций с этим объектом. Права ядро проверяет при каждом syscall, и
нехватка нужного бита даёт `AccessDenied`.

Дублирование создаёт второй handle на тот же объект — с равным или меньшим
набором прав. Расширить права дублированием нельзя. Таблица вмещает 1024 записи,
а заполненная отвечает `OutOfHandles`.

| Право       |      Бит | Описание                                                                                                                 |
|-------------|---------:|--------------------------------------------------------------------------------------------------------------------------|
| `DUPLICATE` | `1 << 0` | разрешает создать новый handle на тот же объект с подмножеством прав                                                     |
| `TRANSFER`  | `1 << 1` | разрешает передать handle через port                                                                                     |
| `READ`      | `1 << 2` | чтение из объекта: `recv` на port, mapping памяти на чтение, ожидание сигналов, чтение метаданных                        |
| `WRITE`     | `1 << 3` | запись в объект: `send`/`call` на port, mapping памяти на запись, изменение сигналов, управление process/thread, минтинг |
| `EXECUTE`   | `1 << 4` | mapping памяти с правом исполнения                                                                                       |

## Сигналы

Сигналы — это 32-битная маска состояния объекта. Каждый бит означает наступление
своего события: появилось сообщение, объект завершился и так далее.
`SignalWaitOne` принимает маску интересующих битов и блокирует вызывающий поток,
пока хотя бы один из них не поднимется.

Ждать можно не только `Signal`. Подходит любой объект, который предъявляет
ожидаемый источник, — `Signal`, `Process`/`Thread` (бит `SIGNALED` означает
«завершён») и `IrqLine` (бит `SIGNALED` означает «сработало прерывание»). А вот
менять биты через `SignalSet` разрешено только у `Signal`.

| capability target  | Сигнал     |      Бит | Описание                   |
|--------------------|------------|---------:|----------------------------|
| `Signal`           | `SIGNALED` | `1 << 0` | событие наступило          |
| `Process`/`Thread` | `SIGNALED` | `1 << 0` | объект завершился          |
| `IrqLine`          | `SIGNALED` | `1 << 0` | сработало прерывание линии |

## Signal

Signal-вызовы — wait/signal API над `Signal`. Так как все ждущиеся события —
это `Signal`, `SignalWaitMany` ждёт "A или B" как набор `Signal`.

|     Op | Имя              | Аргументы                         | Возврат                                | Права            |
|-------:|------------------|-----------------------------------|----------------------------------------|------------------|
| `0x10` | `SignalSet`      | `handle`, `set`, `clear`, `count` | `0`                                    | `WRITE`          |
| `0x11` | `SignalWaitOne`  | `handle`, `signals`, `timeout_ns` | observed mask                          | `READ`           |
| `0x12` | `SignalWaitMany` | `items_va`, `count`, `timeout_ns` | primary=observed mask, secondary=index | `READ` на каждом |
| `0x13` | `SignalCreate`   | —                                 | `signal_h`                             | —                |

`SignalSet` принимает `count` как закрытый `WakeCount`-код:

|    `count` | Значение | Поведение                                     |
|-----------:|----------|-----------------------------------------------|
|        `0` | `None`   | выставить/снять биты, никого не будить        |
|        `1` | `One`    | разбудить одного ждущего в FIFO-порядке       |
| `u64::MAX` | `All`    | разбудить всех ждущих, чья маска пересекается |

Любое другое значение `count` возвращает `InvalidArgument`. Биты
выставляются/снимаются независимо от `count`.

`SignalCreate` создаёт объект `Signal` и регистрирует handle с полным набором
прав в таблице текущего процесса.

`signals` в `SignalWaitOne` берётся из нижних 32 бит аргумента; нулевая
маска возвращает `InvalidArgument`. `timeout_ns == 0` — poll без парковки.
Ненулевой `timeout_ns` — относительный тайм-аут в наносекундах. `Timeout`
приходит только по истечении срока. Пробуждение до него, не принёсшее сигнала,
возвращает поток в ожидание.

`SignalWaitMany.items_va` указывает на массив 8-байтных записей
`[handle: u32, mask: u32]` (little-endian); `count` ограничен
`1..=WAIT_MANY_MAX_COUNT` (256), нулевая маска в записи — `InvalidArgument`.
Возвращает primary-маску сработавшего capability target и индекс записи в `items` в
secondary-регистре. Дубликаты `handle` в `items` допустимы.

Закрытие или передача handle, на котором висит активный
`SignalWaitOne`/`SignalWaitMany`, разбудит ожидающий поток с кодом
`Canceled`. Ожидание привязано к конкретному slot+generation: после
переиспользования слота под новый handle старая регистрация cancel
не срабатывает повторно.

## Port

`Port` — синхронный rendezvous-IPC примитив. Отправитель и получатель
встречаются на одном объекте, а сам кадр сообщения лежит в per-thread IPC-буфере
вызывающего потока. Один кадр содержит до `IPC_BUFFER_DATA_MAX` байт данных и до
`IPC_BUFFER_MAX_CAPS` хэндлов.

Передача handle его перемещает. Из таблицы отправителя он удаляется и появляется
в таблице получателя. Доступа к нему у отправителя после этого не остаётся.

|     Op | Имя          | Аргументы              | Возврат              | Права   |
|-------:|--------------|------------------------|----------------------|---------|
| `0x23` | `PortCreate` | —                      | `port_h`             | —       |
| `0x24` | `PortSend`   | `handle`, `timeout_ns` | `0`                  | `WRITE` |
| `0x25` | `PortRecv`   | `handle`, `timeout_ns` | `reply_h` (либо `0`) | `READ`  |
| `0x26` | `PortCall`   | `handle`, `timeout_ns` | `0`                  | `WRITE` |
| `0x27` | `PortReply`  | `reply_handle`         | `0`                  | `WRITE` |

`PortCreate` создаёт один port-объект. Отдельного объекта на каждую сторону тут
нет — роль стороны задают права её handle: `READ` принимает, `WRITE` отправляет.
Копии handle раздаются другим процессам дублированием и переносом.

`PortSend` блокирующе отправляет кадр из IPC-буфера текущего потока и ждёт, пока
встречный `recv`/`call` его примет. `PortRecv` блокирующе принимает кадр в
IPC-буфер текущего потока; если встречным был `call`, в возврат записывается
handle одноразового `Reply`-объекта, иначе — `0`.

`PortCall` — блокирующий запрос-ответ. Кадр уходит из IPC-буфера, и ответ
оказывается в нём же. На `Reply`-handle сервер вызывает `PortReply`, доставляя
кадр из своего IPC-буфера вызывателю. `Reply` одноразов.

**Тайм-аут (`timeout_ns`).** Блокирующие `PortSend`/`PortRecv`/`PortCall`
ограничивают ожидание встречной стороны параметром `timeout_ns`:

- `PORT_TIMEOUT_INFINITE` (`u64::MAX`) — ждать бессрочно;
- `0` (`PORT_TIMEOUT_POLL`) — не блокируется. Операция либо завершается
  немедленно (встречная сторона уже ждёт), либо возвращает `Timeout`;
- иначе — относительный дедлайн в наносекундах.

При истечении тайм-аута (в т.ч. в режиме poll, когда нет встречной
стороны) syscall возвращает `Timeout` (`SYSCALL_RETURN_TIMEOUT = -9`).
Для `PortCall` тайм-аут покрывает всю операцию (ожидание получателя +
ожидание `reply`); если вызывающая сторона уходит по тайм-ауту, не
дождавшись ответа, сервер при попытке `PortReply` получит `PeerClosed`,
а IPC-буфер вызывателя не будет затронут.

**Доставка badge.** На `PortRecv`/`PortCall` ядро записывает в поле
`IpcBuffer.badge` получателя значок port-хендла отправителя (`0`, если
хендл незаклеймён). Значок пишется получателю всегда, даже при пустом
теле; на стороне отправителя поле `badge` не читается, и ответ
`PortReply` его не передаёт.

**Живость сторон.** Порт считает своих держателей — capability с `READ`
(получатели) и capability со значком и `WRITE` (отправители этого значка).

На порту без получателей `PortSend` и `PortCall` возвращают `PeerClosed`, не
блокируясь. Тем же кодом обнуление множества получателей будит уже припаркованные
`PortSend`, `PortCall` и `PortRecv`.

Уход последнего держателя значка достаётся очередному `PortRecv` кодом
`SenderGone`. Кадра при этом не приходит, значок ушедшей стороны лежит в
`IpcBuffer.badge`, а `tag`, `data` и `caps` остаются нетронутыми. Механизм и
правила владения — в [port.md](port.md).

Содержимое кадра — байты и хэндлы — кодируется в IPC-буфере по адресу, который
возвращает `ThreadIpcBufferAddr` (op `0x55`). Wire-формат типизированного IPC
поверх этого транспорта описан в [ipc.md](ipc.md), и синхронность нижележащей
доставки на него никак не влияет.

Пример: клиент шлёт запрос сервису и ждёт ответ.

```rust
let ipc = ipc_buffer_addr() as *mut IpcBuffer;
// уложить кадр запроса в IPC-буфер
write_request_frame(ipc, request);
// блокирующий запрос-ответ: ответ окажется в том же IPC-буфере
port_call(service_h, PORT_TIMEOUT_INFINITE);
let response = read_response_frame(ipc);
```

## Handle

Handle-вызовы управляют временем жизни handle в таблице текущего
процесса. Закрытие удаляет запись из таблицы; если это была последняя
ссылка на объект, объект освобождается.

|     Op | Имя               | Аргументы                       | Возврат      | Права       |
|-------:|-------------------|---------------------------------|--------------|-------------|
| `0x30` | `HandleClose`     | `handle`                        | `0`          | —           |
| `0x31` | `HandleDuplicate` | `handle`, `new_rights`, `badge` | `new_handle` | `DUPLICATE` |

### Каскадный отзыв при `HandleClose`

`HandleDuplicate` (копия — производная исходного handle) и `MemorySlice`
(под-регион — производная нарезанного) строят граф деривации. Перенос
капы через Port двигает handle целиком, граф деривации переносится с ним
и сохраняется при межпроцессной передаче.

Минт значка на port-капе регистрирует на порту запись отправителей этого
значка ([port.md](port.md#уход-значка)). Минт упирается в события об
уходе значка, которые накопились на порту и остались непрочитанными.
Набрав потолок, порт не создаёт новых записей, и `HandleDuplicate` со
значком возвращает `ResourceExhausted`, пока `PortRecv` не разберёт
скопившиеся `SenderGone`. Минт со значком, запись которого на порту уже
есть, проходит и на потолке.

`HandleClose` (а также завершение таблицы вместе с процессом) **отзывает
всё поддерево производных** закрываемой капы:

- производные, в том числе в **чужих** таблицах, становятся невалидными —
  любая операция над ними возвращает `Revoked`;
- для memory-капы дополнительно **срываются активные маппинги**
  поддерева (PTE снимаются, range возвращается аллокатору), в том числе в
  чужом адресном пространстве.

Каскад идёт **строго вниз** по графу, и сиблинги с предками закрываемой капы
доступ сохраняют. Перенос **корневой** капы (не производной) — безвозвратная
передача владения. Узла грантор за собой не оставляет, и отзывать оказывается
некому.

Два режима раздачи памяти (и любого capability target) выражаются одним примитивом:

- `transfer` корня — handover (отозвать нельзя);
- `duplicate` -> `transfer` производной — отзываемая "аренда":
  закрыл/завершился грантор -> производная у получателя отозвана
  (`Revoked`).

Гранулярность идёт по клиентам. Грантор держит на каждого клиента отдельный
промежуточный узел (`duplicate` под клиента, передать клиенту уже его
производную). Закрыл узел клиента — отвалился только он; закрыл корень —
отвалились все.

Закрытие уже отозванного слота допустимо и освобождает слот, при этом
капа не "застревает".

`new_rights` берётся из нижних 32 бит `arg1` (неизвестные биты отбрасываются) и
обязан быть подмножеством прав исходного хендла. `badge` (полные 64 бита `arg2`,
`0` = без значка) применяется по семантике **set-once**:

- источник не заклеймён (`badge == 0`) и `arg2 != 0` — новый хендл заклеймён
  значком `arg2`;
- источник не заклеймён и `arg2 == 0` — новый хендл без значка;
- источник заклеймён и `arg2 == 0` — новый хендл наследует значок источника;
- источник заклеймён и `arg2 != 0` — попытка переклеймить, ошибка `BadHandle`.

Минт значка (`arg2 != 0` и `WRITE` в `new_rights`) делает значок живым на порту.
Непрочтённое событие о его уходе при этом снимается, и сервер может
переиспользовать значения, не закрывая живую сессию (см. [port.md](port.md)).

Badge — свойство хендла, а не объекта, и разные копии одного и того же
port содержат разные значки. На приёме сообщения ядро доставляет
badge отправителя получателю (см. [Port](#port)).

Пример: выдать дочернему процессу только право ожидания (без значка).

```rust
let wait_only = handle_duplicate(process_h, Rights::READ | Rights::TRANSFER, 0)?;

// Сервер минтит badged-копию port под конкретного клиента:
let client_ep = handle_duplicate(port_h, Rights::WRITE | Rights::TRANSFER, CLIENT_BADGE)?;
```

## Process

Process-вызовы создают процесс, возвращают handle на текущий процесс и
позволяют наблюдать или принудительно завершать процесс по handle.

|     Op | Имя                   | Аргументы                                                                         | Возврат               | Права                                                                    |
|-------:|-----------------------|-----------------------------------------------------------------------------------|-----------------------|--------------------------------------------------------------------------|
| `0x40` | `ProcessCreate`       | `name_va`, `name_len`                                                             | `process_h`           | —                                                                        |
| `0x41` | `ProcessSelf`         | —                                                                                 | `process_h`           | —                                                                        |
| `0x42` | `ProcessLoadImage`    | `process_h`, `desc_va`, `desc_len`                                                | `0`                   | `WRITE` на `process_h`; `WRITE` + права по флагу на каждом region-handle |
| `0x43` | `ProcessExitCode`     | `process_h`                                                                       | `exit_code` как `u32` | `READ`                                                                   |
| `0x44` | `ProcessTerminate`    | `process_h`, `exit_code`                                                          | `0`                   | `WRITE`                                                                  |
| `0x45` | `ProcessStart`        | `process_h`, `entry_pc`, `user_sp`, `bootstrap_handle`, `priority`, `resource_h` | `thread_h`            | `WRITE` на `process_h`; `TRANSFER` на `bootstrap_handle`; `WRITE` и `DUPLICATE` на `resource_h` |
| `0x46` | `ProcessResourceSelf` | —                                                                                 | `resource_h`          | —                                                                        |
| `0x47` | `ResourceSplit`       | `resource_h`, `budget_pages`                                                      | `resource_h` (производный) | `WRITE` и `DUPLICATE` на `resource_h`                               |
| `0x48` | `ProcessExit`         | `exit_code`                                                                       | не возвращается       | —                                                                        |

Завершение процесса наблюдается ожиданием по `process_h`
(`SignalWaitOne`/`Many`, бит `SIGNALED`).

Необработанное исключение userspace-процесса завершает процесс так же, как
`ProcessTerminate`. Все потоки и capability процесса освобождаются, а
`ProcessExitCode` возвращает служебный отрицательный код как `u32`.
Конкретное значение не является частью ABI.

Незавершённый процесс снимается уходом последнего держателя capability с правом
`WRITE` - тем же путём и с отдельным служебным кодом, в том числе когда последний
держатель - сам процесс. Процессы, которые снятый держал, снимаются по тому же
правилу. Процесс, на который capability не выдавалась ни разу, снимается только
явным завершением.

`ProcessCreate` копирует имя процесса из user-памяти, требует корректный UTF-8
и ограничение `1 <= name_len <= 64` байт. Пустое имя (`name_len == 0`)
отвергается (`InvalidArgument`).

`ProcessLoadImage` и `ProcessStart` описаны подробно в разделе
[Process Spawning](#process-spawning).

`ProcessStart` создаёт первый поток процесса и возвращает handle на него.
`bootstrap_handle` (x3) — HandleId обязательного стартового хэндла-канала из таблицы loader-процесса.
Ядро изымает его из caller-таблицы (`TRANSFER`) и устанавливает в child-таблицу без права
`TRANSFER`. Значок и остальные права handle сохраняются.
`priority` (x4) задаёт нижними 8 битами приоритет потока, а биты [8..)
зарезервированы и обязаны быть нулевыми. `entry_pc` (x1) и `user_sp` (x2)
записываются в стартовый user-контекст первого потока. `resource_h` (x5) задаёт
метеринг-`Resource` стартуемого процесса; нулевой `resource_h` отдаёт потомку
`Resource` вызывающего (caller).

`ProcessSelf` возвращает handle на текущий процесс. Эта capability держателем
не считается и время жизни процесса не продлевает.
`ProcessResourceSelf` возвращает handle на метеринг-`Resource` текущего процесса (объект, из бюджета которого 
списываются аллокации памяти).

`ResourceSplit` выделяет `budget_pages` страниц бюджета в отдельный `Resource` с
тем же физдиапазоном и потолком доступа (см. [Memory](#memory)). Глубина цепочки
производных ограничена восемью уровнями. Производный ресурс удерживает предков в
куче ядра даже после отзыва их хэндлов. На потолке глубины `ResourceSplit`
возвращает `ResourceExhausted`.

Для self-exit `ProcessTerminate` не годится — на handle текущего процесса он
возвращает `AccessDenied` даже при `WRITE`. Собственное завершение идёт через
`ProcessExit` либо `ThreadExit`, и последний поток процесса помечает процесс
завершённым.

`ProcessExit` снимает все потоки текущего процесса разом, включая те, что стоят в
ожидании, и публикует `exit_code` как код выхода процесса. Хэндла вызов не берёт —
полномочие на собственный процесс есть у каждого потока по построению.
`ThreadExit` уносит только вызывающий поток, так что процессу с несколькими
потоками нужен именно `ProcessExit`.

Завершение необратимо: `ProcessStart` и `ThreadCreate` на handle завершённого процесса возвращают `WrongType`.

Типичный сценарий user-spawn состоит из трёх шагов: `ProcessCreate`,
 `ProcessLoadImage`, затем `ProcessStart`. Между `LoadImage` и
`Start` никакой поток в child-процессе ещё не исполняется.

Пример: создатель процесса делегирует наблюдение за ним стороннему процессу через производную capability.

```rust
// сторона создателя (process_h - handle на дочерний процесс; report_h - port к наблюдателю)
let wait_h = handle_duplicate(process_h, Rights::READ | Rights::TRANSFER, 0)?;
let ipc = ipc_buffer_addr() as *mut IpcBuffer;
write_cap_frame(ipc, wait_h);
port_send(report_h, PORT_TIMEOUT_INFINITE);

// --- сторона наблюдателя (monitor_h - тот же port) ---
port_recv(monitor_h, PORT_TIMEOUT_INFINITE);
let monitored_h = read_cap_frame(ipc).expect("peer transferred wait_h");

let observed = signal_wait_one(monitored_h, SIGNALED, timeout_ns);
if observed as u32 & SIGNALED != 0 {
    let code = process_exit_code(monitored_h);
}
```

## Thread

Thread-вызовы создают поток в процессе, возвращают handle на текущий
поток и управляют завершением потока.

|     Op | Имя                       | Аргументы                                             | Возврат                | Права   |
|-------:|---------------------------|-------------------------------------------------------|------------------------|---------|
| `0x50` | `ThreadCreate`            | `process_h`, `entry_pc`, `user_sp`, `arg`, `priority` | `thread_h`             | `WRITE` |
| `0x51` | `ThreadSelf`              | —                                                     | `thread_h`             | —       |
| `0x52` | `ThreadExit`              | `exit_code`                                           | не возвращается        | —       |
| `0x53` | `ThreadExitCode`          | `thread_h`                                            | `exit_code` как `u32`  | `READ`  |
| `0x54` | `ThreadTerminate`         | `thread_h`, `exit_code`                               | `0`                    | `WRITE` |
| `0x55` | `ThreadIpcBufferAddr`     | —                                                     | `ipc_buffer_va`        | —       |
| `0x56` | `ThreadYield`             | —                                                     | `0`                    | —       |

`ThreadSelf` возвращает handle на текущий поток.

`ThreadYield` уступает остаток кванта. Поток встаёт в конец очереди
готовых своего приоритета и остаётся runnable. Может не оказаться
готовых потоков того же приоритета — тогда вызов возвращается тому же
потоку.

Для self-exit `ThreadTerminate` не годится — на handle текущего потока он
возвращает `AccessDenied` даже при `WRITE`. Текущий поток завершает `ThreadExit`.

Замков процесса `ThreadTerminate` за снятым потоком не отпускает, и захваченный
им `Mutex` (в том числе мьютекс кучи) остаётся занятым навсегда. Условия
безопасного снятия — в [concurrency.md](concurrency.md).

`ThreadIpcBufferAddr` возвращает user-VA per-thread IPC-буфера текущего потока. Адрес используется как указатель
на `IpcBuffer` перед каждым port-вызовом (см. секцию [Port](#port)).

Поток стартует с обнулённым регистровым состоянием: `arg` лежит в
регистре первого аргумента, прочие регистры общего назначения, указатель
локальных данных потока и регистры SIMD/FP — нули. Дальше регистровое
состояние приватно потоку. Ядро сохраняет и восстанавливает его вокруг
обработки исключения, так что ни syscall, ни переключение контекста его
не меняют.

`exit_code` берётся из младших 32 бит аргумента и читается как `i32`.

Пример: создать worker-поток и дождаться его exit code.

```rust
fn worker_entry() -> ! {
    thread_exit(0)
}

let process_h = process_self()?;
let thread_h = thread_create(process_h, worker_entry as u64, worker_sp, 0, priority)?;

let observed = signal_wait_one(thread_h, SIGNALED, timeout_ns);
if observed as u32 & SIGNALED != 0 {
    let code = thread_exit_code(thread_h);
}
```

## Memory

Memory-вызовы выделяют память и управляют её маппингом в адресное
пространство процесса. Есть два режима:

- **anonymous** (`MemoryAllocate` / `MemoryFree`) — быстрое выделение
  без handle; такую память нельзя передать другому процессу или
  задублировать с другими правами;
- **region handle** (`MemoryCreateVirtual`) — возвращает handle на регион,
  который можно замапить, нарезать на под-регионы (`MemorySlice`), передать
  через port или задублировать с уменьшенными правами.

| Op     | Имя                   | Аргументы                                         | Возврат                                                                                       | Права                                                                                                               |
|-------:|-----------------------|---------------------------------------------------|-----------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| `0x60` | `MemoryCreateVirtual` | `resource_h`, `size_bytes`, `access_mask`         | `region_h`                                                                                    | `WRITE` на `Resource`; расходует `size/PAGE` бюджета (`ResourceExhausted` при нехватке)                             |
| `0x61` | `MemoryWithProfile`   | `region_h`, `profile`                             | `region_h` (производный)                                                                      | `DUPLICATE` на регионе; профиль меняется в пределах некэшируемых; бюджет не расходует                               |
| `0x62` | `MemorySlice`         | `region_h`, `offset`, `size_bytes`, `access_mask` | `region_h` (производный)                                                                      | `DUPLICATE` на регионе; окно `[offset, offset+size)` в границах региона, доступ не шире гранта; бюджет не расходует |
| `0x63` | `MemoryMap`           | `region_h`, `size_bytes`, `flags`                 | `va`                                                                                          | `WRITE` и права по `flags`                                                                                          |
| `0x64` | `MemoryRemap`         | `va`, `size_bytes`, `flags`                       | `0`                                                                                           | grant исходного mapping                                                                                             |
| `0x65` | `MemoryAllocate`      | `resource_h`, `size_bytes`, `flags`               | `va`                                                                                          | `WRITE` на `Resource`; расходует `size/PAGE` бюджета (`ResourceExhausted` при нехватке)                             |
| `0x66` | `MemoryFree`          | `va`, `size_bytes`                                | `0`                                                                                           | —                                                                                                                   |
| `0x67` | `MemoryRegionInspect` | `region_h`                                        | primary=`size_bytes`, secondary=`base_pa \| (profile << 5) \| (kind_tag << 3) \| access_bits` | `READ`                                                                                                              |

`access_mask`: `R=1`, `W=2`, `X=4`; ноль — `InvalidArgument`; высокие биты отбрасываются.
`flags`: `0=ReadWrite`, `1=ReadOnly`, `2=ReadExecute`; `MemoryAllocate` принимает в дополнение
бит `MEMORY_ALLOCATE_GUARD_PAGE` (`1 << 8`); другие значения — `InvalidArgument`.
`profile`: `0=Cached`, `1=WriteCombining`, `2=Device`; другие значения — `InvalidArgument`.

`MemoryRegionInspect` укладывает три поля в один secondary-возврат. `base_pa`
выровнен на страницу, так что его младшие 12 бит свободны под остальные поля:

| Биты      | Поле          | Значения                                                   |
|-----------|---------------|------------------------------------------------------------|
| `[2:0]`   | `access_bits` | маска доступа региона (`R=1`, `W=2`, `X=4`)                |
| `[4:3]`   | `kind_tag`    | `1` — `Virtual` (анонимные страницы), `2` — `Physical`     |
| `[6:5]`   | `profile`     | `0` — `Cached`, `1` — `WriteCombining`, `2` — `Device`     |
| `[11:7]`  | —             | ноль                                                       |
| `[63:12]` | `base_pa`     | физическая база `Physical`-региона; `0` для `Virtual`      |

Теги `kind_tag` перечислены целиком, и значение вне `1`/`2` означает дрейф
ABI.

`Resource` — полномочие на минтинг памяти, включающее **бюджет** (счётчик
страниц по 4 KiB). Каждый успешный `MemoryCreateVirtual` / `MemoryAllocate`
атомарно списывает с бюджета ресурса `size_bytes / PAGE_SIZE` страниц (обязана
делиться нацело). При нехватке бюджета операция возвращает `ResourceExhausted`
и регион не создаётся. Корневой `Resource` создаётся ядром при старте и доступен bootstrap-процессу
через контракт Bootstrap-канала (см. [userland.md](userland.md)).

Бюджет делится [`ResourceSplit`](#process). Вызов списывает
`budget_pages` страниц с исходного ресурса и создаёт производный со
своим счётчиком, тем же физдиапазоном и тем же потолком доступа.
Производный ресурс — капа-потомок исходной, и закрытие исходной
[отзывает](#каскадный-отзыв-при-handleclose) заодно и его.

Уход производного ресурса возвращает исходному его бюджет, и происходит это в два
шага. Сначала регионы, выданные на этом бюджете, возвращают свои страницы
ресурсу. Затем ресурс отдаёт весь счётчик родителю. Сам ресурс сохраняется дольше
выданных из него регионов, так что страницы не теряются, даже если его капу
закрыли раньше.

Метеринг-`Resource` наследуется: `ProcessStart` с нулевым `resource_h` передаёт
потомку тот же `Resource`, что у caller, и тогда всё дерево процессов списывает
из одного общего пула. Явный `resource_h` даёт потомку отдельный бюджет
аллокаций; сегменты и стек его образа при этом минтит загрузчик со своего
ресурса. `ProcessResourceSelf` отдаёт handle на ресурс текущего процесса, каким
бы из двух способов он ни назначен.

Явный `resource_h` требует `WRITE` и `DUPLICATE` — тот же набор, что и
`ResourceSplit`. Отдача ресурса потомку размещает капу на него в чужой таблице,
то есть является той же самой деривацией.

Права капы, которую потомку выдаёт `ProcessResourceSelf`, — это права самого
`resource_h` на старте, а при наследовании — права гранта родителя. Капа без
`TRANSFER` делегируемой от старта процесса не становится.

Ресурс достаётся потомку объектом, а не производной капой, и граф деривации его
не покрывает. Закрытие `resource_h` у родителя не отзывает метеринг потомка и
бюджета не возвращает. Возвращает его завершение процесса — вместе с его
регионами.

`MemorySlice` отдаёт под-регион производной капой нарезанного. Закрытие
исходной капы [отзывает](#каскадный-отзыв-при-handleclose) все окна,
которые из неё нарезаны, вместе с их маппингами. Права под-региона —
стартовые для региона, суженные правами источника. Срез read-only капы
не получит `WRITE`, а срез капы без `TRANSFER` дальше не передаётся.

Нарезка поддерживает оба вида backing. Для `Physical` происхождение окна
проверяется по PA, для `Virtual` — по общему владельцу списка фреймов и
вложенности страничных окон.

Virtual-срез не копирует фреймы и своего metering-обязательства не создаёт. И
фреймы, и возврат полного бюджета исходного региона держатся до последнего
региона либо маппинга над любым его окном.

`MemoryMap` требует, чтобы `size_bytes` совпадал с полным размером
региона; он не поддерживает частичный mapping поддиапазона.

Страницы региона с `Virtual` backing ядро зануляет при первом маппинге региона.
В свежей памяти процесс получает нули, а не содержимое, оставшееся от прежнего
владельца фрейма.

Зануление одноразовое. Повторный `MemoryMap` того же региона, в том числе в
другом процессе, отдаёт текущее содержимое — на этом и стоит разделяемая память.
`MemoryAllocate` создаёт новый регион на каждый вызов и потому всегда возвращает
занулённую память. На `Physical` backing (device-окна) зануление не
распространяется.

`MemoryMap` привязывает установленный маппинг к той capability, через которую он
сделан, и существует маппинг ровно столько, сколько сама эта капа. `MemoryFree` и
[отзыв капы](#каскадный-отзыв-при-handleclose) идут через один и тот же teardown.
Поэтому `HandleClose` региона — своего или у предка по деривации — снимает
активные маппинги всего поддерева, в том числе кросс-процессно. У
`MemoryAllocate` публичной капы нет вовсе, и его маппинг снимает только
`MemoryFree` либо завершение AS.

Бит `MEMORY_ALLOCATE_GUARD_PAGE` резервирует защитную страницу непосредственно под
маппингом `MemoryAllocate`. Ядро не отображает защитную страницу и не выдаёт её
другим маппингам процесса. Страница не расходует бюджет, и `MemoryFree` маппинга
освобождает её вместе с ним. Обращение к странице вызывает необработанное
исключение, которое завершает процесс ([Process](#process)).

Пример: временный рабочий буфер.

```rust
let resource_h = process_resource_self()?;
let buf_va = memory_allocate(resource_h, 4096, 0 /* ReadWrite */);

copy_to_user_buffer(buf_va as u64, payload);
memory_remap(buf_va, 4096, 1 /* ReadOnly */);

send_read_only_buffer(buf_va, 4096);
memory_free(buf_va, 4096);
```

Пример: создать регион, записать данные и передать его другому процессу.

```rust
let resource_h = process_resource_self()?;
let region_h = memory_create_virtual(resource_h, 4096, 3 /* R|W */)?;
let shared_va = memory_map(region_h, 4096, 0 /* ReadWrite */);

write_payload(shared_va as *mut u8, payload);

let readonly_h = handle_duplicate(region_h, Rights::READ | Rights::TRANSFER, 0)?;
// уложить readonly_h как cap в IPC-буфер и отправить peer
let ipc = ipc_buffer_addr() as *mut IpcBuffer;
write_cap_frame(ipc, readonly_h);
port_send(peer_h, PORT_TIMEOUT_INFINITE);
```

### Профиль работы с памятью

Профиль задаёт, как процессор кэширует, объединяет и упорядочивает доступ к
странице. Профиль принадлежит региону: он выбран при создании, неизменен и
общий для всех маппингов этого региона во всех процессах.

| Профиль          | Кэш | Объединение записей | Порядок доступа | Назначение                           |
|------------------|-----|---------------------|-----------------|--------------------------------------|
| `Cached`         | да  | да                  | свободный       | обычная память процесса              |
| `WriteCombining` | нет | да                  | свободный       | фреймбуфер, буфер обмена с DMA       |
| `Device`         | нет | нет                 | сохраняется     | регистры устройства                  |

Регион с `Virtual` backing всегда `Cached`. Device-окна, выданные драйверу,
приходят как `Device`.

`MemoryWithProfile` отдаёт производную капу того же PA-диапазона с
другим профилем. Профиль меняется в пределах `WriteCombining` и
`Device`, потому что страницы `Cached`-региона отображены ещё и линейной
картой ядра, и второе отображение с иными атрибутами кэширования теряет
когерентность. Переход в `Cached` и из него возвращает
`InvalidArgument`.

Этим запретом ядро держит ровно один инвариант уровня физической страницы.
Кэшируемое и некэшируемое отображение одного PA не сосуществуют. Ничего более
сильного ядро не гарантирует.

Исходная капа при деривации сохраняется, да и `MemorySlice` точно так же даёт
второе окно поверх того же PA. Поэтому один PA-диапазон допускает одновременные
`Device`- и `WriteCombining`-отображения. Оба некэшируемы, и когерентность на
этом не теряется. Разница всё же есть: `WriteCombining` разрешает спекулятивное
чтение, а для регистров, меняющих состояние по чтению, это уже наблюдаемо.

Держать на окне устройства один некэшируемый профиль за раз — обязанность
драйвера. Композиция ему в этом помогает: одно и то же окно достаётся ровно
одному компоненту ([rootkeeper.md](rootkeeper.md)).

Драйвер фреймбуфера выбирает профиль перед маппингом окна:

```rust
let window_h = /* device-окно из ответа на требование mmio */;
let framebuffer_h = memory_with_profile(window_h, 1 /* WriteCombining */)?;
let va = memory_map(framebuffer_h, size, 0 /* ReadWrite */);
```

Запись через `WriteCombining` доходит до устройства пакетами и в
неопределённом порядке. Драйвер, которому нужен порядок между записями в
память и обращением к регистру, ставит между ними барьер.

`Cached` — единственный профиль, на котором работают exclusive-инструкции.
Отсюда и жёсткая привязка. Примитивы синхронизации (`Futex`, `Mutex`) существуют
только в `Cached`-памяти.

## IRQ

IRQ-вызовы выдают userspace-драйверу аппаратную линию прерывания как
capability. `IrqControl` содержит полномочие минтить линии
(range-bounded, как `Resource` для физпамяти). Минтинг возвращает
`IrqLine` — привязанную линию, срабатывание которой userspace ждёт как
обычный сигнал.

|     Op | Имя       | Аргументы                         | Возврат      | Права                   |
|-------:|-----------|-----------------------------------|--------------|-------------------------|
| `0x70` | `IrqMint` | `irq_control_h`, `irq`, `trigger` | `irq_line_h` | `WRITE` на `IrqControl` |
| `0x71` | `IrqAck`  | `irq_line_h`                      | `0`          | `WRITE` на `IrqLine`    |

`IrqMint` минтит `IrqLine` для линии `irq` (нижние 16 бит). Требует `WRITE` на
`IrqControl`-хендле и попадания `irq` в его диапазон, иначе — `AccessDenied`.
Занятая линия отвечает `AlreadyBound`: разделяемых линий здесь не бывает.

`trigger` называет, как контроллер распознаёт активность линии. `1` — по фронту,
`2` — по уровню, иной код — `InvalidArgument`. Триггер настраивается до включения
линии, и edge-устройство проходит настройку тем же путём, что уровневое.

Корневой `IrqControl` создаётся ядром при старте над полосой линий, которую
сообщает контроллер платформы, и доступен bootstrap-процессу через контракт
Bootstrap-канала. Делегируется он через `TRANSFER`/`DUPLICATE`.

Ожидание и подтверждение (линии GIC уровневые):

- ждать срабатывания — `SignalWaitOne(irq_line_h, SIGNALED, …)`;
- при срабатывании ядро синхронно маскирует линию и поднимает `SIGNALED` (для уровневой линии это обязательно — иначе interrupt storm);
- обслужив устройство, драйвер вызывает `IrqAck(irq_line_h)`: снимает latch `SIGNALED` и размаскирует линию. 

Закрытие последнего хендла `IrqLine` отвязывает линию и отключает её на
контроллере.

## MMIO

Доступ к регистрам устройства — memory-капа поверх **физического**
диапазона (`RegionKind::Physical`). Ядро выдаёт капу через
Bootstrap-канал (`acquire_device_memory(index)`, см.
[userland.md](userland.md)), rootkeeper выдаёт её драйверу по его требованию
`mmio`.

- `MemoryRegionInspect` отдаёт размер региона (primary) и его физическую базу
  `base_pa` (secondary, для корреляции с FDT-узлом устройства);
- `MemoryMap` маппит регистры в адресное пространство драйвера;
- доступ к регистрам — volatile-чтения/записи по полученному VA;
- прерывание линии устройства обслуживается через [IRQ](#irq).

Закрытие memory-капы (или завершение процесса) снимает маппинг тем же
[каскадным teardown](#каскадный-отзыв-при-handleclose), и регистры устройства
становятся недоступны.

Пример: драйвер маппит регистры устройства и обслуживает его прерывание.

```rust
let (region_size, _meta) = memory_region_inspect(device_region_h);
let regs_va = memory_map(device_region_h, region_size as u64, 0 /* ReadWrite */);
let regs = regs_va as *mut u32;

let irq_h = irq_mint(irq_control_h, DEVICE_IRQ)?;
loop {
    let observed = signal_wait_one(irq_h, SIGNALED, PORT_TIMEOUT_INFINITE);
    if observed as u32 & SIGNALED != 0 {
        let _status = unsafe { core::ptr::read_volatile(regs) };
        unsafe { core::ptr::write_volatile(regs, ACK_BIT) };
        irq_ack(irq_h);
    }
}
```

## Process Spawning

`ProcessLoadImage` загружает произвольный образ и одним syscall поручает
ядру установить эти регионы в child AS; `ProcessStart` атомарно стартует
первый поток вместе с bootstrap-хэндлом. Сигнатуры обоих — в таблице
[Process](#process).

Стек потомка — обычный сегмент, отдельно ядро его не различает. Регион под стек
минтит загрузчик со своего `Resource` и передаёт наравне с остальными. Оттого вся
память child AS оплачена бюджетом и учтена. Регионы образа держит сам процесс, и
их бюджет возвращает его завершение. Один слот `segment_count` при этом уходит
под стек.

Для `ProcessLoadImage` необходимые права на region-handle зависят от флага
сегмента: `WRITE | READ` для `RW`, `WRITE | READ` для `RO`, `WRITE | READ | EXECUTE`
для `RX`. Иными словами, `WRITE` на region-handle требуется всегда (он авторизует установку маппинга в чужой AS).

### Layout `UserImageDescAbi` (40 B)

`desc_va` указывает на little-endian структуру размером `40` байт:

| Offset | Поле            | Тип   | Описание                                                   |
|-------:|-----------------|-------|------------------------------------------------------------|
|      0 | `version`       | `u32` | ABI-версия (`= 1`)                                         |
|      4 | `segment_count` | `u32` | `1..=16`                                                   |
|      8 | `segments_va`   | `u64` | user-указатель на массив `[UserSegmentAbi; segment_count]` |
|     16 | `entry_va`      | `u64` | PC первой инструкции в child AS                            |
|     24 | `user_vm_base`  | `u64` | база `user_vm`-аллокатора (4K-выровнена)                   |
|     32 | `user_vm_size`  | `u64` | размер `user_vm`-диапазона                                 |

### Layout `UserSegmentAbi` (32 B)

`segments_va` указывает на массив `segment_count` записей по `32` байта:

| Offset | Поле            | Тип   | Описание                                    |
|-------:|-----------------|-------|---------------------------------------------|
|      0 | `region_handle` | `u32` | `HandleId` региона в loader-таблице         |
|      4 | `flags`         | `u32` | `0=RW`, `1=RO`, `2=RX`                      |
|      8 | `va_base`       | `u64` | база сегмента в child AS (4K-выровнена)     |
|     16 | `mapped_size`   | `u64` | `== region.size_bytes()`                    |
|     24 | `reserved`      | `u64` | `0`                                         |

Некорректная версия ABI, нулевой/слишком большой `segment_count`,
невыровненные адреса, несовпадающий размер региона, ненулевой `reserved`
или несовместимый `access_mask` региона возвращают `InvalidArgument` /
`AccessDenied`.

### Pipeline (loader-side)

```text
PortCreate                                       -> bootstrap_h
resource_h = process_resource_self()             -> resource_h
MemoryCreateVirtual(resource_h, size, R|W|X)     -> region_h
MemoryMap(region_h, size, RW)                    -> seg_va  // в loader-AS
copy image bytes -> seg_va                                  // CPU stores
MemoryRemap(seg_va, size, RX)                               // если нужен RX
ProcessCreate("child")                           -> proc_h
MemoryCreateVirtual(resource_h, stack_size, R|W)  -> stack_region_h  // стек - сегмент
build UserImageDescAbi + [UserSegmentAbi; N] на стеке loader-а
ProcessLoadImage(proc_h, desc_va, 40)            -> 0
MemoryFree(seg_va, size)                                    // фреймы остаются за child
ProcessStart(proc_h, entry_pc, user_sp, bootstrap_h, prio, resource_h)
                                                 -> thread_h
SignalWaitOne(proc_h, SIGNALED, ...)             // ожидание прямо по process-handle
ProcessExitCode(proc_h)                          -> exit_code
```
