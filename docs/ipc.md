# IPC

Процессы обмениваются данными через синхронный port ядра (`Port`):
rendezvous-примитив, на котором отправитель и получатель встречаются, а сам кадр
лежит в per-thread IPC-буфере вызывающего потока. Port переносит сырые байты
и хэндлы; чтобы стороны понимали друг друга, нужен общий формат сообщения и общий
набор операций. IPC задаёт это поверх port'а: вызов именованной операции с
типизированными аргументами превращается в кадр в IPC-буфере, синхронно
доставляется на встречную сторону, а из ответного кадра восстанавливается
результат или ошибка. Набор операций и их типов, о котором договорились два
процесса, — контракт; прикладной код работает в его терминах и не касается байтов,
тегов и смещений.

## Обмен

У port'а две роли: одна сторона вызывает операции (клиент), другая выполняет
(сервер). Каждый вызов и каждый ответ — одно сообщение, один кадр.

Операция бывает трёх видов:

- two-way: клиент шлёт запрос и ждёт ответ;
- one-way клиент -> сервер: запрос без ответа;
- событие сервер -> клиент: уведомление без ответа.

Ответ two-way несёт один из трёх исходов:

| Исход           | Через port                       |
|-----------------|--------------------------------------|
| успех           | значение `T`, соединение живо        |
| доменная ошибка | значение `E`, соединение живо        |
| сбой протокола  | код причины, соединение закрывается  |

Доменная ошибка — часть контракта (тип `E`): ожидаемый отказ, после которого
обмен продолжается. Сбой протокола (незнакомая операция, битый кадр) закрывает
соединение.

## Идентификация клиента (badge)

Сервер обслуживает много клиентов через ОДИН port, не создавая отдельных
объектов под каждого. Чтобы различать, от кого пришёл кадр, используется
**badge** — значок, привязанный к port-хендлу (аналог badges в seL4).
Сервер минтит несколько копий своего port-хендла через `handle_duplicate`,
каждой назначая свой badge (set-once: заклеймить можно только незаклеймённый
хендл, переклеймить нельзя), и раздаёт копии клиентам. Клиент шлёт через свою
копию; ядро на приёме (`recv`/`call`) кладёт badge отправителя в
`IpcBuffer.badge` сервера. Так сервер сопоставляет кадр с клиентом/соединением
без опоры на koid — koid остаётся лишь диагностическим идентификатором и в
авторизации/маршрутизации IPC не участвует. Подробности ABI — в
[syscalls.md](syscalls.md#port).

## Кадр

Сообщение — один кадр: заголовок 14 байт и тело переменной длины. Кадр
укладывается целиком в data-область IPC-буфера и собирается без аллокации в куче.
Все целые — little-endian.

### Заголовок

| Смещение | Размер | Поле      | Семантика                                     |
|----------|--------|-----------|-----------------------------------------------|
| 0        | 8      | `ordinal` | идентификатор операции                        |
| 8        | 4      | `txid`    | идентификатор транзакции; `0` — односторонняя |
| 12       | 2      | `flags`   | битовая маска                                 |

`txid` связывает ответ с запросом в пределах соединения: ответ повторяет `txid`
запроса. У односторонних операций `txid = 0`.

Биты `flags`:

| Бит | Имя          | Значение                                             |
|-----|--------------|------------------------------------------------------|
| 0   | `RESPONSE`   | кадр — ответ на two-way вызов                        |
| 1   | `EPITAPH`    | последний кадр: незнакомая операция или сбой         |
| 3   | `DOMAIN_ERR` | ответ несёт доменную ошибку `E`; только с `RESPONSE` |

Биты 2 и 4-15 зарезервированы и записываются нулём.

### Тело

Тело — последовательность записей полей, завершённая терминатором `0x00`:

```
+----------+----------+----------+
| field_id | len      | data     |
| u8       | u8       | [u8;len] |
+----------+----------+----------+
```

- `field_id` — `1..=254`, уникален и строго возрастает в теле (`0` — терминатор);
- `len` — длина `data` в байтах;
- получатель пропускает незнакомый `field_id` по `len`; каждое поле, которого он
  ждёт, обязано присутствовать.

Заголовок занимает 14 байт, поэтому тело — до 242 байт включая терминатор.

Пример: тело операции с одним параметром `u16 = 1` (`field_id = 1`):

```
01 02 01 00 00
^  ^  ^^^^^ ^
|  |  |     терминатор
|  |  data = 1u16 LE
|  len = 2
field_id = 1
```

### Значения

`field_id` назначается по позиции: первый параметр — `1`, далее по порядку.
Значение в ответе two-way (`T` или `E`) занимает поле `field_id = 1`.

| Тип                          | `data`                  | `len`       |
|------------------------------|-------------------------|-------------|
| целое (`u8..u64`, `i8..i64`) | little-endian           | размер типа |
| `bool`                       | `0` или `1`             | 1           |
| `Str<N>`                     | UTF-8 байты, длина <= N | 0..=N       |
| `Bytes<N>`                   | сырые байты, длина <= N | 0..=N       |

Это полный набор типов. Параметр операции — любой из них; тип успеха `T` и тип
ошибки `E` — только целое или `bool`.

## Идентификатор операции

`ordinal` выводится из канонического имени `"<namespace>.<operation>"` (например
`"Clock.now"`): младшие 64 бита SHA-256 имени в UTF-8 — последние 8 байт
дайджеста, прочитанные big-endian. Имя и хэш фиксированы и покрыты golden-тестом,
поэтому одно имя даёт один `ordinal` в любой реализации. Кадр чужого протокола
несёт `ordinal`, которого у получателя нет, и отвергается.

Wire-формат кадра (заголовок, тело, набор типов, вывод `ordinal`) не зависит от
транспорта и не изменился с переходом от буферизованного канала к port'у —
изменилось лишь то, что кадр лежит в IPC-буфере, а доставка синхронна.

## Поток вызова

two-way:

1. клиент берёт `txid` из счётчика соединения (старт `1`, при переполнении снова
   `1`, никогда `0`);
2. пишет заголовок (`ordinal`, `txid`, без флагов) и тело параметров в свой
   IPC-буфер и выполняет `call` на port'е — синхронный запрос-ответ, который
   блокирует до получения ответа в тот же IPC-буфер;
3. разбирает заголовок полученного кадра:
   - `EPITAPH` -> соединение закрыто (`PeerClosed`);
   - нет `RESPONSE` или `txid` чужой -> кадр не его;
   - иначе по `DOMAIN_ERR` декодирует тело в `E` либо в `T`.

Сервер выполняет `recv` на port'е, по `ordinal` выбирает операцию, декодирует
параметры, выполняет её и для two-way отвечает через одноразовый Reply-handle:
успех — `RESPONSE` с телом `T`; доменная ошибка — `RESPONSE | DOMAIN_ERR` с телом
`E`. На незнакомый `ordinal` сервер отвечает кадром `EPITAPH` и закрывает
соединение.

one-way запрос и событие шлются с `txid = 0` и ответа не порождают; получатель
события незнакомый `ordinal` игнорирует молча.

## Транспорт

IPC опирается на underlying-транспорт, не определяя его. Этим транспортом служит
синхронный `Port` ядра плюс per-thread IPC-буфер: кадр (байты и вектор
хэндлов, до `MESSAGE_MAX_HANDLES = 4`) собирается в IPC-буфере вызывающего потока,
а доставка идёт через rendezvous-syscalls port'а — `send`/`recv` (one-way),
`call`/`reply` (two-way). Платформенный адаптер сводит эти примитивы к трём
логическим операциям: отправка кадра, приём кадра, ожидание встречной стороны;
он сообщает `PeerClosed` после закрытия дальнего конца и `WouldBlock`, когда
встречи нет. Подробнее про сами syscalls и IPC-буфер — в [syscalls.md](syscalls.md).

## Стабильность

Имя операции и раскладка полей — часть ABI:

- каноническое имя фиксировано: переименование меняет `ordinal`, то есть это
  другая операция;
- `field_id` позиционен и не переиспользуется; снятый параметр оставляет свой
  `field_id` занятым, тип под существующим `field_id` не меняется;
- изменение сигнатуры согласуется на обоих концах: получатель требует каждое
  объявленное поле.

## Объявление контракта

Контракт пишется как Rust trait с атрибутом `#[protocol]`; операции размечаются
`#[call]` (two-way), `#[cast]` (one-way клиент -> сервер) и `#[event]` (событие).
Proc-macro по trait строит клиента с методом на операцию и серверный диспетчер
кадра; `#[protocol(name = "...")]` задаёт namespace для `ordinal`.

```rust
#[protocol]
pub trait Clock {
    #[call]  fn now(&self) -> u64;
    #[call]  fn checked(&self, value: u32) -> Result<u32, u8>;
    #[cast]  fn arm(&self, deadline_ns: u64);
    #[event] fn tick(seq: u64);
}
```

Макрос отвергает контракт при типе вне набора, кадре сверх бюджета или коллизии
`ordinal`.

### Тайм-аут ожидания ответа

Two-way `#[call]` ждёт ответ через `Transport::wait_readable(timeout_ns)`. Срок
задаётся декларативно и пробрасывается до транспорта (для `PortTransport` -
в `port_call`/`port_recv`):

- `#[protocol(timeout_ns = N)]` - дефолтный срок (нс) для всех `#[call]`
  клиента (по умолчанию `u64::MAX` - бессрочно);
- `#[call(timeout_ns = N)]` - per-call перекрытие дефолта;
- `Client::with_wait_ns(ns)` - переопределение дефолта в рантайме при
  конструировании клиента; `Client::wait_ns()` возвращает текущее значение.

`N == 0` - poll (не блокироваться), `u64::MAX` - бессрочно, иначе относительный
дедлайн. По истечении операция возвращает `IpcError::Timeout`.

```rust
#[protocol(name = "Sensor", timeout_ns = 50_000_000)] // 50 мс по умолчанию
pub trait Sensor {
    #[call]                      fn read(&self) -> u32;        // 50 мс
    #[call(timeout_ns = 0)]      fn poll(&self) -> u32;        // не блокировать
}
```
