# IPC

Процессы обмениваются данными через синхронный port ядра (`Port`):
rendezvous-примитив, на котором отправитель и получатель встречаются, а сам кадр
лежит в per-thread IPC-буфере вызывающего потока. Port переносит сырые байты
и хэндлы; чтобы стороны понимали друг друга, нужен общий формат сообщения и общий
набор операций. IPC задаёт это поверх port: вызов именованной операции с
типизированными аргументами превращается в кадр в IPC-буфере, синхронно
доставляется на встречную сторону, а из ответного кадра восстанавливается
результат или ошибка. Набор операций и их типов, о котором договорились два
процесса, — контракт; прикладной код работает в его терминах и не касается байтов,
тегов и смещений.

## Обмен

У port две роли: одна сторона вызывает операции (клиент), другая выполняет
(сервер). Каждый вызов и каждый ответ — одно сообщение, один кадр.

Операция бывает трёх видов:

- two-way (`call`): клиент шлёт запрос и ждёт ответ;
- one-way клиент -> сервер (`cast`): запрос без ответа;
- событие сервер -> клиент (`event`): уведомление без ответа.

Ответ two-way несёт один из трёх исходов:

| Исход           | Через port                           |
|-----------------|--------------------------------------|
| успех           | значение `T`, соединение живо        |
| доменная ошибка | значение `E`, соединение живо        |
| сбой протокола  | код причины, соединение закрывается  |

Доменная ошибка — часть контракта (тип `E`): ожидаемый отказ, после которого
обмен продолжается. Сбой протокола (незнакомая операция, битый кадр) закрывает
соединение.

## Идентификация клиента (badge)

Сервер обслуживает много клиентов через один port, не создавая отдельных
объектов под каждого. Чтобы различать, от кого пришёл кадр, используется
**badge** — значок, привязанный к port-хэндлу. Сервер создаёт несколько копий
своего port-хэндла через `handle_duplicate`, каждой назначает свой badge
(set-once: заклеймить можно только незаклеймённый хэндл, переклеймить нельзя), и
раздаёт копии клиентам. Клиент шлёт через свою копию; ядро на приёме (`recv`/`call`)
кладёт badge отправителя в `IpcBuffer.badge` сервера. Так сервер сопоставляет кадр
с клиентом/соединением без глобального идентификатора объекта: в
авторизации/маршрутизации IPC участвуют только хэндлы, права и badge. Подробности
ABI — в [syscalls.md](syscalls.md#port).

Серверной стороне транспорта значок принятого кадра отдаёт
`PortTransport::peer_badge`; значение действительно до следующей операции над
IPC-буфером потока.

## Кадр

Сообщение — один кадр: заголовок 14 байт и тело переменной длины. Кадр
укладывается целиком в data-область IPC-буфера и собирается без аллокации в куче.
Все целые — little-endian.

### Заголовок

| Смещение | Размер | Поле      | Семантика                                     |
|----------|--------|-----------|-----------------------------------------------|
| 0        | 8      | `ordinal` | идентификатор операции                        |
| 8        | 4      | `txid`    | идентификатор транзакции; `0` — односторонняя |
| 12       | 2      | `flags`   | битовая маска                                 |

`txid` связывает ответ с запросом в пределах соединения: ответ повторяет `txid`
запроса. У односторонних операций `txid = 0`.

Биты `flags`:

| Бит | Имя          | Значение                                             |
|-----|--------------|------------------------------------------------------|
| 0   | `RESPONSE`   | кадр — ответ на two-way вызов                        |
| 1   | `PEER_CLOSE` | peer завершает соединение этим последним кадром      |
| 3   | `DOMAIN_ERR` | ответ несёт доменную ошибку `E`; только с `RESPONSE` |

Бит 2 и биты 4-15 зарезервированы и записываются нулём.

### Тело

Тело — последовательность записей полей, завершённая терминатором `0x00`:

```
+----------+----------+----------+
| field_id | len      | data     |
| u8       | u16 LE   | [u8;len] |
+----------+----------+----------+
```

- `field_id` — `1..=254`, уникален и строго возрастает в теле (`0` — терминатор);
- `len` — длина `data` в байтах, `u16` little-endian;
- получатель пропускает незнакомый `field_id` по `len`; каждое поле, которого он
  ждёт, обязано присутствовать.

Заголовок занимает 14 байт, поэтому тело — до 4050 байт включая терминатор, а
тело IPC-буфера (а с ним и кадр) занимает страницу целиком.

Пример: тело операции с одним параметром `u16 = 1` (`field_id = 1`):

```
01 02 00 01 00 00
^  ^^^^^ ^^^^^ ^
|  |     |     терминатор
|  |     data = 1u16 LE
|  len = 2 (u16 LE)
field_id = 1
```

### Значения

`field_id` назначается по позиции: первый параметр — `1`, далее по порядку.
Значение в ответе two-way (`T` или `E`) занимает поле `field_id = 1`.

| Тип                          | `data`                             | `len`       |
|------------------------------|------------------------------------|-------------|
| целое (`u8..u64`, `i8..i64`) | little-endian                      | размер типа |
| `bool`                       | `0` или `1`                        | 1           |
| `Str<N>`                     | UTF-8 байты, длина <= N            | 0..=N       |
| `Bytes<N>`                   | сырые байты, длина <= N            | 0..=N       |
| `Cap`                        | u8-индекс в векторе хэндлов кадра  | 1           |

`Cap` — capability-хэндл: сам хэндл путешествует вне байтового тела кадра в
отдельном векторе (до `MESSAGE_MAX_HANDLES = 4` хэндлов на кадр); поле body несёт
только u8-индекс в этом векторе. Параметр операции — любой тип из таблицы; тип
успеха `T` и тип ошибки `E` — owned-тип: целое, `bool`, `Cap` либо агрегат.
`Str<N>` и `Bytes<N>` в возврате запрещены: они заимствуют буфер ответа.

Агрегат — пользовательский тип, укладывающийся в одно поле: его значение
пишется вложенным суб-кадром той же раскладки (записи полей по позиционному
`field_id`, терминатор), а `len` поля равен длине суб-кадра. Вложенность
рекурсивна. `ipc::wire_value!` объявляет структуру с именованными полями и выводит
такую укладку; структура без лайфтайма годится и в возврат two-way.

Вектор хэндлов у кадра один и общий со всеми его суб-кадрами, поэтому `Cap` —
такое же поле агрегата, как целое: агрегат вправе нести capability вместе со
скалярами и вернуться из two-way целиком. Индексы выдаются в порядке записи
полей, и кадр сверх `MESSAGE_MAX_HANDLES` капы отвергается `TooManyHandles`.

## Идентификатор операции

`ordinal` выводится из канонического имени `"<namespace>.<operation>"` (например
`"Clock.now"`): последние 8 байт SHA-256 имени в UTF-8, прочитанные big-endian.
Имя и хэш фиксированы и покрыты golden-тестом, поэтому одно имя даёт один
`ordinal` в любой реализации. Кадр чужого протокола несёт `ordinal`, которого у
получателя нет, и отвергается.

Примеры:

| Имя          | `ordinal`              |
|--------------|------------------------|
| `Clock.now`  | `0x6ca580d0d09ad48b`   |
| `Calc.add`   | `0xb74487cd9b2841ba`   |

## Поток вызова

two-way:

1. клиент берёт `txid` из счётчика соединения (старт `1`, при переполнении снова
   `1`, никогда `0`);
2. пишет заголовок (`ordinal`, `txid`, без флагов) и тело параметров в свой
   IPC-буфер и выполняет `call` на port — синхронный запрос-ответ, который
   блокирует до получения ответа в тот же IPC-буфер;
3. разбирает заголовок полученного кадра:
   - `PEER_CLOSE` -> соединение закрыто (`PeerClosed`);
   - нет `RESPONSE` или `txid` чужой -> кадр не его;
   - иначе по `DOMAIN_ERR` декодирует тело в `E` либо в `T`.

Сервер выполняет `recv` на port, по `ordinal` выбирает операцию, декодирует
параметры, выполняет её и для two-way отвечает через одноразовый Reply-handle:
успех — `RESPONSE` с телом `T`; доменная ошибка — `RESPONSE | DOMAIN_ERR` с телом
`E`. На незнакомый `ordinal` peer отвечает кадром `PEER_CLOSE` и закрывает
соединение.

one-way запрос и событие шлются с `txid = 0` и ответа не порождают; получатель
события с незнакомым `ordinal` игнорирует его молча.

## Транспорт

IPC опирается на underlying-транспорт, не определяя его. Транспорт — реализация
трёх логических операций:

| Метод                                               | Назначение                |
|-----------------------------------------------------|---------------------------|
| `write_message(&[u8], &[u32]) -> Result<..>`        | отправить кадр            |
| `read_message(&mut [u8], &mut [u32]) -> Result<..>` | принять кадр              |
| `wait_readable(timeout: Timeout) -> Result<..>`     | ждать готовности к приёму |

Платформенный адаптер реализует этот интерфейс через rendezvous-syscalls port —
`send`/`recv` (one-way) и `call`/`reply` (two-way). Адаптер сообщает `PeerClosed`
после ухода дальней стороны, `SenderGone` — когда вместо кадра пришло событие об
уходе значка ([port.md](port.md)), `ResourceExhausted` — когда кадр доставлен, а
принять его нечем (`OutOfHandles` нормализуется в этот покадровый исход), и
`WouldBlock`, когда встречной стороны нет. `PortTransport::client` по умолчанию
ждёт one-way rendezvous бессрочно; `with_send_timeout(timeout)` задаёт срок
только для `send`/`cast`: `Timeout::POLL` означает poll, `Timeout::INFINITE` —
бессрочное ожидание, другое значение — относительный deadline. Истечение
возвращает `IpcError::Timeout`,
кадр остаётся у отправителя и capability не передаются. После
`ResourceExhausted` цикл продолжает приём, не читая поля недоставленного кадра;
`PeerClosed` и отзыв серверной стороны остаются терминальными. Syscall
`Revoked` на отправке нормализуется в `IpcError::PeerClosed`.
Подробнее про syscalls и IPC-буфер — в [syscalls.md](syscalls.md).

## Транспортная плоскость

Плоскость объявляется на весь протокол настройкой `plane`:

| Плоскость | `call` | `cast` | `event` |
|-----------|--------|--------|---------|
| `port`    | да     | да     | да      |
| `ring`    | нет    | да     | да      |

Дефолт — `port`. Настройка включает компиляторную проверку операций под плоскость:
`ring`-протокол с `call` не скомпилируется — const-ассерт по дескриптору не проходит.
Выбранная плоскость отражается в константе `<protocol>::TRANSPORT_PLANE: &str` — для
runtime-диагностики и тестов.

## Стабильность

Имя операции и раскладка полей — часть ABI:

- каноническое имя фиксировано: переименование меняет `ordinal`, то есть это
  другая операция;
- `field_id` позиционен и не переиспользуется; снятый параметр оставляет свой
  `field_id` занятым, тип под существующим `field_id` не меняется;
- изменение сигнатуры согласуется на обоих концах: получатель требует каждое
  объявленное поле.

## Объявление контракта

Контракт объявляется макросом `ipc::protocol!` в виде модуля; операции размечаются
ключевым словом `call` (two-way), `cast` (one-way клиент -> сервер) и `event`
(событие). Макрос строит в этом модуле клиента с методом на операцию и серверный
диспетчер кадра; `name` задаёт namespace для `ordinal`.

```rust
ipc::protocol! {
    /// Часы устройства.
    pub mod clock {
        name = "Clock";

        call fn now() -> u64;
        call fn checked(value: u32) -> Result<u32, u8>;
        cast fn arm(deadline_ns: u64);
        event fn tick(seq: u64);
    }
}
```

Макрос декларативный (`macro_rules!`), а не производный: крейт `ipc` попадает в граф
зависимостей стандартной библиотеки, где proc-макрос собраться не может. Разбор типов,
который проделывал бы proc-макрос, снят уровнем типов — трейтами `WireValue`,
`WireTyped`, `WireReply` и `IntoWireHandle`, — а бюджет кадра и совместимость с
плоскостью проверяются const-функциями по готовому дескриптору.

`Cap` как параметр, возвращаемый тип или поле агрегата указывает, что операция
передаёт capability-хэндл:

```rust
ipc::wire_value! {
    pub struct Vended {
        pub session: ipc::wire::Cap,
        pub prefix_len: u32,
    }
}

ipc::protocol! {
    pub mod resource {
        name = "Resource";

        call fn acquire(exclusive: bool) -> Result<ipc::wire::Cap, u32>;
        call fn vend(prefix_len: u32) -> Vended;
        cast fn release(handle: Cap);
    }
}
```

Параметр верхнего уровня объявляется именно словом `Cap`: по нему макрос выбирает
`IntoWireHandle` вместо `WireValue`. Возврат `-> Cap` означает то же для ответа —
сервис возвращает `impl IntoWireHandle`, и владение снимается после успешной
передачи. Внутри `Result<..>` и агрегата пишется обычный тип `ipc::wire::Cap`.

Cap-параметр верхнего уровня принимается как `impl IntoWireHandle`, поэтому в
него передаётся и владеющий хэндл: после успешной отправки владение снимается.

Внутри агрегата поле остаётся `Cap` — само значение ничем не владеет, и судьбу
хэндла решает итог отправки. Успешная отправка переносит хэндл ядром в таблицу
получателя; после отказа он остаётся в таблице отправителя, и закрыть его —
обязанность отправителя. Серверы файловой подсистемы держат эту дисциплину
примитивом `vend`/`settle` из `lib/filesystem-server`: хэндл лежит в состоянии
кадра до итога отправки. На приёме капы кадра принадлежат получателю с момента
рандеву: не потреблённые разбором — в том числе оборванным посреди кадра — обязан
закрыть принимающий цикл. Каждый слот кадра потребляется декодом один раз:
второе поле с тем же индексом отвергается как `InvalidValue`.

Кадр сверх бюджета тела и операция, чьих параметров больше, чем несёт пространство
`field_id` записи (`1..=254`), отвергаются const-ассертом на месте объявления. Модуль
контракта несёт: `Client`, trait `Service`, функцию `dispatch`, trait `Events` вместе
с `EventSender` и `dispatch_event`, `DESC: ProtocolDesc`, `TRANSPORT_PLANE` и по
модулю на операцию с её `ORDINAL` и `CANONICAL`.

Пример объявления операции из `lib/bootstrap-abi` (односторонняя `cast`):

```rust
ipc::protocol! {
    pub mod bootstrap {
        name = "Bootstrap";

        cast fn log(
            tag: ipc::wire::Str<{ crate::LOG_TAG_MAX }>,
            message: ipc::wire::Str<{ crate::LOG_MESSAGE_MAX }>,
        );
    }
}
```

### Тайм-аут ожидания ответа

Two-way `call` ждёт ответ через `Transport::wait_readable(timeout)`. Срок задаётся
декларативно и пробрасывается до транспорта:

- `name = "...", wait = N` — дефолтный срок (нс) для всех `call` клиента (по
  умолчанию бессрочно);
- `call(wait = N)` — перекрытие дефолта на отдельной операции;
- `Client::with_wait(timeout)` — переопределение дефолта в рантайме при
  конструировании клиента; `Client::wait()` возвращает текущее значение.

Настройки макроса несут число наносекунд: `N == 0` — poll (не блокироваться), иначе
относительный дедлайн. По истечении операция возвращает `IpcError::Timeout`.

```rust
ipc::protocol! {
    pub mod sensor {
        name = "Sensor", wait = 50_000_000; // 50 мс по умолчанию

        call fn read() -> u32; // 50 мс
        call(wait = 0) fn poll() -> u32; // не блокировать
    }
}
```

`with_wait` не меняет срок one-way отправки. Клиент, которому нужны оба
ограничения, настраивает transport до передачи его сгенерированному клиенту:

```rust
let transport = PortTransport::client(startup.handle())
    .with_send_timeout(Timeout::from_millis(50));
let client = driver_args::Client::new(transport).with_wait(Timeout::from_millis(200));
```

Успешный `cast` означает состоявшийся rendezvous: получатель уже принял кадр,
а capability перемещены в его таблицу. При `Timeout` встреча не состоялась,
поэтому владеющие аргументы кадра закрываются обычным RAII-путём отправителя.
