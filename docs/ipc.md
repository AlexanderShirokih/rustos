# IPC

Port переносит сырые байты и хэндлы ([port.md](port.md)). Чтобы стороны понимали
друг друга, поверх этого нужен общий формат сообщения и общий набор операций. Их
и задаёт IPC.

Работает это так. Вызов именованной операции с типизированными аргументами
превращается в кадр в IPC-буфере. Кадр синхронно доставляется на встречную
сторону. Из ответного кадра восстанавливается результат либо ошибка.

Набор операций и их типов, о котором договорились два процесса, называется
контрактом. Прикладной код работает в терминах контракта и байтов, тегов и
смещений не касается.

## Обмен

У port две роли. Одна сторона вызывает операции и называется клиентом, другая
выполняет их и называется сервером. Каждый вызов и каждый ответ — одно
сообщение, один кадр.

Операция бывает двух видов:

- two-way (`call`) — клиент шлёт запрос и ждёт ответ;
- one-way клиент -> сервер (`cast`) — запрос без ответа.

У ответа two-way три возможных исхода:

| Исход           | Через port                                  |
|-----------------|---------------------------------------------|
| успех           | значение `T`                                |
| доменная ошибка | значение `E`                                |
| сбой протокола  | вызов отвергнут, вызывающий получает отказ  |

Доменная ошибка — часть контракта, её тип `E`. Это ожидаемый отказ, после
которого обмен продолжается. Сбой протокола (незнакомая операция, битый кадр)
отвергает вызов. Сервер разрушает канал ответа кадра, и вызывающий получает
`PeerClosed`.

Сервер обслуживает много клиентов через один port и различает их по значку
принятого кадра ([port.md](port.md#роли-и-значки)).

## Кадр

Сообщение — один кадр: заголовок 8 байт и тело переменной длины. Кадр
укладывается целиком в data-область IPC-буфера и собирается без аллокации в
куче. Все целые — little-endian.

### Заголовок

| Смещение | Размер | Поле      | Семантика              |
|----------|--------|-----------|------------------------|
| 0        | 8      | `ordinal` | идентификатор операции |

Вид кадра заголовок не называет. Ответ приходит по одноразовому Reply-объекту
своего вызова, а односторонний кадр и кадр вызова различает syscall отправки,
поэтому ни номера транзакции, ни флагов кадру не нужно.

### Тело

Тело — последовательность записей полей, завершённая терминатором `0x00`:

```
+----------+----------+----------+
| field_id | len      | data     |
| u8       | u16 LE   | [u8;len] |
+----------+----------+----------+
```

- `field_id` — `1..=254`, уникален и строго возрастает в теле (`0` — терминатор);
- `len` — длина `data` в байтах, `u16` little-endian;
- получатель пропускает незнакомый `field_id` по `len`; каждое поле, которого он
  ждёт, обязано присутствовать.

Заголовок занимает 8 байт, поэтому тело — до 4056 байт включая терминатор.

Пример: тело операции с одним параметром `u16 = 1` (`field_id = 1`):

```
01 02 00 01 00 00
^  ^^^^^ ^^^^^ ^
|  |     |     терминатор
|  |     data = 1u16 LE
|  len = 2 (u16 LE)
field_id = 1
```

### Значения

`field_id` назначается по позиции: первый параметр — `1`, далее по порядку.
Значение ответа two-way занимает поле `field_id = 1`.

| Тип                          | `data`                                        | `len`        |
|------------------------------|-----------------------------------------------|--------------|
| целое (`u8..u64`, `i8..i64`) | little-endian                                 | размер типа  |
| `bool`                       | `0` или `1`                                   | 1            |
| `Str<N>`                     | UTF-8 байты, длина <= N                       | 0..=N        |
| `Bytes<N>`                   | сырые байты, длина <= N                       | 0..=N        |
| `Cap<K>`                     | u8-индекс в векторе хэндлов кадра             | 1            |
| `Result<T, E>`               | вложенная запись: поле `1` = `T`, поле `2` = `E` | длина записи |
| `Option<T>`                  | `Some` — запись `T`, `None` — пусто           | 0 либо длина `T` |
| перечисление `wire_enum!`    | дискриминант little-endian                    | размер типа дискриминанта |

`Result<T, E>` содержит ровно одно из двух полей. Запись без обоих полей
отвергается как `MissingField`, запись с обоими — как `InvalidValue`.

`Cap<K>` — capability-хэндл вида `K`. Сам хэндл передаётся вне байтового тела
кадра, в отдельном векторе (до `MESSAGE_MAX_HANDLES = 4` хэндлов на кадр).
Сессия протокола `ipc::wire::Session<P>` кодируется как `Cap<kind::Port>`.
Протокол `P` существует только при компиляции, и принятая сессия его сохраняет.
Тип успеха `T` и тип ошибки `E` — owned-тип.

Перечисление, объявленное `ipc::wire_enum!`, передаёт вариант дискриминантом из
объявления. Тип дискриминанта задаёт объявление, по умолчанию это `u16`. Дискриминант вне
объявленных отвергается как `InvalidValue`.

Агрегат — пользовательский тип, укладывающийся в одно поле. Его значение пишется
вложенной записью той же раскладки, а `len` поля равен длине этой записи.
Вложенность рекурсивна.

Вектор хэндлов у кадра один и общий со всеми его вложенными записями. Отсюда и свобода
агрегата: он вправе содержать capability вместе со скалярами и целиком вернуться
из two-way. Кадр, вышедший за `MESSAGE_MAX_HANDLES` капы, отвергается
`TooManyHandles`.

## Идентификатор операции

`ordinal` выводится из канонического имени `"<namespace>.<operation>"`, например
`"Clock.now"`. Берутся последние 8 байт SHA-256 этого имени в UTF-8, прочитанные
big-endian.

Имя и хэш зафиксированы и покрыты golden-тестом, так что одно имя даёт один и тот
же `ordinal` в любой реализации. В кадре чужого протокола стоит `ordinal`,
которого получатель не объявляет, и такой кадр отвергается.

| Имя         | `ordinal`            |
|-------------|----------------------|
| `Clock.now` | `0x6ca580d0d09ad48b` |
| `Calc.add`  | `0xb74487cd9b2841ba` |

## Поток вызова

Клиент пишет заголовок и тело параметров в свой IPC-буфер и выполняет `call` на
port. Ядро кладёт ответ в тот же буфер по Reply-объекту этого вызова, поэтому
ответ чужого вызова прийти не может. Клиент сверяет `ordinal` ответа с операцией
вызова и декодирует значение ответа из поля `1`. Ответ другой операции
отвергается как `InvalidValue`.

Two-way вызов возвращает прочитанное значение ответа. Оно владеет capability,
которые называют его поля, а остальные capability кадра закрываются сразу.

Сервер выполняет `recv` на port, по `ordinal` выбирает операцию, декодирует
параметры и выполняет её. У two-way операции две серверные формы. В первой
обработчик возвращает значение ответа, во второй получает долг ответа и отвечает
им позже. Ответ уходит через одноразовый Reply-handle кадром со значением ответа
в поле `1`. Доменная ошибка — исход `Err` этого значения. Кадр ответа повторяет
`ordinal` вызова. Долг, разрушенный без ответа, даёт вызывающему отказ
`PeerClosed`. Кадр с незнакомым `ordinal` сервер отбрасывает вместе с его каналом
ответа, и вызыватель получает `PeerClosed`.

One-way запрос шлётся `send` и ответа не порождает. Кадр two-way операции,
пришедший без канала ответа, до обработчика не доходит.

## Транспорт

IPC опирается на транспорт рандеву и сам его не определяет. Клиент отправляет
кадр односторонне либо вызовом, который ждёт ответа. Сервер принимает кадр
вместе с его capability, значком отправителя и каналом ответа. Между операциями
транспорт состояния не держит. Для port это `PortTransport` поверх
rendezvous-syscalls.

Отправка отказывает с `PeerClosed`, когда встречной стороны нет либо ответ
отменён, и с `Timeout`, когда срок истёк, а кадр остался у отправителя. Вызов,
чей ответ ядро не смогло установить вызывающему из-за полной таблицы handle либо
исчерпанного бюджета, отказывает с `ResourceExhausted`. Приём
вместо кадра может вернуть уход значка, отброшенный кадр или истёкший срок, и
цикл сервера на них продолжается. Закрытие порта цикл завершает.

## Стабильность

Имя операции и раскладка полей — часть ABI:

- каноническое имя фиксировано. Переименование меняет `ordinal` и объявляет
  другую операцию;
- `field_id` позиционен и не переиспользуется. Снятый параметр оставляет свой
  `field_id` занятым, тип под существующим `field_id` не меняется;
- изменение сигнатуры согласуется на обоих концах. Получатель требует каждое
  объявленное поле.

## Объявление контракта

Контракт объявляется макросом `ipc::protocol!` в виде модуля; операции
размечаются словом `call` (two-way) и `cast` (one-way клиент -> сервер). Макрос
строит в этом модуле клиента с методом на операцию и серверный диспетчер кадра;
`name` задаёт namespace для `ordinal`.

```rust
ipc::protocol! {
    /// Часы устройства.
    pub mod clock {
        name = "Clock";

        call fn now() -> u64;
        call fn checked(value: u32) -> Result<u32, u8>;
        cast fn arm(deadline_ns: u64);
    }
}
```

Модуль контракта содержит `Client`, trait `Service`, функцию `dispatch`, тип
`Protocol` с именем контракта и по модулю на операцию с её `ORDINAL` и
`CANONICAL`. Модуль операции с отложенным ответом содержит ещё псевдоним
`Reply<C>` её долга `ipc::Reply<V, C>`. Кадр сверх бюджета тела и операция, чьих
параметров больше, чем вмещает пространство `field_id`, отвергаются
const-ассертом на месте объявления.

Макрос декларативный (`macro_rules!`), а не производный. Крейт `ipc` попадает в
граф зависимостей стандартной библиотеки, где proc-макрос собраться не может.

### Передача capability

`Cap` как параметр, возвращаемый тип или поле агрегата указывает, что операция
передаёт capability-хэндл:

```rust
ipc::wire_value! {
    pub struct Lease<S = ipc::wire::Cap<syscall::kind::Port>> {
        pub session: S,
        pub prefix_len: u32,
    }
}

ipc::protocol! {
    pub mod resource {
        name = "Resource";

        call fn acquire(exclusive: bool)
            -> own Result<ipc::wire::Cap<syscall::kind::MemoryRegion>, u32>;
        call fn lease(prefix_len: u32) -> own Lease;
        cast fn release(own handle: ipc::wire::Cap<syscall::kind::Port>);
    }
}
```

Владение параметра и ответа объявляется словом `own`. Метод отправителя
принимает владеющее значение `impl IntoWireValue<R, Read = T>`, где `R` —
ресурсы кадра канала, `T` — объявленный тип записи, и вид capability приходит
из этого типа. Компилятор
отвергает отправку хэндла другого вида. Обработчик получает параметр `own T`
значением, которое владеет его capability, а ответ `own T` отдаёт владеющим
значением. Параметр без `own` capability не содержит, и такое объявление
отвергается при компиляции. Поле-capability агрегата задаётся параметром
владельца, и получатель читает агрегат с владеющей capability в этом поле.
Сессия передаётся владеющим значением `kernel_objects::Session<P>`.

Запись владеющего значения переносит владельца хэндла в ресурсы кадра, и номер
хэндла попадает в кадр только вместе с владельцем. Успешная отправка переносит
хэндл в таблицу получателя без закрытия у отправителя. Отказ одностороннего
сообщения или ответа возвращает `Undelivered` с причиной и значением,
прочитанным декодером получателя, а хэндлы вне значения закрываются при разборе.
Отказ записи кадра и отказ вызова закрывают владеющие параметры. У серверов нет отдельного примитива
выдачи capability.

На приёме разбор переносит capability каждого поля в прочитанное значение, и
у capability один владелец. Второе поле с тем же индексом слота отвергается как
`InvalidValue`. Капы, которых не назвало ни одно поле, и невзятый канал ответа
закрываются вместе с кадром.

Долг ответа остаётся у держателя после возврата обработчика и отвечается позже.
Долг типизирован типом ответа `V` и содержит канал ответа и ординал исходной
операции. Другому процессу долг уходит полем `ipc::Reply<V>`, и получатель
читает его долгом со своим каналом ответа. Ответ по пересланному долгу
содержит ординал исходной операции, и вызыватель принимает его как ответ своей
операции.

### Тайм-аут ожидания ответа

Срок ожидания задаёт `Client::with_wait(timeout)` для всех операций клиента. Он
ограничивает приём одностороннего кадра получателем и ответ на вызов. Клиент
ждёт бессрочно, пока срок не задан. `Timeout::POLL` означает poll, любое другое
значение — относительный дедлайн. По истечении операция возвращает
`IpcError::Timeout`.

```rust
ipc::protocol! {
    /// Датчик температуры.
    pub mod sensor {
        name = "Sensor";

        /// Последнее показание в сотых долях градуса.
        call fn read() -> i32;
        /// Сдвиг нуля датчика.
        cast fn calibrate(offset: i32);
    }
}

fn latest(port: &Port) -> Result<Option<i32>, IpcError> {
    // Срок 50 мс ограничивает и приём `calibrate`, и ответ на `read`.
    let sensor = sensor::Client::new(PortTransport::new(port))
        .with_wait(Timeout::from_millis(50));
    sensor.calibrate(-15)?;
    match sensor.read() {
        Ok(value) => Ok(Some(value)),
        // Датчик не ответил в срок, и повторять ли вызов, решает вызывающий.
        Err(IpcError::Timeout) => Ok(None),
        Err(error) => Err(error),
    }
}
```

Для операций с другим сроком создаётся второй клиент над тем же портом. Клиент
`sensor::Client::new(PortTransport::new(port)).with_wait(Timeout::POLL)`
опрашивает датчик без ожидания.

Успешный `cast` означает, что получатель уже принял кадр, и capability перенесены
в его таблицу.
