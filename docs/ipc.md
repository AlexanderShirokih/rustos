# IPC

Port переносит сырые байты и хэндлы ([port.md](port.md)). Чтобы стороны понимали
друг друга, поверх этого нужен общий формат сообщения и общий набор операций. Их
и задаёт IPC.

Работает это так. Вызов именованной операции с типизированными аргументами
превращается в кадр в IPC-буфере. Кадр синхронно доставляется на встречную
сторону. Из ответного кадра восстанавливается результат либо ошибка.

Набор операций и их типов, о котором договорились два процесса, называется
контрактом. Прикладной код работает в терминах контракта и байтов, тегов и
смещений не касается.

## Обмен

У port две роли. Одна сторона вызывает операции и называется клиентом, другая
выполняет их и называется сервером. Каждый вызов и каждый ответ — одно
сообщение, один кадр.

Операция бывает трёх видов:

- two-way (`call`) — клиент шлёт запрос и ждёт ответ;
- one-way клиент -> сервер (`cast`) — запрос без ответа;
- событие сервер -> клиент (`event`) — уведомление без ответа.

У ответа two-way три возможных исхода:

| Исход           | Через port                          |
|-----------------|-------------------------------------|
| успех           | значение `T`, соединение живо       |
| доменная ошибка | значение `E`, соединение живо       |
| сбой протокола  | код причины, соединение закрывается |

Доменная ошибка — часть контракта, её тип `E`. Это ожидаемый отказ, после
которого обмен продолжается. Сбой протокола (незнакомая операция, битый кадр)
закрывает соединение.

Сервер обслуживает много клиентов через один port и различает их по значку
принятого кадра ([port.md](port.md#роли-и-значки)). Значок доставленного кадра
отдаёт `ReceivedFrame::badge`, а `PortTransport::peer_badge` — значок ушедшей
стороны при отказе приёма `SenderGone`.

## Кадр

Сообщение — один кадр: заголовок 14 байт и тело переменной длины. Кадр
укладывается целиком в data-область IPC-буфера и собирается без аллокации в
куче. Все целые — little-endian.

### Заголовок

| Смещение | Размер | Поле      | Семантика                                     |
|----------|--------|-----------|-----------------------------------------------|
| 0        | 8      | `ordinal` | идентификатор операции                        |
| 8        | 4      | `txid`    | идентификатор транзакции; `0` — односторонняя |
| 12       | 2      | `flags`   | битовая маска                                 |

`txid` связывает ответ с запросом в пределах соединения. Ответ повторяет `txid`
запроса.

| Бит | Имя          | Значение                                             |
|-----|--------------|------------------------------------------------------|
| 0   | `RESPONSE`   | кадр — ответ на two-way вызов                        |
| 1   | `PEER_CLOSE` | peer завершает соединение этим последним кадром      |
| 3   | `DOMAIN_ERR` | ответ несёт доменную ошибку `E`; только с `RESPONSE` |

Бит 2 и биты 4-15 зарезервированы и записываются нулём.

### Тело

Тело — последовательность записей полей, завершённая терминатором `0x00`:

```
+----------+----------+----------+
| field_id | len      | data     |
| u8       | u16 LE   | [u8;len] |
+----------+----------+----------+
```

- `field_id` — `1..=254`, уникален и строго возрастает в теле (`0` — терминатор);
- `len` — длина `data` в байтах, `u16` little-endian;
- получатель пропускает незнакомый `field_id` по `len`; каждое поле, которого он
  ждёт, обязано присутствовать.

Заголовок занимает 14 байт, поэтому тело — до 4050 байт включая терминатор.

Пример: тело операции с одним параметром `u16 = 1` (`field_id = 1`):

```
01 02 00 01 00 00
^  ^^^^^ ^^^^^ ^
|  |     |     терминатор
|  |     data = 1u16 LE
|  len = 2 (u16 LE)
field_id = 1
```

### Значения

`field_id` назначается по позиции: первый параметр — `1`, далее по порядку.
Значение в ответе two-way (`T` или `E`) занимает поле `field_id = 1`.

| Тип                          | `data`                            | `len`       |
|------------------------------|-----------------------------------|-------------|
| целое (`u8..u64`, `i8..i64`) | little-endian                     | размер типа |
| `bool`                       | `0` или `1`                       | 1           |
| `Str<N>`                     | UTF-8 байты, длина <= N           | 0..=N       |
| `Bytes<N>`                   | сырые байты, длина <= N           | 0..=N       |
| `Cap<K>`                     | u8-индекс в векторе хэндлов кадра | 1           |

`Cap<K>` — capability-хэндл вида `K`. Сам хэндл передаётся вне байтового тела
кадра, в отдельном векторе (до `MESSAGE_MAX_HANDLES = 4` хэндлов на кадр). Вид
`K` существует только при компиляции, поэтому в кадре стоит тот же u8-индекс, а
байты, `field_id` и `WireType` от вида не зависят. Тип успеха `T` и тип ошибки `E` —
owned-тип, то есть целое, `bool`, `Cap<K>` либо агрегат.
`Str<N>` и `Bytes<N>` в возврате запрещены, они заимствуют буфер ответа.

Агрегат — пользовательский тип, укладывающийся в одно поле. Его значение пишется
вложенным суб-кадром той же раскладки, а `len` поля равен длине суб-кадра.
Вложенность рекурсивна.

Вектор хэндлов у кадра один и общий со всеми его суб-кадрами. Отсюда и свобода
агрегата: он вправе содержать capability вместе со скалярами и целиком вернуться
из two-way. Кадр, вышедший за `MESSAGE_MAX_HANDLES` капы, отвергается
`TooManyHandles`.

## Идентификатор операции

`ordinal` выводится из канонического имени `"<namespace>.<operation>"`, например
`"Clock.now"`. Берутся последние 8 байт SHA-256 этого имени в UTF-8, прочитанные
big-endian.

Имя и хэш зафиксированы и покрыты golden-тестом, так что одно имя даёт один и тот
же `ordinal` в любой реализации. В кадре чужого протокола стоит `ordinal`,
которого получатель не объявляет, и такой кадр отвергается.

| Имя         | `ordinal`            |
|-------------|----------------------|
| `Clock.now` | `0x6ca580d0d09ad48b` |
| `Calc.add`  | `0xb74487cd9b2841ba` |

## Поток вызова

Клиент берёт `txid` из счётчика соединения (старт `1`, при переполнении снова
`1`, никогда `0`), пишет заголовок и тело параметров в свой IPC-буфер и
выполняет `call` на port. Разбирая ответ, он проверяет заголовок:

- `PEER_CLOSE` -> соединение закрыто (`PeerClosed`);
- нет `RESPONSE` или `txid` чужой -> кадр не его;
- иначе по `DOMAIN_ERR` декодирует тело в `E` либо в `T`.

Two-way вызов возвращает `Response` — значение кадра вместе с владением его
capability. Названную в теле capability забирают из ответа один раз, остальные
закрываются вместе с ним. Отказ разбора и чужой кадр ресурсов без владельца не
оставляют, и следующий вызов по транспорту владение не меняет.

Сервер выполняет `recv` на port, по `ordinal` выбирает операцию, декодирует
параметры, выполняет её и для two-way отвечает через одноразовый Reply-handle:
успех — `RESPONSE` с телом `T`, доменная ошибка — `RESPONSE | DOMAIN_ERR` с
телом `E`. На незнакомый `ordinal` peer отвечает кадром `PEER_CLOSE` и закрывает
соединение.

one-way запрос и событие шлются с `txid = 0` и ответа не порождают; получатель
события с незнакомым `ordinal` игнорирует его молча.

## Транспорт

IPC опирается на underlying-транспорт, не определяя его. Транспорт — реализация
четырёх логических операций:

| Метод                                               | Назначение                     |
|-----------------------------------------------------|--------------------------------|
| `write_message(&[u8], &[u32]) -> Result<..>`        | отправить кадр                 |
| `read_message(&mut [u8], &mut [u32]) -> Result<..>` | принять кадр                   |
| `wait_readable(timeout: Timeout) -> Result<..>`     | ждать готовности к приёму      |
| `take_resources() -> Resources`                     | забрать ресурсы принятого кадра |

`Resources` — тип-владелец capability одного кадра; транспорт, который capability
не переносит, объявляет его единичным типом.

Платформенный адаптер реализует этот интерфейс через rendezvous-syscalls port.
Исходы port он переводит в исходы IPC:

| Исход адаптера      | Когда                                                    |
|---------------------|----------------------------------------------------------|
| `PeerClosed`        | дальняя сторона ушла; сюда же нормализуется `Revoked`     |
| `SenderGone`        | вместо кадра пришло событие об уходе значка              |
| `ResourceExhausted` | кадр доставлен, а принять его нечем                       |
| `WouldBlock`        | встречной стороны нет                                     |
| `Timeout`           | истёк срок; кадр остался у отправителя, капы не переданы |

`PeerClosed` и отзыв серверной стороны терминальны; после `ResourceExhausted`
цикл продолжает приём, не читая поля недоставленного кадра.

`PortTransport::client` по умолчанию ждёт one-way rendezvous бессрочно;
`with_send_timeout(timeout)` задаёт срок только для `send`/`cast`.

## Транспортная плоскость

Плоскость объявляется на весь протокол настройкой `plane`:

| Плоскость | `call` | `cast` | `event` |
|-----------|--------|--------|---------|
| `port`    | да     | да     | да      |
| `ring`    | нет    | да     | да      |

Дефолт — `port`. Настройка включает компиляторную проверку операций под
плоскость: `ring`-протокол с `call` не скомпилируется. Выбранная плоскость
отражается в константе `<protocol>::TRANSPORT_PLANE: &str`.

## Стабильность

Имя операции и раскладка полей — часть ABI:

- каноническое имя фиксировано. Переименование меняет `ordinal` и объявляет
  другую операцию;
- `field_id` позиционен и не переиспользуется. Снятый параметр оставляет свой
  `field_id` занятым, тип под существующим `field_id` не меняется;
- изменение сигнатуры согласуется на обоих концах. Получатель требует каждое
  объявленное поле.

## Объявление контракта

Контракт объявляется макросом `ipc::protocol!` в виде модуля; операции
размечаются словом `call` (two-way), `cast` (one-way клиент -> сервер) и `event`
(событие). Макрос строит в этом модуле клиента с методом на операцию и серверный
диспетчер кадра; `name` задаёт namespace для `ordinal`.

```rust
ipc::protocol! {
    /// Часы устройства.
    pub mod clock {
        name = "Clock";

        call fn now() -> u64;
        call fn checked(value: u32) -> Result<u32, u8>;
        cast fn arm(deadline_ns: u64);
        event fn tick(seq: u64);
    }
}
```

Модуль контракта содержит `Client`, trait `Service`, функцию `dispatch`, trait
`Events` вместе с `EventSender` и `dispatch_event`, `DESC: ProtocolDesc`,
`TRANSPORT_PLANE` и по модулю на операцию с её `ORDINAL` и `CANONICAL`. Кадр
сверх бюджета тела и операция, чьих параметров больше, чем вмещает пространство
`field_id`, отвергаются const-ассертом на месте объявления.

Макрос декларативный (`macro_rules!`), а не производный. Крейт `ipc` попадает в
граф зависимостей стандартной библиотеки, где proc-макрос собраться не может.
Разбор типов снят уровнем типов — трейтами `WireValue`, `WireTyped`, `WireReply`
и `IntoWireHandle`.

### Передача capability

`Cap` как параметр, возвращаемый тип или поле агрегата указывает, что операция
передаёт capability-хэндл:

```rust
ipc::wire_value! {
    pub struct Vended {
        pub session: ipc::wire::Cap<syscall::kind::Port>,
        pub prefix_len: u32,
    }
}

ipc::protocol! {
    pub mod resource {
        name = "Resource";

        call fn acquire(exclusive: bool)
            -> Result<ipc::wire::Cap<syscall::kind::MemoryRegion>, u32>;
        call fn vend(prefix_len: u32) -> Vended;
        cast fn release(handle: Cap<syscall::kind::Port>);
    }
}
```

Параметр верхнего уровня объявляется как `Cap<K>`. Метод отправителя принимает
`impl IntoWireHandle<Kind = K>`, а обработчик сервиса или события — `Cap<K>`.
Компилятор отвергает отправку хэндла другого вида. Возврат `-> Cap<K>` задаёт
`impl IntoWireHandle<Kind = K>` для результата сервиса. Квалифицированный тип
`ipc::wire::Cap<K>`, в том числе внутри `Result<..>` и агрегата, кодируется через
`WireValue`; значение не владеет хэндлом.

Судьбу хэндла решает итог отправки. Успешная отправка переносит хэндл ядром в
таблицу получателя, после отказа он остаётся в таблице отправителя, и закрыть
его — обязанность отправителя. Серверы держат эту дисциплину примитивом
`vend`/`settle` из `lib/kernel-objects`.

На приёме капы кадра принадлежат получателю с момента рандеву. Капы, не
потреблённые разбором, и незавершённый reply закрываются вместе с кадром, и
отдельной очистки после `dispatch` обработчик не делает. Каждый слот кадра
потребляется декодом один раз. Второе поле с тем же индексом отвергается как
`InvalidValue`.

### Тайм-аут ожидания ответа

Two-way `call` ждёт ответ через `Transport::wait_readable(timeout)`. Срок
задаётся декларативно и пробрасывается до транспорта:

- `name = "...", wait = N` — дефолтный срок (нс) для всех `call` клиента (по
  умолчанию бессрочно);
- `call(wait = N)` — перекрытие дефолта на отдельной операции;
- `Client::with_wait(timeout)` — переопределение дефолта в рантайме.

Настройки макроса задают число наносекунд. `N == 0` означает poll, любое другое
значение — относительный дедлайн. По истечении операция возвращает `IpcError::Timeout`.

```rust
ipc::protocol! {
    pub mod sensor {
        name = "Sensor", wait = 50_000_000; // 50 мс по умолчанию

        call fn read() -> u32; // 50 мс
        call(wait = 0) fn poll() -> u32; // не блокировать
    }
}
```

`with_wait` не меняет срок one-way отправки. Клиент, которому нужны оба
ограничения, настраивает transport до передачи его сгенерированному клиенту:

```rust
let transport = PortTransport::client(startup.handle())
    .with_send_timeout(Timeout::from_millis(50));
let client = driver_args::Client::new(transport).with_wait(Timeout::from_millis(200));
```

Успешный `cast` означает состоявшийся rendezvous. Получатель уже принял кадр, а
capability перемещены в его таблицу. При `Timeout` встреча не состоялась, и
владеющие аргументы кадра закрываются обычным RAII-путём отправителя.
