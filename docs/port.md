# Port

`Port` обеспечивает обмен кадрами и capability между процессами.
Реестр операций и аргументы определены в [syscalls.md](syscalls.md#port),
формат типизированных сообщений — в [ipc.md](ipc.md).

## Рандеву

Порт доставляет кадр при встрече отправителя и получателя.
Первая пришедшая сторона ждёт вторую. Кадр хранится в IPC-буфере
потока либо в буфере ядра у отложенной операции; очередь порта содержит
ожидающие операции.

`send` ждёт приёма, `recv` — отправителя, `call` — приёма и ответа.
Успешный `send` означает доставку кадра, но не завершение его обработки.
Истечение срока до встречи оставляет кадр недоставленным.

`send_async` и `call_async` ставят операцию без парковки потока и возвращают
`Pending`. Его сигнал `SIGNALED` означает конечный исход; `take` выдаёт этот
исход и расходует handle. Закрытие handle отменяет операцию. Capability кадра
изымаются при постановке, а недоставленная отправка возвращает их через `take`.

## Роли и значки

Право `READ` разрешает приём, `WRITE` — отправку и вызов.
Сервер выдаёт клиентам копии хендла с ненулевыми значками (badge)
и различает клиентов по значку принятого кадра.

Значок `0` означает отсутствие значка. Права и правила присвоения
значка определены в [syscalls.md](syscalls.md#handle).

## Передача capability

Передача требует `TRANSFER` и перемещает хендл из таблицы отправителя
в таблицу получателя. Права и деривация сохраняются. У отправителя
может оставаться доступ через другие capability или установленный маппинг.

Разделяемая память и новые IPC-сессии делегируются передачей соответствующих
capability. Стартовый хендл процесса передаёт операция запуска.

## Отложенный ответ

Приём запроса `call` возвращает одноразовую capability `Reply`.
Ответ может отправить другой поток или процесс.

Закрытие `Reply` без ответа завершает вызов с `PeerClosed`.
Каждый ответ должен иметь владельца, который ответит или закроет его.
Сохранённый и неиспользуемый `Reply` оставляет вызывающего в ожидании
до истечения срока.

## Живость сторон

Порт учитывает capability получателей с `READ` и capability отправителей
с `WRITE` по каждому ненулевому значку. Capability учитывается также
во время передачи и незавершённой операции.

### Отказ отправителю

Уход последнего получателя завершает ожидающие операции с `PeerClosed`.
Последующие `send` и `call` отказывают сразу. Нового получателя
из capability без `READ` создать нельзя.

Закрытый предок клиентской capability даёт `Revoked`.
Если capability валидна, но у порта нет получателей, вызов даёт
`PeerClosed`. Отзыв проверяется раньше состояния порта.

Отсутствие отправителей не завершает `recv`: в будущем может появиться
новый отправитель.

### Уход значка

Уход последней capability с `WRITE` и данным значком возвращает
очередному `recv` исход `SenderGone`. Значок записывается в
`IpcBuffer.badge`. Сообщение при этом не доставляется;
остальные поля буфера остаются прежними.
Сервер освобождает сессию и продолжает приём.

Все capability с одинаковым значком считаются одной группой отправителей.
Повторная выдача того же значка снимает непрочитанное событие его ухода.

Непрочитанные уходы занимают ограниченные записи порта. При исчерпании
предела выдача нового значка даёт `ResourceExhausted`. Сервер должен
читать события ухода, чтобы освобождать записи.

## Несколько получателей

На одном порту могут принимать несколько потоков. Недоставленные кадры
ушедшего значка отменяются до публикации `SenderGone`.
Однако один поток может получить событие ухода раньше, чем другой
начнёт обработку уже принятого кадра этого значка. Общая блокировка
обработчиков не восстанавливает этот порядок.

Для такого сервера действуют правила:

- Сессия регистрируется при установлении; кадр неизвестного значка
  отклоняется.
- Значки не переиспользуются, чтобы запоздавший кадр не попал в новую сессию.
- Сессия должна быть зарегистрирована до выдачи клиентской capability.
  Если уход может обрабатываться одновременно с минтом, регистрация
  должна предшествовать минту.
- Ответ запоздавшего кадра закрывается, если сессия уже завершена.

Несколько вызовов одной сессии могут обрабатываться в любом порядке.
Клиент, которому нужен порядок, выполняет их последовательно.

## Владение сервисом

Клиенту выдаётся capability со значком и правами `WRITE | TRANSFER`.
Клиент сессии экспорта получает права `DUPLICATE | WRITE | TRANSFER` и
может выдать производную сессии другому процессу. Закрытие capability
клиента отзывает производную.
Сервис владеет capability с `READ`.

Чтобы уход сервиса наблюдался клиентами, другие процессы не должны
удерживать получательские capability. Создатель сначала выдаёт клиентские
производные, затем может передать корневую capability сервису целиком.
Оставленный у создателя корень с `READ` сохраняет возможность приёма.

## Тайм-ауты и границы

Тайм-аут `call` ограничивает доставку и ожидание ответа. По его истечении
кадр уже может быть принят, поэтому клиенту неизвестен исход операции.
Повтор требует идемпотентности либо прикладного механизма проверки результата.

Получательская capability означает возможность приёма. Сервер, который
держит её и не вызывает `recv`, остаётся живым; клиент может дождаться
только тайм-аута.

`SenderGone` и `Timeout` позволяют продолжить приём.
`PeerClosed` и `Revoked` требуют завершить работу с этой capability.
Поле `badge` действительно до следующей операции над IPC-буфером потока.

Событие ухода значка не отменяет выданный `Reply`: он относится к
конкретному вызову. Клиент с принятым запросом ждёт ответа или закрытия
`Reply`, а не наличия получателей порта.

Порт сообщает о готовности приёма сигналом `READABLE`
([syscalls.md](syscalls.md#сигналы)). Поток ждёт этот сигнал вместе с сигналами
других объектов через `SignalWaitMany`, затем вызывает `recv` в режиме опроса.
Опрос нужен потому, что отправитель может уйти по сроку раньше приёма.
