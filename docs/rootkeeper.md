# Rootkeeper

`rootkeeper` — это корневой процесс, с которого начинается загрузка всей
userspace-подсистемы. `rootkeeper` владеет запуском и жизненным циклом системных
компонентов.

Супервизор выполняет загрузку userland согласно записи плана. Из неё он берёт
виды слотов, рёбра зависимостей и жизненный цикл. Путь программы и имя провайдера
слота приходят той же записью.

## План загрузки

План — отдельная запись userland-образа `/boot/rootkeeper/plan`. Манифест образа
отвечает на вопрос, что лежит в образе; план — на вопрос, что и с какими
аргументами rootkeeper поднимает ([userland.md](userland.md#образ)).

Источник плана — host-side `system.toml`, который сборщик образа проверяет и
кодирует в запись. Невалидный `system.toml` ломает сборку, и композиция,
которая не поднимется на устройстве, не доходит до образа.

```toml
version = 1

[[components]]
executable = "namespace-router"
memory_limit = "8M"
startup_timeout = "2s"
on_failure = "restart 2 then halt"

[[components]]
name = "clock"
executable = "driver-pl031"
memory_limit = "1M"
on_failure = "detach"
```

| Ключ              | Значение                                                  |
|-------------------|-----------------------------------------------------------|
| `executable`      | идентичность программы компонента                         |
| `name`            | имя экземпляра; без ключа — идентичность программы        |
| `memory_limit`    | предел памяти компонента                                  |
| `on_failure`      | политика отказа: перезапуски и исход их исчерпания        |
| `startup_timeout` | конечный срок доставки каждого кадра стартовой транзакции |
| `after`           | компоненты, которые поднимаются раньше без обмена с ним   |

Ссылки на компонент идут по имени экземпляра, а не по пути программы. Композиция
поднимает одну программу несколькими экземплярами и различает их именно по
имени. Под именем экземпляра идут процесс компонента, строки его журнала и
ссылки на него из `after` и слотов.

Экземпляры одной программы делят один каталог, а с ним и файлы. Запись каталога
называет сама программа своим объявлением, и композиция не выбирает состав её
файлов.

`memory_limit` — десятичное число с необязательным двоичным суффиксом `K`, `M`
либо `G`, кратное странице. Предел не преаллокация и не куча. В него
засчитывается всё, что занимает процесс. `startup_timeout` — число с суффиксом
`ms` либо `s`, по умолчанию `2s`. `on_failure` задан грамматикой
`[restart N then] halt|detach`, где `N` — число перезапусков сверх первого
запуска, `halt` останавливает композицию, а `detach` снимает компонент с неё.

План не задаёт, чем компонент наполняется. Сама программа объявляет слоты,
совместимости устройств и импортируемые протоколы
([userland.md](userland.md#манифест-компонента)), а сборка их связывает.

### Связывание

Слот — capability, которую супервизор кладёт в стартовую транзакцию компонента.
Какие у компонента слоты, объявляет его программа. Чем их наполнить, решает
сборка, сводя объявления композиции между собой.

| Вид слота    | Что объявляет программа             | Что получает компонент                                       |
|--------------|-------------------------------------|--------------------------------------------------------------|
| `userland`   | ничего                              | read-only регион userland-образа                             |
| `irq`        | строки совместимости, номер ресурса | `IrqLine` устройства                                         |
| `mmio`       | строки совместимости, номер ресурса | регион MMIO-окна устройства                                  |
| `service`    | имя протокола, имя экземпляра       | сессия service-порта экспортёра                              |
| `control`    | имя протокола, имя экземпляра       | клиентская capability control-порта провайдера               |
| `directory`  | имя экземпляра                      | сессия провайдера с каталогом компонента в корне             |
| `supervisor` | ничего                              | клиентская capability порта транзакции со значком компонента |

**Устройство.** Программа объявляет семейство строк совместимости, и подойти
может любая из них. Какая стоит на этой машине, показывает описание платформы в
рантайме. Супервизор перебирает строки по порядку и берёт первую, которую
описание содержит, а линию и окно выдаёт резолвер `lib/device-resolver`. Само
описание платформы драйверу не достаётся.

**Сервис и control-протокол.** Потребитель объявляет имя протокола, а провайдер
объявляет, что обслуживает этот протокол на своём service- либо control-порту.
Безымянный импорт сборка связывает с единственным провайдером протокола в
композиции, именованный (`instance`) — с названным экземпляром. Так композиция с
двумя файловыми системами связывает потребителя с той, которую он назвал.

Административные операции провайдера лежат на его control-порту, и клиентская
капа сервиса до них не достаёт. Кадр порта разбирает один `dispatch`, поэтому
два протокола на одном порту не уживаются.

Провайдер объявляет ключом `establishes_sessions`, откуда берётся сама сессия
([userland.md](userland.md#манифест-компонента)):

| Провайдер              | Как супервизор берёт сессию слота                                  |
|------------------------|---------------------------------------------------------------------|
| без объявления         | минтит из минтера service-порта провайдера под значком потребителя  |
| `establishes_sessions` | зовёт `ComponentSessions::open_session` на control-порту провайдера |

Установление принимает область. Пустая область берёт экспорт провайдера целиком,
непустая даёт сессию, суженную до неё. Ключ нужен провайдеру, чья сессия
содержит состояние. Файловая система держит за значком таблицу дескрипторов и
буфер данных ([filesystem.md](filesystem.md#установление-сессии)).

**Каталог.** Слот-каталог называет провайдера именем экземпляра, а сам путь
супервизор берёт из записи плана. Компонент этот путь не выбирает. Слот
наполняет та же операция установления с областью в этом пути, и компонент
получает сессию, корень которой равен его каталогу
([filesystem.md](filesystem.md#сессии-окна)). Путь наружу из каталога закрыт.
Имена отсчитываются от корня окна, а `..` отвергают правила пути.

Каталог приходит из конкретной файловой системы, минуя дерево имён.
Монтирования, присоединённые под каталогом компонента, в нём не видны. Это цена
того, что супервизор не разбирает прикладных контрактов.

**Userland-образ.** Слот `userland` получает read-only регион всего образа.
`imagefs` держит его как backing store файлов, а `init` читает как контейнер
записей. Несколько читателей одного артефакта допустимы.

### Транзакция расширения композиции

Та же машинерия поднимает компонент, которого нет в плане. Обычная программа
подаёт его записью через контракт `Supervisor` (`lib/supervisor-abi`) на порту,
который она получает слотом `supervisor`. Формат записи один с планом — тот же
кодек, то же разрешение слотов и рёбер, тот же жизненный цикл.

| Операция                  | Что делает                                                      |
|---------------------------|-----------------------------------------------------------------|
| `begin()`                 | открывает транзакцию вызывателя; набор прошлой транзакции снят   |
| `define(record, program)` | размещает в наборе запись плана одного компонента и регион программы |
| `commit()`                | проверяет набор целиком и поднимает его в топологическом порядке |
| `session(component)`      | отдаёт сессию поднятого компонента по имени экземпляра           |

Программа приходит регионом. Супервизор не открывает файлов и не разбирает
происхождение региона, а отображает его read-only и читает байты как программу.
Резерв поднятого набора режется из собственного ресурса супервизора.

Отказ любого шага снимает набор целиком — ни один его компонент не поднят, а
уже работающие компоненты транзакция не трогает. Отказ снимает и саму
транзакцию, и следующий набор начинается с `begin`.

Слот `supervisor` минтится под значком компонента, и на этом стоит единственное
правило допуска: `session(component)` отдаёт сессию только тех компонентов,
которых вызыватель сам определил. Компоненты плана через транзакцию не
достаются — их раздаёт статическое связывание.

Поднятый набор принадлежит композиции, а не incarnation вызывателя. Смена
вызывателя застаёт набор поднятым, и повторное определение тех же имён отвечает
`Duplicate`.

### Ступени загрузки

План содержит ступень 0 — минимум, с которого система начинается:
маршрутизатор имён, корневую файловую систему и владельца политики загрузки.
Остальные компоненты задаёт отдельное host-описание ступени 1, и сборка кодирует
каждый его компонент своей записью плана в каталоге образа `/boot/init/stage1`
([userland.md](userland.md#образ)).

Записи ступени 1 лежат в том же образе, а владелец политики находит их обычным
путём файловой системы — перечисляет каталог своей файловой сессией. Дисковая
файловая система примет ступень 1 так же, и код владельца политики от этого не
меняется.

Имя экземпляра занято набором целиком, и слоты ступени 1 называют экспортёров
ступени 0 по имени. Номера действуют внутри одной записи, а имена работают
через ступени.

### Политика загрузки

Состав дерева имён загрузки и набор ступени 1 принадлежат отдельному компоненту
`/boot/init` — монтирования супервизора не касаются. У него четыре
слота: `userland` под таблицу монтирований, `service` на корневую файловую
систему, `control` на `NamespaceAdmin` маршрутизатора и `supervisor` под
транзакцию расширения.

Оборот `init` идёт в одном порядке:

1. таблица монтирований читается записью образа. Корень на этом шаге ещё не
   смонтирован, и компонент ещё не получил каталога;
2. статически связанный корень монтируется маршрутизатору;
3. записи ступени 1 читаются файловой сессией;
4. набор подаётся супервизору транзакцией `begin -> define x N -> commit`;
5. прочие монтирования таблицы присоединяются сессиями, которые отдаёт
   `Supervisor::session` ([filesystem.md](filesystem.md#монтирование)).

Применив таблицу, `init` паркуется на своём control-порту. Дерево имён
существует, пока существует incarnation маршрутизатора, а `init` держит
control-слот на этот маршрутизатор. Смена маршрутизатора снимает `init` вместе с
собой
([«Уход провайдера снимает потребителей»](#уход-провайдера-снимает-потребителей)),
и свежая incarnation `init` применяет таблицу заново. Набор ступени 1 принадлежит
композиции и сохраняется при этой смене.

### Порядок и значки

Импорт протокола и слот-каталог задают ребро зависимости. Провайдер поднимается
раньше потребителя, и это ребро не пишется рукой. Порядок запуска
топологический и считается по объединению провайдеров слотов и рёбер `after`.
Остановка идёт в обратном порядке. Сборка проверяет ацикличность графа, а
супервизор вычисляет порядок по записи.
Транзакция расширения пополняет набор, и порядок пересчитывается по объединению
рёбер всего набора.

Позиция компонента в наборе задаёт три его значка: лог-сессии, service-сессии и
капы порта транзакции.

### Проверки сборки

Сборка сводит `system.toml` с манифестами названных им программ и отвергает
описание, которое не поднимется на устройстве. Отвергаются:

- **имена** — имя экземпляра пустое, с `/`, не-ASCII, длиннее ёмкости имени
  процесса либо повторяется у двух компонентов;
- **состав** — композиция пуста либо названа программа, которой образ не
  содержит;
- **значения** — предел памяти, срок запуска либо политика отказа не отвечают
  своей грамматике;
- **связывание** — импорт не разрешается в единственного провайдера. Такой импорт
  не обслуживает никто, либо обслуживают двое, либо названный экземпляр лежит вне
  композиции, либо он такого протокола не объявляет, либо компонент импортирует
  собственный экспорт;
- **каталог** — слот-каталог называет экземпляр вне композиции, сам компонент
  либо провайдера, который не создаёт своих сессий;
- **граф** — `after` называет компонент вне композиции или сам компонент, а
  рёбра зависимостей замыкаются в цикл;
- **ёмкость** — композиции нужно больше wait-объектов, чем допускает ожидание,
  оценка числа handle супервизора превышает таблицу либо дерево метеринга не
  укладывается в потолок глубины.

Отдельно сверяются объявления манифеста между собой. Слотов должно быть не
больше, чем содержит стартовая транзакция, а установление своих сессий не
объявляется ни без экспорта протокола, ни вместе с control-протоколом.

Описание ступени 1 проверяется теми же правилами над объединением ступеней, а
дерево имён загрузки сводится с той же композицией. Монтирование называет
экземпляр, и имени вне композиции сессию взять негде
([filesystem.md](filesystem.md#монтирование)).

Совместимости устройств сборка не проверяет. Описание платформы доступно лишь в
рантайме, и отсутствующее на машине устройство даёт диагностируемый отказ
загрузки.

### Провижининг устройств

Rootkeeper забирает у ядра capability образа, отображает его read-only и
разбирает запись плана до запуска компонентов. Отсутствие записи, её порча и
отсутствие устройства — разные причины `BootFailure`, и каждая гасит машину.
Отката на вкомпилированную композицию не предусмотрено. Состав системы задан
планом целиком.

Провижининг устройства отказывает по двум причинам. Первая - описание платформы
не содержит устройства, линии либо окна. Вторая - ресурс уже отдан другому
компоненту композиции. Занятость видна только в рантайме. Сборка не располагает
описанием платформы, а пересечение семейств `compatible` конфликт не задаёт.

Исключительность линии держит ядро — второй `bind` отвергается кодом
`AlreadyBound`. За окнами устройств ядро такого учёта не ведёт и выдаёт окно
каждому, кто спросит, поэтому выданные окна считает сама композиция. Учёт
покрывает только её, и процессам вне композиции rootkeeper окон не раздаёт.

### Провижининг каталога

Супервизор наполняет слот-каталог установлением на control-порту названного
экземпляра. Областью идёт `executable` из записи потребителя, а провайдер
отвечает сессией, открытой на этот каталог. Порядок здесь задаёт само ребро
зависимости. Провайдер поднят раньше потребителя, и монтирование каталогу не
нужно.
Провайдер без собственных сессий, отказ области либо исчерпанный startup-срок
переходят в `BootFailure` с кодом `Startup`.

## Managed startup

`ManagedComponent<R>` из `lib/managed-component` хранит waitable `Process`,
резерв бюджета, номер текущей попытки запуска и capability roots типа `R`.

```text
Launching --startup delivered--> Running --exit 0------> Exited
    ^  |                               |
    |  +--startup error--------------->+--exit nonzero--> Failed
    |                                                       |
    +-------------------- launch (generation + 1) ----------+
```

`Running` подтверждает только доставку стартовой транзакции через rendezvous.
Прикладной готовности это состояние не означает. Свои записи образа компонент
читает уже после подъёма.
Уничтожение `ManagedComponent` в состоянии `Running` завершает процесс.

## Incarnation и перезапуск

Запуск разрешён из любого состояния, кроме `Running`, и поднимает номер
поколения. Каждая incarnation получает свежие порты, свой ресурс и свежие слоты,
а capability ушедшей ядро отзывает. Предел числа запусков берётся из
плана и считает первый запуск. Политика без слова `restart` означает компонент
без перезапусков. Исход исчерпанного предела задаёт вторая половина
`on_failure`.

Backoff, интервал стабильной работы и обязательный readiness-сигнал в эту версию
не входят.

### Уход провайдера снимает потребителей

Капы ушедшей incarnation ядро отзывает, и потребитель остаётся с отозванной
сессией и с состоянием, которого нет у свежего провайдера. Поэтому рёбра
зависимости задают не только порядок запуска, но и порядок перезапуска. Уход
компонента снимает тех, кто от него зависит, и они поднимаются заново вместе с
ним.

Группа замыкается транзитивно по тем же рёбрам, которыми выводится порядок
запуска ([«Порядок и значки»](#порядок-и-значки)). Снятие идёт в порядке,
обратном порядку запуска, подъём — в прямом. Зависимость односторонняя, и уход
потребителя на провайдере не сказывается.

Предел числа запусков считает только отказы самого компонента. Снятие ради
чужой смены предела не тратит, и перезапуски провайдера не гасят композицию
исходом `halt` его потребителя, который сам ни разу не отказывал. Исчерпав
предел, провайдер целиком уходит из композиции, и его потребители остаются
снятыми. Слот у ушедшего брать негде.

## Владение и rollback

Отказ любого компонента при подъёме снимает уже поднятые. Композиция уходит
целиком, и её компоненты не остаются держать линии и окна устройств. Один откат
разбирает её — полномочия устройств, порт транзакции, резервы бюджета и
лог-сессии берутся уже внутри поднимаемой композиции. Откат транзакции
расширения — тот же путь, суженный до её набора.

Резерв бюджета компонента создаётся до первого запуска и действует до его
уничтожения. Ресурс каждой incarnation нарезается из этого резерва. Резерв —
капа-потомок родительского ресурса, поэтому закрытие родительской капы отзывает
его вместе со всем бюджетом компонента.

Композиция останавливается, когда критический компонент исчерпал предел
запусков, не поднялся заново либо не вернул свой бюджет. Тогда супервизор
завершает компонент и выходит с ненулевым кодом.

## Роли компонента

Каждой incarnation супервизор создаёт два порта и оставляет себе их клиентские
стороны. Клиентская капа control-порта содержит значок супервизора. Её уход
приходит компоненту как `SenderGone` с этим значком и завершает процесс. Прочие
отправители control-порта приходят импортом его протокола, и их уход цикл приёма
продолжает ([port.md](port.md#уход-значка)). Клиентские капы
service-порта супервизор минтит под значками — это единственный путь, которым
сервис компонента достаётся кому-то ещё.

Серверные корни обоих портов передаются компоненту одноразовой транзакцией
`ComponentStartup` вместе с производной лог-сессией, а следом за базовым кадром
приходят capability слотов
([userland.md](userland.md#стартовая-транзакция-компонента)). Какие контракты
обслуживать на этих портах, решает сам компонент. Маршрутизатор имён отвечает
`Namespace` на service-порту и `NamespaceAdmin` на control-порту, а файловая
система — `FileSystem` и общий контракт компонента `ComponentSessions`
([filesystem.md](filesystem.md#владение-портами)).

Супервизор ждёт одновременно process каждого компонента, поток log relay и
сигнал порта транзакции расширения. Уход компонента записывается в журнал под
его именем вместе с кодом выхода, после чего оборот поднимает следующую
incarnation. Завершение потока пересылки критично. Композиция не восстанавливает
этот поток.

## Запись плана

Формат записи — контракт между сборщиком образа и супервизором; кодек находится
в `lib/supervisor-abi`. Заголовок занимает 16 B:

| Поле            | Смещение | Размер | Описание                    |
|-----------------|----------|--------|-----------------------------|
| magic           | 0        | 8 B    | `RKPLAN\0\0`                |
| version         | 8        | u16 LE | версия формата (текущая: 1) |
| component_count | 10       | u16 LE | число компонентов (>= 1)    |
| reserved        | 12       | u32 LE | ноль                        |

За ним идут записи компонентов по 40 B заголовка:

| Поле               | Смещение | Размер | Описание                            |
|--------------------|----------|--------|-------------------------------------|
| launches           | 0        | u32 LE | предел числа запусков (>= 1)        |
| on_exhausted       | 4        | u8     | 0 halt, 1 detach                    |
| flags              | 5        | u8     | бит 0: компонент сам создаёт сессии |
| executable_len     | 6        | u16 LE | длина пути программы в байтах       |
| name_len           | 8        | u16 LE | длина имени экземпляра в байтах     |
| slot_count         | 10       | u16 LE | число слотов                        |
| after_count        | 12       | u16 LE | число рёбер `after`                 |
| reserved           | 14       | u16 LE | ноль                                |
| reserved           | 16       | u64 LE | ноль                                |
| memory_pages       | 24       | u64 LE | предел памяти в страницах (> 0)     |
| startup_timeout_ns | 32       | u64 LE | конечный срок startup в наносекундах |

За заголовком компонента идут байты пути программы, имя экземпляра, записи слотов
и имена экземпляров рёбер `after` — длина `u16` LE и байты каждого. Число
запусков считает первый. Грамматика `restart N then ...` записывает сюда `N + 1`.

Запись слота занимает 12 B:

| Поле           | Смещение | Размер | Описание                                                                   |
|----------------|----------|--------|----------------------------------------------------------------------------|
| kind           | 0        | u8     | 0 userland, 1 irq, 2 mmio, 3 service, 4 directory, 5 supervisor, 6 control |
| reserved       | 1        | u8     | ноль                                                                       |
| provider_len   | 2        | u16 LE | длина имени экземпляра-провайдера (service, directory и control)           |
| instance       | 4        | u16 LE | номер экземпляра устройства (irq и mmio)                                   |
| resource       | 6        | u16 LE | номер ресурса устройства (irq и mmio)                                      |
| selector_count | 8        | u16 LE | число строк совместимости (irq и mmio)                                     |
| reserved       | 10       | u16 LE | ноль                                                                       |

За ней идёт хвост: у service, directory и control — байты имени
экземпляра-провайдера, у irq и mmio — строки совместимости, каждая длиной `u16`
LE и своими байтами. У прочих видов нет хвоста.

Провайдер слота и рёбра `after` названы именем экземпляра. Номер компонента
действует внутри одной записи, а имя работает и через ступени загрузки.
Супервизор разрешает имя при провижининге, и неразрешимое имя даёт
`BootFailure::Provider`.

Декодер самодостаточен и отвергает всё, что не отвечает этому описанию: чужую
магию, другую версию, пустую композицию, ненулевые reserved-поля, значения вне
объявленных наборов, пустые строки и байты сверх записи.
